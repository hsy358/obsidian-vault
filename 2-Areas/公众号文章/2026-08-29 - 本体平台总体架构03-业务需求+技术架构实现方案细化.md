# 本体平台总体架构 03 - 业务需求+技术架构实现方案细化

> 来源：人月聊IT（系列 03，2026-08-29）
> 内容规模：完整 19 章 + 总结
> 重要性：**企业级本体驱动 AI Native 应用平台的全套架构范式**——和德勤 MVP 高度同构

## 一句话定位

**本体驱动（Ontology-Driven）的 AI Native 应用构建与成果交付平台**——不是合并若干历史项目，而是建立一套**场景驱动的智能交付机制**：

- **统一平台** → 理解目标、规划过程、治理资产
- **专业引擎** → 完成具体任务
- **本体模型** → 保证各环节使用同一套业务语义
- **工作流** → 保证整个交付过程可执行、可暂停、可恢复、可追溯

---

## 第一部分：核心命题

### 企业数字化的核心矛盾（**强共鸣**）

> "企业数字化发展到一定阶段后，主要矛盾不再是没业务系统，而是**系统数量多、业务语义分散、数据难以复用、指标口径不统一、应用建设周期长、AI 难以获得可靠上下文**。"

每一层都在进行**语义翻译**：
- 需求文档 → 可能无法表达业务真实意图
- 数据库字段 → 可能无法说明业务对象和规则
- 指标 SQL → 可能脱离原始业务口径
- 大模型看到数据 → 也无法判断字段是否可靠

→ **最终得到的是多个彼此独立的局部系统，而不是一套可持续演进的业务语义资产**

### 本体驱动平台的核心判断

> "企业需要一个位于需求、应用、数据和 AI 之间的**统一业务语义层**。这个语义层不能只是知识图谱或说明文档，而必须能够被**程序读取、校验、引用和执行**。"

### 第二个问题：用户的目标不是用引擎，而是获得结果

客户不说"我要调用 X、Y、Z 引擎"，客户只说：
- "帮我分析销售下滑原因"
- "建设一个合同管理系统"
- "把现有数据库发布为查询 Agent"
- "发现供应商风险后自动通知负责人"

→ 平台必须先**理解问题属于什么场景**，再决定**使用哪些能力、需要哪些模型、如何组织步骤、哪些内容必须由客户确认**

## 第二部分：核心概念（7 个）

| 概念 | 职责 |
|---|---|
| **本体项目** | 平台管理业务语义和交付过程的基本空间 |
| **交付任务** | 用户希望平台完成的一次明确目标（构建应用 / 发布 Agent / 生成报告等）|
| **能力引擎 + 能力** | 实现一类专业职责的运行组件；**能力是控制面最小编排单位** |
| **场景配方** | 经过验证的交付流程模板（草稿 / 测试 / 发布 / 废弃，独立版本化）|
| **执行计划** | 场景配方针对当前任务实例化的结果（保存版本，调整记录原因）|
| **平台交付工作流 vs 客户业务流程** | 前者完成平台任务（探索 / 建模 / 连接 / 生成 / 输出），后者描述业务过程（M6 合同审批等）；两者**必须明确分离** |
| **交付物** | 平台最终/阶段性产生的可使用成果，**必须具有版本、状态、来源工作流和依赖资产** |

## 第三部分：V6 本体模型体系（核心建模规范）

### 9 个模型一览

| 模型 | 职责 | 使用边界 |
|---|---|---|
| **M1 对象** | 定义业务中真实存在的对象、属性、关系 | 大多数项目的基础 |
| **M2 行为** | 系统操作、查询入口、外部调用承接 | 需要定义行为时 |
| **M3 规则** | 跨对象 / 跨行为 / 事件驱动的规则 | **不堆简单字段约束** |
| **ME 事件** | 真实事实事件 + 生产订阅关系 | 不能把"未决判断"当事实事件 |
| **M4 跨对象事件协同场景** | 跨对象的事件协同 | **不能代替普通顺序流程** |
| **M5 主体角色权限** | 角色、权限、数据范围、外部主体 | 涉及权限时 |
| **M6 流程** | 端到端协同和审批 | 不能因页面多步骤虚构流程 |
| **M7 查询统计与固定报表** | 正式跨对象查询 / 统计 / 固定报表 | **不是 BI 指标模型** |
| **MU 用户界面** | 生成或追溯 UI | 需要 UI 时 |
| **MM 对象数据表映射** | 连接已有数据库或明确持久化 Mapping | 物理持久化时 |
| **MI 接口模型** | 系统对外提供接口或依赖外部接口 | 集成时 |

### 关键模型选择原则（**精彩**）

> "平台支持全部模型不意味着每个任务都要创建所有模型。模型是否出现**必须由真实业务语义和交付目标决定**。"

**典型场景的模型组合**：

| 场景 | 模型组合 |
|---|---|
| 新建业务应用 | M1 + M2 + M3 + M5 + M6 + M7 主体，根据事件协同增 ME + M4，需要 UI 增 MU，需要 DB 增 MM，需要集成增 MI |
| 存量系统逆向建模 | **从 MM 和 MI 切入**→ 通过元数据推导 M1 → 业务文档补充 M2、M3、M5、M7 |
| 经营分析 | M1 + MM + 指标扩展模型 + 分析场景资产，需要正式查询/报表加 M2 + M7，涉及权限加 M5 |
| Agent 构建 | M1 + M2 + M5 + MI；查询型加 MM + M7；决策型加 M3；触发自动化加 ME + M4 或 M6 |

### 数据分析扩展模型（**指标独立**）

> "V6 已经明确 M7 不是 BI 指标模型，因此平台需要在**不改变 V6 现有语义**的前提下，引入可插拔的指标扩展模型。"

**指标 vs 对象 vs 物理表三者职责分离**：
- **指标模型**：业务度量语义（定义 / 公式 / 粒度 / 时间口径 / 过滤 / 维度 / 单位 / 适用范围 / 责任人 / 版本）
- **M1 对象**：业务对象
- **MM**：对象属性 ↔ 物理表字段映射
- **连接配置**：如何访问数据（账号 / 网络）

→ **SQL 只是某个数据源方言下的执行实现，不能成为指标业务定义本身**

## 第四部分：控制面 + 执行面（核心架构）

### 控制面（Control Plane）

**9 个核心模块**：

1. **统一任务入口 + 上下文收集** — 接收自然语言 / 文档 / DB 设计 / 接口 / 已有本体
2. **意图与场景分析器** — 识别用户目标、交付类型、业务范围；**置信度不足时主动提问**
3. **场景配方管理** — 配方库：草稿 / 测试 / 发布 / 废弃，**独立版本化**
4. **能力注册与发现** — 控制面认识执行面的唯一入口；每项能力声明 ID / 版本 / 引擎 / 输入输出 / 依赖 / 权限 / 资源 / 幂等 / 事件
5. **模型选择器** — 根据场景、需求证据、交付物形成模型集合（**持续监控变化**）
6. **计划生成器** — 把配方 / 能力 / 模型 / 资产 / 约束组合为执行计划；**静态检查**（环路 / 类型 / 权限 / 预算 / 危险操作）
7. **工作流运行 + 状态管理** — 至少 11 种（等待输入 / 资源 / 准备执行 / 执行中 / 确认 / 成功 / 失败重试 / 失败人工 / 跳过 / 取消 / 补偿）
8. **人工任务与决策中心** — 集中呈现：需求确认 / 低置信度 Mapping / 模型错误 / 指标口径 / 权限 / 代码差异
9. **项目、资产与版本中心** — 资产类型 / 版本 / 状态 / 所有者 / 来源 / 依赖 / 元数据统一管理
10. **追溯、审计与成本中心** — 全局追踪标识 + 场景分析 / 配方 / 计划 / 能力 / 资产 / 决策 / 模型 / Token / 耗时 / 错误

### 执行面（Execution Plane）— **18 类能力引擎**

| # | 引擎 | 核心职责 |
|---|---|---|
| 1 | 需求探索 | 一句话目标 → 结构化需求（**不是普通聊天模块**） |
| 2 | 本体模型 | V6 全部模型支持；正向 + 逆向建模；一致性校验；版本；差异；影响分析 |
| 3 | 数据连接 | 安全访问企业真实数据和外部服务；统一处理认证 / 网络 / 元数据 / 分页 / 方言 |
| 4 | 数据探索 + Mapping | 理解 DB 表 / 字段 / 关系 / 样例；**置信度 + 推断依据** |
| 5 | 指标模型 + 计算 | 业务语义 ↔ 物理实现分离；计算前完整性检查；结果含数据集 / 公式 / 质量 |
| 6 | 数据分析 | 业务问题 → 逻辑分析任务（趋势 / 拆解 / 漏斗 / 分层 / 周转 / 风险） |
| 7 | AI 分析推理 | **受控上下文**内完成归因 / 风险 / 解释；事实区 + 口径区 + 约束区 + 任务区 |
| 8 | 应用生成 | 本体 + 技术架构规范 → 中间表示 → 代码；**增量生成关键，不覆盖人工代码** |
| 9 | API 与接口生成 | MI 为主契约来源；接口变化分析消费者 / Agent 工具 / 外部系统影响 |
| 10 | Skills 生成 | 本体 + 可调用能力 → Agent 技能资产；**最小必要上下文**（不是把所有模型文件简单拼接） |
| 11 | Agent 构建 + 发布 | Skills + 模型配置 + 工具权限 + 系统指令 → 可运行 Agent；**能力最小暴露** |
| 12 | 规则引擎 | 加载 M3 + 已批准规则；**无副作用**；高频规则可编译 / 缓存 |
| 13 | 事件引擎 | ME 事实事件；至少一次投递需幂等键；回路有去重 + 最大跳数 + 防抖 |
| 14 | 业务流程执行 | M6 端到端协同和审批；只使用稳定 ID 引用 |
| 15 | 报告与可视化 | 网页 / Markdown / Word / Excel / PDF；**每个数字定位到指标结果或数据集** |
| 16 | 本体能力网关 | 内部对象 / 行为 / 查询 / 规则 / 场景 / Agent 工具 → 外部（REST / MCP / 消息）|
| 17 | 大模型网关 | 模型供应商 / 密钥 / 路由 / Token / 预算 / 缓存 / 脱敏 / 成本 |
| 18 | 存储与制品 | 结构化资产 + 大文件制品 + Git 仓库；版本 / 校验 / 锁 / 归档 / 恢复 |

### 大模型网关的核心约束（**精彩**）

> "**AI 负责理解问题、补充通用知识、生成候选模型、选择场景配方、形成执行计划和生成分析建议**，但 AI 必须受到**本体规范、能力契约、数据权限、场景配方、人工门禁和结果校验**的共同约束。"

## 第五部分：动态编排机制

### 1. 配方优先、AI 补充

> "平台优先匹配成熟场景配方，因为**固定配方更稳定、更易解释，也便于积累测试和交付经验**。AI 主要负责理解用户意图、选择配方、填充参数、判断可跳过步骤和补充当前任务特有节点。"

### 2. 结构化计划 + 依赖图

- 节点引用具体能力版本
- 输入通过资产 ID 传递
- 输出声明资产类型
- 支持串行 / 并行 / 条件 / 人工 / 重试 / 子计划
- **单次执行计划内部不得形成依赖环**

### 3. 运行时上下文（**关键**）

> "引擎之间**不传递无限增长的聊天记录**，而是读取**明确版本的结构化资产**，并由上下文构建器生成当前步骤所需的最小输入。"

### 4. 检查点 + 恢复

- 重要阶段完成后形成检查点
- 失败 / 重启 / 暂停后从最近检查点恢复
- 已完成且输入未变化的节点不重复执行
- **上游资产变化时，通过依赖图判断哪些节点失效**

### 5. 异常分类 + 补偿

| 异常类型 | 策略 |
|---|---|
| 输入缺失 | 补充输入 |
| 模型校验失败 | 自动修复 / 重试 / 切换模型 |
| 连接失败 | 重试 / 切换版本 |
| 权限拒绝 | 回退 / 跳过 / 转人工 |
| 资源超限 | 切换模型 / 限流 |
| AI 输出不合格 | 要求模型修复 / 标记低置信度 |
| 构建失败 | 保留中间表示 + 构建日志 |
| 外部服务不可用 | 重试 / 切换 |

> "**补偿不是简单删除结果**。已经形成的资产保留为失败运行证据，正式资产是否回退由版本和发布策略决定。"

### 6. 人工门禁

- 企业特有规则 / 指标口径 / 低置信度 Mapping / 权限 / 写操作技能 / 生产发布 → 默认人工门禁
- **不能由单次 AI 规划自行取消安全门禁**

## 第六部分：典型场景（5 个闭环）

### 场景 1：新业务应用构建

需求探索 → 模型选择器 → 本体模型生成 + 评审 → 选择技术架构 → 应用生成 → 接口契约 → 编译 / 测试 → 追溯关系展示 → 验收发布

**核心不是一次提示词生成代码**，而是需求、本体、技术规范、中间表示、代码、测试、发布之间形成**稳定链路**。

### 场景 2：Agent 与 Skills 构建

需求探索（工具能力 / 数据范围 / 写操作 / 人工确认 / 错误处理）→ 模型建立（对象 / 行为 / 权限 / 接口）→ Skills 引擎形成最小技能集合 → Agent 配置（模型 / 工具 / 权限）→ 测试集（工具选择 / 参数 / 越权 / 异常恢复）→ 门禁发布

**核心原则**：**能力最小暴露**——Agent 能查客户 ≠ 能改客户；能调 API ≠ 能用 API 全部参数范围

### 场景 3：数据探索与经营分析（**第一阶段切入点**）

需求确认（对象 / 时间 / 口径 / 基准 / 期望报告）→ 只读数据源配置 → 数据探索识别对象 → Mapping 形成候选（低置信度人工确认）→ 指标引擎建立语义和计算计划 → 数据分析（多维拆解 / 趋势 / 异常）→ AI 推理（只使用相关本体 / 指标 / 规则 / 分析结果）→ 报告（数据范围 / 口径 / 证据 / 追溯）

**核心差异**：真实外部数据通过连接器受控进入；数据通过 Mapping 获得对象语义；指标定义独立管理；大模型在本体和事实范围内推理

### 场景 4：存量系统逆向本体化

连接 DB + 导入接口 + 业务文档 → 数据探索和接口分析形成候选 → 本体引擎生成 M1 / MM / MI → 业务访谈补充 M2 / M3 / M5 / M7 → **每个推导结果标记来源和置信度**

### 场景 5：事件驱动自动化

需求明确（哪些是事实 / 哪些是判断 / 哪些动作允许自动执行）→ 模型建立（M1 / M2 / M3 / ME / M4 / M5，可选 M6 / MI）→ 运行时由连接器或业务行为提供事实 → 规则引擎判断 → 事件引擎发布 → M4 / M6 组织动作 → 能力网关调用外部系统

## 第七部分：数据 / 权限 / 安全

### 5 层权限

| 层次 | 谁能做什么 |
|---|---|
| 平台管理 | 管理员配置引擎，但不能查看所有项目数据 |
| 项目资产 | 项目成员编辑模型，但不能连接生产数据库 |
| 能力调用 | 能调用某个能力，不代表可以调用其他能力 |
| 数据访问 | **控制面把调用者身份 / 项目 / 用途传递给数据连接引擎**，注入行级过滤 / 列级限制 / 脱敏 |
| 发布 | 涉及业务规则 / 指标口径 / 数据权限 / 生产发布必须保留人工确认 |

> "**不能先读取全部数据再由前端隐藏**。"

### 关键安全设计

- 密钥加密保存 + 密钥引用
- 日志 / 提示词 / 错误信息不得输出完整密钥
- 向外部大模型发送数据前执行敏感字段识别和脱敏
- 项目可限制只能使用本地模型
- SQL 默认只读 + 限制时间 / 行数 / 危险语句
- 外部 API 调用需要超时 / 重试 / 熔断 / 审计
- **写操作必须对应明确 M2 行为和权限，危险操作需要人工确认和幂等键**

## 第八部分：资产治理 + 可追溯性

- 需求 / 本体元素 / Mapping / 指标 / 能力 / 代码 / 报告都使用**稳定 ID**
- 平台通过**引用图**管理关系
- **删除对象属性时**，可定位受影响的：行为 / 规则 / 查询 / UI / Mapping / 接口 / 指标 / Agent / 报告

### 每类交付物的追溯链

| 交付物 | 追溯内容 |
|---|---|
| 分析报告 | 本体版本 / Mapping 版本 / 指标版本 / 数据源 / 查询时间 / 数据范围 / 分析计划 / 模型 / 提示词模板 |
| 应用制品 | 需求版本 / 本体版本 / 技术规范 / 模板 / 构建结果 |
| Agent | Skills / 工具 / 权限 / 测试集版本 |

- 资产采用草稿 / 评审 / 发布 / 废弃状态
- **已发布资产不能原地修改**
- **跨模型破坏性变化必须生成影响分析和迁移说明**

## 第九部分：总体技术架构 + 实施路线（**关键借鉴**）

### 平台前端

统一任务入口 / 项目工作台 / 需求工作台 / 本体工作台 / 数据连接工作台 / 工作流中心 / 人工任务中心 / 交付中心 / 管理控制台

### 后台

控制面服务 / 执行引擎服务 / 资产与治理服务 / 基础设施适配层

### 实施路线（**4 阶段**，**极关键**）

| 阶段 | 范围 | 切入点 |
|---|---|---|
| **第一阶段** | 平台控制面骨架 + **数据分析闭环** | 项目资产 / 统一入口 / 场景识别 / 能力注册 / 配方 / 计划 / 工作流 / 本体模型 / 数据连接 / Mapping / 指标 / 数据分析 / AI 推理 / 报告 / 追溯。**首个配方选择已有数据库经营分析** |
| 第二阶段 | 需求 → Agent 闭环 | 需求探索 / API 与 Skills 生成 / 能力网关 / Agent 构建 / 测试 / 发布 |
| 第三阶段 | 需求 → 应用闭环 | 技术架构规范 / 应用生成 / MU 页面生成 / M6 流程实现 / 代码仓库 / 构建 / 部署。**首批只支持边界明确的单体业务应用，不承诺复杂分布式系统全自动生成** |
| 第四阶段 | 增强 | 事件自动化 / 企业治理 / 多租户 / 模型市场 / 配方市场 / 影响分析 / 成本治理 / 团队协作 |

### 第一阶段验收标准（**极精彩**）

> 用户提出一个经营分析问题后，平台能够：
> 1. 识别场景并解释选择理由
> 2. 推荐本次所需模型和引擎，**说明不适用模型**
> 3. 生成可审查的执行计划
> 4. 配置只读数据源并识别表字段
> 5. 形成 M1 和 MM 候选、展示置信度并接受人工修正
> 6. 建立指标定义和逻辑分析计划
> 7. 在权限范围内执行物理查询
> 8. 基于本体、指标和真实数据生成结论
> 9. 输出包含证据、口径、数据范围的报告
> 10. 从报告追溯到全部输入和执行记录
> 11. 任务失败后能够从检查点恢复
> 12. 新增第二个分析配方时**不修改核心工作流代码**

> "平台还需要证明**本体确实参与执行**，而不是生成后闲置。"

## 第十部分：关键风险 + 控制原则

| 最大风险 | 控制方式 |
|---|---|
| 产品风险：把平台做成**能力菜单集合** | 统一任务入口 + 场景理解 + 工作流交付，让用户围绕目标而不是工具操作 |
| AI 风险：自由规划不稳定 | 配方优先 + 结构化计划 + 能力白名单 + 静态校验 + 人工门禁 |
| 模型风险：为了完整而虚构模型 | 按 V6 语义边界选择模型，所有元素要求需求证据，模型选择结果**必须可解释** |
| 数据风险：Mapping 和指标口径错误 | 置信度 + 人工确认 + 版本 + 质量检查 + 源结构变化检测 |
| 工程风险：平台范围过大 | **按 4 个闭环逐步建设，每个阶段形成可独立验收的业务价值** |

## 核心立场（**值得抄**）

> "本平台要解决的不是如何把历史项目放进一个新界面，而是如何把已经反复验证的需求、本体、数据、应用、Agent 和分析能力**重新抽象为一套统一交付体系**。"

> "用户最终看到的应当是一个能够**组织交付过程的 AI 工作台**。用户提出问题，平台解释理解，推荐场景和模型，生成工作流，逐步请求必要输入，调用合适引擎，并交付应用、Agent、报告或改进建议。"

> "这也是平台区别于传统 AI 助手的根本所在：**它不只生成答案**，而是在本体语义、真实数据、受控能力和可执行工作流基础上完成**可持续使用的业务成果交付**。"
