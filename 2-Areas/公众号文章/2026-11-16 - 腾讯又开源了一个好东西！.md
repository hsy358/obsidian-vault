# 腾讯又开源了一个好东西！

> [!info] 同项目不同视角

> 本文侧重 **Local vs 平台版** 的部署形态、LoopForge Local 的 `/start-devflow` 入口、内置 Classic/Portable 工作流与安装注意事项。

技术群里有朋友分享了腾讯开源的一个 AI 编程工作流平台，还挺有意思的，分享一下。

不知道大家有没有这种感受，就是用 Codex、Claude Code 等 Coding Agent 写代码或者修 Bug 的时候，确实可以直接把需求发给它们，但整个任务却还得自己盯着。

改完以后，还得检查需求有没有遗漏，让它跑一遍测试，再看看结果到底能不能交付。如果发现问题，就补充要求，让它继续改。团队如果还要求独立评审、人工验收，这些步骤也得安排进去。

这些要求可以写进提示词或者规范文档里，后续任务继续用。但每一步有没有执行、结果交给谁、什么时候停下来等人确认，往往还需要自己跟进。

腾讯开源的 **LoopForge** 提供了一套现成的做法：给开发任务配置工作流，Agent 写完代码后，按流程执行检查，到需要人确认的地方就停下来。

## LoopForge 是什么？

LoopForge 是腾讯开源的一个可以自托管的 AI 编程工作流平台。

CodeBuddy、Codex、Claude Code 等编程助手负责读写代码。LoopForge 则负责运行环境和任务流转，例如把实现结果交给评审角色，调用测试脚本，把报告送到人工审批节点。这些步骤的运行记录也会保存下来。

![](https://mmbiz.qpic.cn/mmbiz_jpg/icJuV9QZRqg6ejQKQt8EzGEO3sBzgXyFCanCE09nrg8kUco0DIcjLJswnFibuwHfZ7sTtc0kXzCNUuf8EfLowdad71uGibtJM5icGAfia7ctmfhU/640?wx_fmt=other&from=appmsg)
编程助手与 LoopForge 的分工示意如果你只想在自己的编程助手里用内置流程，可以安装 **LoopForge Local**。需要可视化配置工作流、集中查看审批和运行记录，再部署平台版。两种用法都在同一个仓库里。

## LoopForge 有什么用？

举个例子，假设项目的列表接口有个 Bug：没有查询结果时会报错，预期应该返回空列表。把复现方式和预期结果交给 Codex 或 Claude Code，它们就可以着手修改。

但团队可能还要求：改完要让另一个角色评审，跑一遍已有测试，最后由人确认结果。如果这类任务经常出现，就可以在 LoopForge 平台里配置一套流程：

**分析问题 → 修改代码 → 独立评审 → 执行测试 → 人工验收**。

在这套配置里，实现角色负责修改接口，评审角色检查需求有没有遗漏，脚本节点执行项目准备好的测试命令。

运行到人工验收节点时，流程停下来，等你查看代码和报告。假如测试通过了，但你发现“筛选后没有结果”这个情况仍然报错，就可以补充要求，把任务退回实现环节处理。测试能检查哪些情况，仍取决于项目准备了什么用例。

**LoopForge 的用处，就是把这些步骤和交接方式保存下来。** 下一次修复类似 Bug，可以继续用这套流程，并查看每一步的运行记录，不必每次重新安排谁来改、谁来查、什么时候停下来等人确认。具体的代码工作，仍由编程助手完成。

如果只是偶尔改一个小功能，直接用编程助手通常就够了。需要反复执行同一套评审、测试和审批要求时，才更值得引入这样的流程工具。

LoopForge 中文工作流，据官方流程整理修复 Bug 之外，项目还内置了后端开发、前端开发和产品方案等 SOP 模板。

## LoopForge 有哪些值得关注的功能？

### 把 Agent、脚本和人工审批串起来

LoopForge 提供可视化 SOP 编辑器，节点可以是 Agent，也可以是一段脚本或一次人工审批。

![](https://mmbiz.qpic.cn/mmbiz_png/icJuV9QZRqg5uZjwkkzn3j5SKjeUsXy2DiaTOuC27oIjTWJawQXhqh1uzwfHZ4k0HTJkIJY0utf4iam0VGJxb5hpOBLgAW2YpKV7XFku1auIFw/640?wx_fmt=png&from=appmsg)
LoopForge 流程设计与独立评审节点配置分析需求、编写代码可以交给 Agent；构建、测试、Lint 这些已经有明确命令的操作，可以直接配置为脚本节点。运行到人工审批节点时，流程会暂停，等人查看产物后再决定是否继续。

这样就能把“请记得跑测试”落实为一个真正需要执行的步骤。至于测试是否覆盖了需求，仍然取决于项目准备了什么用例，流程工具不会替我们补齐所有检查。

### 实现和评审可以使用不同角色

每个角色可以有自己的提示词、执行器、模型、规则、Skills 和 MCP 工具。

例如，实现角色关注代码修改，评审角色关注需求遗漏和潜在回归；团队的编码规范可以作为规则交给它们，已有工具则按需要配置。

![](https://mmbiz.qpic.cn/sz_mmbiz_png/icJuV9QZRqg4rOxCEAGo72tJ9kk09AJ5Z62ibrCXnFTxmEzJjibK2Dy1n3kMFkKX49WF1J5haFwSQxLwYIGPfCQ4xBW55yXSdEiawy2gAicOe0d4/640?wx_fmt=png&from=appmsg)
LoopForge 官方独立评审配置界面局部不过，换一个角色来评审，也可能漏掉同样的问题。涉及权限或数据迁移时，我还是会留下实际测试和人工验收这两步。

Cursor CLI 和 Antigravity 也出现在官方支持列表中，不过当前还没有安装进 SOP 沙箱。另外，部分辅助能力仍使用 CodeBuddy。准备换执行器的同学，需要先确认所用入口支持它，不能只按这份列表选。

### 验收不通过，可以退回指定步骤

下面的审批界面里，任务会停在等待验收的状态，供人查看代码和报告。确认结果没问题，就批准继续；发现遗漏，可以补充要求，把任务退回前面的步骤。

![](https://mmbiz.qpic.cn/mmbiz_png/icJuV9QZRqg7UibmVnZxNqJvz2GZU8HLMxqhGxfr3PzZ4gB5yq8e4a3WwyBVfgt2SOP2b25AU4N6oMMwr5e60poiaA2XoMDCibgzeZRbsekrmj4/640?wx_fmt=png&from=appmsg)
LoopForge 人工验收与退回重跑操作比如测试通过了，但需求里有个条件没实现，仍然可以退回实现环节处理。测试结果和人工验收在这里分别保留，不必因为测试全绿就放行。

退回会让相应步骤重新执行。已经推送的提交或其他外部变更，还需要单独检查，并不会因为点了退回就全部撤销。

### 每一步都能查看记录

运行记录里可以看到节点状态、工具调用、日志和各阶段产物。任务失败时，找到对应节点，先看报错和输出，再决定重试，或者从指定节点重新运行。

这些记录也方便交接。另一个人接手时，可以直接查看之前做过哪些修改、留下哪些文件，以及任务是不是还在等审批。

![](https://mmbiz.qpic.cn/mmbiz_jpg/icJuV9QZRqg4dpTQXmqXEu9uNqByBLRqctvqILHSCBeUicQmwleSNH8X8vgDSFRJFsWc0V394Lb8e8GUTn5yzfVYfsjJecREHNAtOUibWMDnKE/640?wx_fmt=other&from=appmsg)

## LoopForge 怎么使用？

Local 和平台版需要准备的环境不同：

Local

平台版

主要场景

个人在现有编程助手里使用工作流

团队共享流程、审批和运行记录

基础环境

Node.js 20+、Python 3.8+、受支持的编程助手

Docker、Compose、Python 3 等部署依赖

工作流

内置 Classic / Portable 工作流

可视化配置自定义 SOP

个人尝试可以先装 Local。安装这一步也可以直接交给 Codex、Claude Code 等 Coding Agent，在测试项目里打开它，把项目地址和要求发过去就行：

```
帮我按照官方文档安装 LoopForge Local，项目地址：https://github.com/Tencent/LoopForge
```

比如，用 Claude Code 安装完成后，可以输入下面这条指令，试着跑一个任务：

```
/start-devflow "修复这个项目中的一个 Bug，并运行相关测试"
```

上面的需求只是一个写法示例，使用时还要补上 Bug 的复现方式和预期结果。任务跑完，检查工作流产物和测试结果，才知道这次修复有没有完成。模型调用使用自己的凭证，费用也需要自己承担。

Codex 等其他宿主的启动入口见 Local 使用指南[1]。Local 目前只运行内置工作流。如果你已经在平台上配置了自己的 SOP，还不能直接导入 Local 独立运行，这部分仍在后续计划中。

平台版需要多维护一套服务。官方启动脚本会创建平台服务、MySQL，并初始化配置。默认部署还会通过宿主机 Docker socket 创建执行容器，适用对象是可信团队。如果打算开放给互不信任的用户，就不能照搬这套部署。账户访问范围和相关设置要先看部署与账户说明[2]。

平台还提供不需要模型 Key 的“脚本 + 人工审批”演示。可以先观察报告生成、等待审批、批准后继续的过程，再配置真实 Agent 任务。

## 值得尝试吗？

我愿意推荐大家关注它，主要是因为评审、测试和验收这几个步骤能保存下来，下一次任务继续用。已经有固定开发流程的团队，可以看看其中哪些环节适合交给 Agent。

至于用上以后能省多少时间，目前这些材料还回答不了。多跑一个评审角色会增加模型调用，维护工作流也要花时间。建议先用一个带验收测试的小 Bug 做比较，记录耗时和模型消耗，再决定要不要扩大使用范围。
