# 20ms 把 PDF 变成 Markdown！开源 OCR 神器快了近 300 倍

> 来源：量子位（文婷 发自 凹非寺）
> 项目：[thiagotigaz/ocr-it](https://github.com/thiagotigaz/ocr-it)（Y Combinator 孵化 Firecrawl 团队 CTO Nicolas Camara 发布）
> 发布时间：2026-08-29 11:59

## 一句话定位

**OCR It**：Chrome/Firefox 浏览器扩展，把不可复制的 PDF 转成清晰的 Markdown。**20ms / 页**（比 Docling 快 ~300 倍），**100% 离线**，**无需 API Key**，**不索取任何网站权限**。

## 核心特性

### ⚡ 性能

- **20ms / 页** OCR 处理（用户视角："刚点完确定还没眨完眼"）
- 对比：质量与 Docling 旗鼓相当，速度 **~300x 快**
- 3 秒可处理 200 份 PDF

### 🔒 隐私 / 离线

- **Offline via Bundled Tesseract**——本地 Tesseract OCR 引擎，不联网
- **不需要 API Key**
- **不需要任何网站权限**——只在需要"自动运行 / 跨域 iframe"时才按需申请
- 适合处理敏感文档（合同、内部报告等）

### 🎯 工作流

**手动档**：
1. `Option+Shift+R` 框选识别区域 → `Enter` 保存
2. `Option+Shift+S` 触发单页识别 → 自动翻页
3. 重复操作直到结束
4. 面板里检查 / 修改 → "Copy all" / "Download .txt"

**自动档**：
- `Option+Shift+A` 或点 "Start auto-run" → 自动循环 截图→OCR→翻页
- `ESC` 中途停止

### 🛡 防误触保护

**自动停止条件**：
- 连续识别到两张相同页面
- 无法继续翻页
- OCR 失败
- 达到 300 页上限

### ⚠️ 短板（实测共识）

**目前只能相当顺手地处理版式简单、文字清晰的 PDF**——复杂版式（标题 + 脚注 + 表格 + 数学公式 + 正文段落混排）还不行。

**浏览器内置 PDF 阅读器暂时不支持自动翻页**——这类 PDF 用手动档处理。

## 适用场景 vs 不适用场景

| ✅ 适合 | ❌ 不适合 |
|---|---|
| 扫描版电子书（连续文字、版式统一）| 财报 / 合同（表格 + 脚注混排）|
| 单栏排版论文 | 招股书（章节层级 + 多元素混排）|
| 截图 OCR 转文本 | 数学公式密集的论文 |
| 文字清晰的内训文档 | 复杂双栏 / 三栏学术论文 |
| 敏感文档（离线无权限）| 浏览器内置 PDF 阅读器 |

## 🧠 小助分析（不强挂钩，按 7-8 分析偏好走）

### 一句话方法论

**OCR It 体现了 AI Native 工具的三个核心设计原则**：
1. **极致速度**（20ms 让"实时"成为可能）
2. **零摩擦启动**（离线 + 无 Key + 无权限）
3. **明确边界**（不强求解决复杂版式，明确告诉你"什么时候用不了我"）

这三个原则在 Firecrawl 团队的其他产品（Mendable / Firecrawl）也一脉相承。

### 三个可能的应用场景（不预设特定项目）

#### 场景 1：平时读论文 / 文档的"快速转录"

- **背景**：何大人工作里会有大量 PDF 文档（招聘 JD、客户合同、行业报告等）需要快速消化
- **价值**：20ms / 页 + 离线 + 无权限 → 装一个 Chrome 扩展就能解决"扫描版 PDF 不能复制文字"的痛点
- **风险**：复杂版式不行 → **不适合**混排 PDF（财报、招股书、合同）
- **建议**：**值得装**，但要先用一个简单版式 PDF 试，确认本地 OCR 质量够用

#### 场景 2：vault 文档处理流程的潜在升级点

- **现状**：TOOLS.md 里的 PDF 处理流程（重命名 + Inbox + sidecar）只涉及元数据，**没有 OCR 步骤**
- **未来可能**：如果 vault 里开始大量堆 PDF 内容（不只是元数据），OCR It 这种工具可以做"快速内容索引"——但**现在 vault 主要是 markdown 笔记 + 二进制存档**，OCR 不是瓶颈
- **建议**：**不急**，先观察 vault 里 PDF 数量是否爆发增长再说

#### 场景 3：观察 AI Native 工具的产品哲学

- **Firecrawl 团队的三个产品**（Firecrawl / Mendable / OCR It）都贯彻同一原则：**快、零摩擦、明确边界**
- **方法论可借鉴**：做工具类产品时，**别试图解决所有问题**——OCR It 明确说"复杂版式不行"，反而比"什么都支持但都不精"更值得信任
- **建议**：如果未来做德勤 MVP 的工具组件（OCR / 文档抽取 / 表格识别），**照搬这三条原则**——别追求全场景覆盖

### 🎯 与德勤项目（不强挂钩，仅作观察）

德勤客户场景大概率有大量复杂版式 PDF（财报 + 表格 + 脚注 + 章节层级），**OCR It 直接用不上**——但其设计哲学值得借鉴。

如果德勤 MVP 真要做 PDF 处理能力，**建议用 Docling 等支持表格 / 公式的方案**，而不是 OCR It。OCR It 更适合"快速摘录文字"的轻量场景。

### ⚠️ 一个未验证的事

文章说"20ms 比 Docling 快 300 倍"——这是 Firecrawl 团队的自测数据，**未独立验证**。Docling 的实际速度取决于 PDF 类型和硬件。建议如果真正要用，先在自己的 PDF 上测一遍。

### 📌 一句话结论

> **OCR It 是一个"够快 / 够轻 / 边界清晰"的浏览器扩展 PDF OCR 工具**——值得装一个作为日常 PDF 处理的轻量选项，**但复杂版式场景下仍需 Docling / 商业 OCR**。
