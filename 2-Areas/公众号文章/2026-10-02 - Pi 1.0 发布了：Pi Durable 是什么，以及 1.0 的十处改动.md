# Pi 1.0 发布了：Pi Durable 是什么，以及 1.0 的十处改动
**Pi 1.0.0 已发布**（2026-10-01，npm 上的 `latest` 已经是 1.0.0）。

官方在发布说明里的定位是一句话：**一个经过加固的、极简的、可扩展的 agent harness，你可以把它变成自己的东西。** 而首页那句标题更直接——**"Pi 1.0 with Pi Durable. Go make them yours."**

这篇讲清两件事：**那个新出现的 Pi Durable 是什么**，以及 **1.0 到底改了哪些**。

## 三句话版本

- **1.0 的主题是"稳"**：官方强调"**我们等一个东西被证明之后才采纳**，权衡它真正的功能与它带来的复杂度"——所以这次的改动以加固、瘦身、认证与体验为主，不追新概念；
- **Pi Durable 是随 1.0 一起发的实验性新包**：它不是"更好的 Pi"，而是**另一个用途的 harness**——**为长跑、耐久、可塑的 agent 而生，能跑在任何地方**；
- **最能立刻感受到的改动有两个**：**codemode 的提示词开销降了约四成**（GPT-5.6 下同一次请求从约 5300 token 降到 3300），以及**全屏成为默认界面**。

## 一、1.0 的信号：克制

先看官方自己的说法，因为这决定了怎么理解这一版：

> **Pi 1.0：一个经过加固的、极简的、可扩展的 agent harness，你可以把它变成自己的。** ……**Pi 以极简著称，我们很在意守住这条线。** 当 agent 工具链每周都在变的时候，很多改动并不长久——**Pi 不走这条路。我们等一个东西被证明之后，才考虑采纳它，权衡它真正的功能与它带来的复杂度。**

所以这一版没有"架构重写"式的新闻。它列出来的改动，几乎都能归到三类：**省钱（token）、加固（认证与错误）、体验（界面）**。而真正的"新东西"，是那个被明确标注为**实验性**的包。

> **一句话小结**：1.0 的意义不在"加了多少功能"，而在**官方把"稳定性"当成发布标准**——所以这一版最该看的是"加固了什么"。

## 二、Pi Durable 是什么：另一个用途的 harness

官方在公告里把动机讲得很清楚，值得原样理解：

> **Pi 这个 coding agent 是为"在你的（远程）机器上、在终端里、由一个人驱动"而设计的。如果进程死了，你去看一眼发生了什么，然后告诉它继续。** 这正是 Pi 1.0 专注并擅长的。
> 但我们的目标是把这项技术带给所有人，**以最适合他们的形式**。为此，我们需要一个 **能跑在任何地方、能从不同界面被触达、支持无限长的对话、能在灾难性的内部与外部故障中存活、并且允许多人来操控**的 harness。
> **Pi Durable 就是那个 harness。它不替代 Pi coding agent。**

这段话里的对照关系很值得记：

Pi coding agent

Pi Durable

你的机器 + 终端

**任何地方**使用者

**一个人****多人可同时操控**触达方式

**不同界面**对话长度

**支持无限长**进程死了

**人工看一眼、叫它继续****存储里接着干****所以它不是"Pi 的 2.0"**：一个解决"我一个人在终端里写代码"，一个解决"这个东西要跑很久、很多人一起用、还不能因为崩了就重来"。

> **一句话小结**：Pi Durable 不是升级版 Pi，而是**把同一套 agent 内核搬到"长跑 + 多人 + 任何环境"的场景**——两者的定位是并列的。

## 三、Pi Durable 的机制：先提交，再展示

这个包自带的说明里，有一句话可以当它的全部设计原则：

> **一个耐久（durable）的 agent harness。对话、模型轮次、工具调用、以及你自己的状态，都会在**任何东西被展示之前**先提交到存储。如果进程在轮次中途死掉，重新打开存储就会从它停下的地方接着做**。

它把这件事拆成四个概念，全部围绕"**什么是已提交的事实**"：

概念

含义

**Harness（执行体）****一份打开的存储 + 在上面运行 agent 的机制**。所有变更都走**同一条原子提交线**，并且**"提交先落库，然后才被展示"**

**会话**一份对话记录。可以创建多个、也可以**分叉**；句柄本身不持状态（靠标识比较）

**条目（Entry）****一条不可变的记录**：用户消息、模型回复、工具结果、系统提示词变更、**重置标记**，或者**你自己的类型**。**模型只看到最新一次重置之后的条目**

**提交（Commit）****一次原子写入**这几个概念合起来，解决的就是"崩溃之后怎么办"这个最难的问题：

- **存储是可替换的**：内存、SQLite、JSONL 都行——**要长跑就用落盘的那种**；重开之后**拿到的是同一个根会话**，再调一次"恢复"，**它会把上一个进程没做完的活儿接着跑**；
- **被打断的工作保持"待处理"状态**，而不是丢失或算成功；
- **重置不等于删除**：重置会开一个新的上下文，**模型看不到更早的条目了，但那些条目永远留在存储里**——**"给模型看的窗口"和"存储里的事实"被刻意分开了**。重置还可以带一句交接说明，相当于"从头开始，但先读这张便条"。
**任务与并发也在这个模型里**：

- **任务可以有子任务，并能"等待"**：等待时提交一个检查点，声明"我在等这几个子任务"，并给出策略（比如**任一失败就中止其余**）；
- **有一张实时的任务图**：每个节点的归属关系、状态、是否后台运行、以及它拥有哪些会话，都能一眼看到——**适合做任务面板或排障**；
- **会话"忙"的时候提交不会丢**：默认排队（当作后续输入），也可以声明"**插进去引导当前运行**"（会插在当前工具轮之后），或者"**忙就直接拒绝**"；你还能顺手提交一条**自己定义类型**的记录（比如"用户打开了一个文件"）；
- **界面看到的一切都是已提交状态**：结构化的视图和"逐次提交的事件流"两种订阅方式，都建立在同一份已提交事实上——**所以界面可以重连、可以换一个界面接上来看同一个会话**。
**这几点合起来回答了一个很实际的问题**：当"agent 要跑很久"时，**什么才是真相？** Pi Durable 的答案是——**存储里的提交才是真相，界面只是它的投影。**

> **一句话小结**：Pi Durable 的核心不是"能持久化"，而是**"先提交再展示 + 条目不可变 + 重置只改窗口"**——把"什么算发生过"这件事钉死在存储里。

## 四、codemode 瘦身：提示词省了约四成

这是这一版**每天都能感受到**的改动。官方给了具体数字：

> **codemode 消耗的提示词 token 少多了：在默认工具集且 codemode 打开的情况下，一次 GPT-5.6 请求从约 5300 token 缩到约 3300 token。**

（也就是说，**光是把"怎么用 codemode"讲清楚这件事，就省掉了将近两千 token**。）

省在三个地方，思路都是"**别重复、别铺满、按需读**"：

- **脚本里的全局对象只保留"一行一条"的摘要**，具体 API（比如模型相关的那些）**指向新的参考文档，模型需要时自己去读**；
- **已声明的工具改成"一行说明"**：说清"脚本里怎么调它、调用会解析成什么"，而**不再把它们完整的声明重复一遍**；
- **系统提示词里 codemode 的指引、以及 MCP 服务器那一节，都变短了**。
**这三条其实是同一个原则的三种应用**：**能指向就指向，能一行就一行，能读时再取就别提前铺。** 这也解释了为什么它敢用"默认不声明、按需发现"那套机制（我们前面几篇讲过）——**同一套省法，从工具一路贯彻到提示词本身。**

> **一句话小结**：codemode 这轮瘦身的本质是"**把重复的声明换成指针**"——省下的 token 是实打实的每次请求。

## 五、codemode 的两个新能力：会教你怎么改，还能画图

**第一，报错开始"教模型怎么恢复"。** 这是我认为被低估的一项改进——**错误信息从"说明发生了什么"升级成"说明该怎么改"**：

- 读一个不存在的工具或模型成员时，**会给出名字相近的候选**（比如把大小写写错了，它会指出正确的那个）；
- 调用模型分类/生图接口时参数不对，**会告诉你期望的形状**；
- 模型名不认识，**指向"查询可用模型列表"的接口**；
- 往脚本的存储里塞了过大的值时，**会解释这个存储是干什么用的**；
- **脚本生成了图片却忘了展示**，会得到一句提醒。
**这比"更聪明的模型"更划算**：模型在长跑里最贵的行为是**试错**——而一句"你是不是想写这个"，往往就把一次试错省掉了。

**第二，脚本里可以生成图片了。** 脚本可以调用图像模型（用**会话自己的凭据**），拿到的是**图像数据块，由展示函数附加到结果里**；**用量照常计入会话成本**（和分类调用一样）。扩展侧也有对应入口。

**把这两条放在一起看就明白了**：codemode 正在从"调用工具的地方"变成"**调用能力的地方**"——工具、分类模型、图像模型，都通过同一套脚本接口到达，**而账都记在同一个会话上。**

> **一句话小结**：一处让错误变成指导（省试错），一处让脚本能产图（扩能力）——**方向都是"让模型一次做对"。**

## 六、登录与认证：这版加固最多的地方

**① Radius 进了登录菜单。** 登录界面顶层多了"用 Radius 登录"这一项（带状态显示）；**登录之后会主动提议帮你把 Radius 的 MCP 服务器写进全局配置并重载**——**一步完成"登录 + 接服务"**。顺带一提，官方文档里 Provider 那一页现在**把 Radius 放在最前面讲**。

**② Anthropic 支持"复制码"登录。** 场景很具体：**浏览器在另一台机器上**（比如你在远程/无界面环境里）。这时登录流程改成"给你一段码，你复制到能开浏览器的地方完成"，再把结果贴回来。

**③ MCP 的 OAuth 做了四项加固**（这块最技术，但每一条都对应真实痛点）：

加固

解决什么

**可手动指定授权服务器的元数据地址**服务器**公布错地址、或者干脆不公布**时的兜底——不再依赖自动发现

**按 RFC 9207 校验 iss（签发方）**防"**看起来对但签发方不对**"的授权响应——这是 OAuth 里经典的混淆攻击面

**凭据按"服务器名 + URL"存储**让**同一个 URL 的服务器可以用不同账号登录**（此前按 URL 存会把它们混成一个）

**升级授权时保留已授予的范围**需要更高权限时**只补增量**，不必把已有的授权全丢一遍

另外两处小的体验修正：**登录/登出界面把"没配凭据的 provider"标成"未配置"**（措辞更准确），以及 **OAuth 的浏览器页面现在带 Pi 的彩色 logo**（这一步看着无关紧要，其实是"让你确认自己正在授权谁"——**防钓鱼的界面惯例**）。

> **一句话小结**：认证类改动读起来枯燥，但它们是"能不能给别人用"的门槛——**1.0 在这里花的功夫，比在功能上花的多。**

## 七、界面改动，和升级时要注意的

**界面**：**默认进入全屏**（TUI 全屏模式成为默认）；想保留终端原来的滚动历史，**把界面模式设回常规即可**（或启动时加对应参数）。另外新增了一个"**安静启动**"的取值：**保留版本号与快捷键提示的头部，隐藏模型范围行与已加载资源清单**——**想少点噪音又不想全静音的人，用这个。**

**升级要注意的破坏性变化**（只有一条，但会咬人）：

> **在脚本里用"检查某成员是否存在"来判断工具是否可用的写法，现在必须换成"名字在不在工具集合里"的写法。**

也就是说，"**探测式**判断"（读一下、看有没有值）**不再可靠**——因为读一个不存在的工具现在**会报错并给出候选名**（前面第五节说的那个改进）。**这是"更好的报错"带来的必然代价**：**以前"读不到"是静默的，现在它是显式的失败。**

**文档层面**：Provider 页改名为"Providers"，其中的"云 provider"一节改称"Provider 特定配置"，并把 Radius 提到最前。

> **一句话小结**：升级前只需记住两件事——**界面默认全屏了；脚本里"探测式判断工具"的写法要改成"存在性判断"。**
