# Ontilio快速体验：基于本体建模构建一套可持续运行的系统
# 速通Ontilio本体建模

> 摘要：本文以研发管理系统中的一次重大版本发布就绪评估为例，先拆解流程、数据、角色和入口，再从本体建模一路配置到页面、协作、权限与自动化，展示一项业务需求怎样在 Ontilio 中运行起来。

看一个研发中心版本发布的例子，“协作云 3.8.0”准备发布上线。

发布经理要回答四个问题：这个版本准备交付什么，测试结果、阻塞缺陷和风险是否可以接受，谁来复核和批准，团队从哪里查看结果并追溯当时的判断依据。

## 一、先把发布准入需求拆清楚

评估从汇集证据开始。系统根据需求完成情况、未关闭阻塞、高风险事项和失败检查计算结果，再交给测试负责人和研发负责人复核。每次重算都要保存当时的检查快照。

判断依据分散在发布、项目、迭代、需求、测试计划、缺陷和风险中。发布是评估中心，其余对象提供范围、质量和风险证据。发布经理发起评估，测试负责人确认质量，研发负责人批准重大版本，SRE 承接部署验证。

使用入口也随之确定：发布经理从列表进入详情页，测试和研发负责人通过待办复核并下钻证据，管理人员从驾驶舱查看阶段分布和整体健康度。后面的页面与视图都围绕这些任务配置。

把这些需求翻译成 Ontilio 配置，搭建清单就清楚了。

### 6. 用聚合公式计算发布指标

在“发布”的字段管理中创建三个计算字段。

计算字段

关系路径

计算方式与过滤条件

发布需求数

发布 → 承载迭代 → 迭代需求

`COUNT` 全部需求

发布需求完成率

同上

分子只统计“交付完成”的需求

未关闭阻塞数

发布 → 发布缺陷

只统计严重程度为“阻塞”且流程未关闭的缺陷

聚合公式可以先过滤目标对象，再执行 COUNT、SUM 等聚合。同一条关系路径因此能算出“全部需求数”和“已完成需求数”两个不同指标。

“发布需求完成率”由 IF、三次 COUNT、DIVIDE 和 MULTIPLY 组合而成：

-
-
-
-
-

```
IF(  COUNT(全部需求) > 0,  COUNT(业务状态 = 交付完成的需求) ÷ COUNT(全部需求) × 100,  0)
```

三次聚合都沿“发布 → 承载迭代 → 迭代需求”执行，只有分子增加目标对象过滤。最外层 IF 处理没有关联需求时的除零问题。公式还可以配置下钻字段，用户看到“未关闭阻塞数”为 2 时，可以继续打开对应缺陷。

## 四、为每次评估留痕，并扩展复杂规则

### 1. 用记录类型保存评估快照

今天的准入分是 72，关闭两个缺陷后可能变成 92。只保存当前字段，半年后就无法还原第一次评估时的证据。

创建“发布准入检查记录”，保存发布引用、检查时间、准入分、阻塞缺陷数、失败检查数、复核结论和执行人。发布本体回答“现在是什么”，不可变记录保存“当时发生了什么”。重新评估时追加新记录，不覆盖旧记录。

![](https://mmbiz.qpic.cn/mmbiz_png/sMicpVRiaZML24GYQV8ZAMEkxaa4v6xnq6adKHd3vobmYXealILRbgNykKRfzA1Q8LPQ20xicDfsbqP3PNhJuMXKAq7IZT3f86vzCQEq2SA6x0/640?wx_fmt=png&from=appmsg)

图 23：记录类型定义。

### 2. 让自动化追加检查记录

创建“发布准入检查留痕”自动化，监听“发布准入分”变化。规则触发后创建一条检查记录，并在发布详情中写入本次重算说明。这样每次计算都会留下对应快照，不需要发布经理手工抄录。

### 3. 用 Function 处理复杂逻辑

当一段规则难以通过现有配置清晰、完整地表达时，再使用 Function。本案例的公式已经算出需求完成率和阻塞数量，准入评分还要读取关联风险、执行多步扣分并受控更新发布对象。

创建 EDIT Function“计算发布准入分”，读取需求完成率、未关闭阻塞数、失败检查数和关联风险。案例规则是：

-
-
-
-
-
-

```
发布准入分 = 发布需求完成率           - 未关闭阻塞数 × 20           - 高风险数 × 10           - 失败检查数 × 8 最终结果限制在 0–100
```

高风险指风险评分不低于 3。这组权重只是演示规则。Function 校验并发布后生成固定 Revision；“计算发布准入分”动作绑定该 Revision，新版本不会让既有动作自动切换。

Function 只能读取自己声明的本体类型、字段和关系；写回发布时仍受类型定义、动作权限、版本和运行审计约束。它扩展的是现有业务模型，不另建一套旁路数据。
