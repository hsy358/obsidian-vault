# Loop Engineering 20种设计模式：真正拉开 Agent 差距的，是这套循环
模型 决定这一轮能做到什么程度， 循环 决定这一轮做错之后，系统还能不能变好。

上个月帮一个做电商客服 Agent 的朋友看代码，他给我复现了一个场景：用户问退货政策，Agent 调用了知识库工具，工具超时了，Agent 换了个说法又调用了一次，又超时，第三次干脆自己编了一个退货政策回复给用户，末尾还加了一句「如有疑问欢迎随时联系」。

日志里能看到它其实知道工具调用失败了——错误信息原封不动地出现在它的上下文里。但它没有停下来，也没有换个思路，就这么把一个已知错误的结果，包装成一个语气很自信的答案，交了出去。

这不是模型不够聪明。这个团队用的是市面上最好的几个模型之一。问题出在别的地方：没有任何机制去检查它这一步做得对不对，也没有任何机制告诉它，工具连续失败之后该怎么办。

它只是被训练成了「要给出一个回答」，仅此而已。

这件事之后我开始重新想一个问题：现在大家谈 Agent，总喜欢比模型、比参数、比 Benchmark 分数。但真正决定一个 Agent 系统能不能用的，好像越来越不是模型本身，而是模型跑在一个什么样的循环里。

同一个模型，套在一个只会「生成一次就交付」的架子里，和套在一个「会检查、会重试、会记住教训」的架子里，表现能差出一个数量级。这篇文章想聊的，就是这个架子该怎么搭——业内目前能看到的做法，大致可以归到 **5 大类、20 种循环设计模式**里。

3 多评审器

4 对抗性批判评审

不问「有什么问题」，问「你能证明哪里错吗」。

5 评判器集成

第二类 · 记忆循环

6 反思循环

任务结束后系统自己复盘，产生经验。

7 记忆更新

把反思结论写进记忆库，下次任务前能被检索。

8 错误库

10 记忆压缩

第三类 · 规划循环

11 规划 → 执行 → 重新规划

先定大致计划，执行几步后停下来看效果，不对劲就重排。

12 动态工作流

根据当下状态实时决定下一步怎么走。

13 目标分解

大目标拆成可被验证的子目标。

14 进度评估

依赖外部可验证信号判断进展，而不是自我感动。

15 约束满足

在 Token、时间、权限、合规限制内找方案。

第四类 · 探索循环

16 分支探索

17 树搜索

让靠谱路径继续展开，不靠谱的尽早剪掉。

18 辩论

正反双方互相攻击论点，由裁判给出结论。

第五类 · 系统优化循环

19 提示词自优化

回看历史执行结果，对 Prompt 做 A/B 迭代。

20 工作流自重构

根据运行数据自动替换模型、增减环节、调整路由。

02CONTROL LOOP

### 从「一次性函数」到「控制循环」

早期做 LLM 应用，逻辑基本上是：输入 → 模型 → 输出 → 结束。跟调用一个函数没什么两样。这套模式最大的好处是简单，坏处是模型没有任何机会从自己刚才做错的事情里学到东西。工具调用失败了，直接报错给用户；第一版方案有明显漏洞，也没人拦一下。

Agent 系统想解决的，正是这一点。它更接近一套控制系统：

观察 → 思考 → 行动 → 再观察

再往生产级别走一步，还得加上评估和调整：

观察 → 行动 → 评估 → 调整 → 观察

这套东西业内已经有不少共识了。Anthropic 在讲 Agent 架构的时候，会专门把「生成一个结果、另一个环节评估反馈、再优化一轮」这种模式单独拎出来讲；AWS 也把类似的评估-反思-修正循环，直接称作一种反馈控制回路——系统盯着自己的输出，按标准打分，不达标就触发修正。

这里有一个值得记下来的区分：

Prompt Engineering 解决的是「第一次怎么让模型做得更好」。Loop Engineering 解决的是「第一次没做好，接下来怎么办」。

这两件事不是替代关系，是叠加关系——你把 Prompt 写得再好，也挡不住工具超时、环境变化、计划走偏这些执行阶段才会冒出来的问题。

还有一个更底层的变化：以前我们看的是答案，现在得看的是轨迹。一个 Coding Agent 写代码、跑测试、测试失败、分析原因、改代码、再跑、通过——决定它能力上限的，早就不只是「第一版代码写得好不好」，而是「整个系统在失败之后还能不能自己往前推进」。

微软团队今年发的一个跑分体系 LoopsBench，专门就是冲着这个问题去的：它不再只看 Coding Agent 最后交没交出正确结果，而是看它在长周期任务里，能不能守住之前定下来的约束、不引入回归、按合理的顺序处理相互依赖的子问题。这跟「模型答对了没有」完全是两个维度的能力。

03FOUR STEPS

### 所有复杂循环，拆到底都是这四步

不管你后面看到的模式有多花哨，本质上都能拆成这四步：

行动 生成一个答案、调用一个工具、执行一段代码、制定一个计划。

观察 工具返回了什么、测试结果如何、环境发生了什么变化、用户给了什么反馈。

评估 这一步做得对不对，达不达标，是不是已经偏离了目标，还值不值得继续往下走。

调整 重试，重写，换一条路径，更新记忆，重新规划，还是干脆停下来。

没有评估的循环，只是在原地重复。没有调整的循环，只是在观望。没有记忆的循环，只能纠正眼前这一次错误，下次照样会犯。没有终止条件的循环，可能永远停不下来。

所以真正的 Loop Engineering，从来不是简单粗暴地写一个 while True 式的无限调用 LLM 的循环，而是要老老实实回答几个问题：什么时候该继续，什么时候该重试，什么时候该换策略，什么时候该认怂回滚，什么时候该把这次的教训存下来，什么时候该彻底停止。

带着这四步，我们正式来看这 20 个模式。

04QUALITY LOOP

### 第一类：质量改进循环——把硬伤消灭在交付之前

这一类要解决的问题很朴素：输出离开系统之前，能不能先过一道质检。

模式 1 · 生成 → 批判性评审 → 重写

一个模型负责生成，另一个角色负责挑毛病，把具体意见反馈回去，生成方拿着意见重写，这是这一类里最基础也是最常用的一个模式。Anthropic 把这种「一个生成、一个评估」的搭配，直接叫做 evaluator-optimizer，算是这个模式最典型的工程化表达。它适合长文章、代码、研究报告这类「好不好」没有一个绝对数字标准的场景。

模式 2 · 评分重试

跟模式 1 相对的另一条路：先给输出打分，分数够不够一个线，够了就放行，不够就重试。这种做法在有明确可验证指标的场景里特别好用——SQL 有没有执行成功、单元测试通不通过、JSON 是不是符合 Schema，这些都能直接判断，不需要靠「感觉」。

这两个模式经常叠加着用：能量化的地方用模式 2 卡一道硬门槛，剩下「读起来顺不顺」「逻辑合不合理」这种软性问题，再交给模式 1 的评审角色去挑。

模式 3 · 多评审器

一个评审角色也有自己的盲区，所以干脆配多个视角的评审——准确性、风格、安全、专业领域各配一个，分别打分再汇总，适合企业客服、金融分析、医疗法律这类容错率低的场景。

模式 4 · 对抗性批判评审

不问评审角色「这个答案有什么问题」，而是要求它「假设这个答案是错的，你能证明哪里错吗」「用户会用什么方式让它失败」。这个提问方式的转变，是把评审从「检查员」变成了「攻击者」，经常能挖出普通检查漏掉的东西。

模式 5 · 评判器集成

模式 3 里的多个评审打分打架了怎么办？投票或者加权汇总，最后统一出一个「通过 / 需要修改 / 直接拦截」的判定，这就是评判器集成要解决的问题。

举个具体的组装例子。做长文章生成，一套还算靠谱的流程是这样的：先出草稿，套上模式 3 分别过逻辑、风格、事实三道评审，用模式 5 把三份意见汇总成一个判定，不通过就带着意见套模式 1 重写，通过了就把这次成功的写法存下来（这个留到第二类记忆循环里再说）。这套流程跑起来，比「生成一次就发出去」要稳得多，代价是多花了几倍的 Token 和几秒到几十秒的延迟——这个代价值不值，得看你的内容值多少钱。

05MEMORY LOOP

### 第二类：记忆循环——这次的坑，下次别再踩

很多所谓的「记忆」，其实只是把聊天记录存了下来，顶多做个检索。但这不是真正有用的记忆。有用的记忆得回答两个问题：这次经历里，什么东西值得留下来？留下来之后，怎么影响下一次的决策？

模式 6 · 反思循环

任务结束后，系统自己复盘一遍「发生了什么、哪里失败了、为什么失败、下次该怎么改」，这一步产生的是经验。但注意，反思只是产生经验，经验只存在这一次对话里，任务一结束就没了。

模式 7 · 记忆更新

这一步是把反思的结论真正写进记忆库——少了这一步，模式 6 再深刻的反思也只是自我感动。举个反思之后能沉淀出来的例子：「遇到支付接口返回 429 的时候，不应该立刻连续重试，应该做指数退避。」这句话如果只停留在这一次任务的复盘里，下次系统还是会傻乎乎地连续重试三次。只有写进记忆、下次任务开始前能被检索到，它才真正起作用。

模式 8 · 错误库

在模式 7 的基础上，把记忆写得更结构化一点：别只记「任务失败了」这种没什么用的信息，而是按「场景、失败模式、根因、修复方式、验证方式」这个结构存下来，下次碰到类似场景先查一遍库，可能比重新试错快得多。

模式 9 · 成功模式

跟错误库对称，别只记教训、也要记成功——一次复杂需求最终跑通了，别只存一个「Done」，把「为什么这次成功了」提炼出来，慢慢就能攒出一套可复用的 Template 或者 SOP。

模式 10 · 记忆压缩

长期跑的 Agent 最大的麻烦往往不是没有记忆，而是记忆越攒越多，最后上下文全被过时的细节淹没——具体某一次做了什么这种「情景记忆」，得定期压缩成「以后遇到这种情况该怎么办」这种「语义记忆」，不然记忆库迟早变成一堆没人翻得动的流水账。

Anthropic 关于长时间运行 Agent 的实践里也提到过类似的观点：光靠压缩上下文窗口，不足以撑起真正的长周期任务，还得靠明确的状态记录和结构化的中间产物，在不同执行阶段之间把进度和经验传下去。

06PLANNING LOOP

### 第三类：规划循环——别在一条走不通的路上死磕

这一类和前两类的区别在于，前两类关心「这一步做得好不好」，这一类关心「整个计划还走不走得通」。

模式 11 · 规划 → 执行 → 重新规划

传统的工作流是提前写死的：A 到 B 到 C 到 D，不管中途发生什么都按这个顺序走。这个模式反过来：先定一个大致的计划，执行几步之后停下来看看效果，不对劲就重新规划，这个循环可以一直转下去。这是整个规划循环大类的主干模式，下面四个都是围绕它的具体细节。

模式 12 · 动态工作流

别提前把流程写死，而是根据当下的状态实时决定下一步怎么走，比如数据正常就直接分析，数据缺失就去检索，检索也失败了就转人工，风险太高就直接停下来，这跟固定流程图完全是两种设计思路。

模式 13 · 目标分解

大目标拆成子目标的时候，关键不是简单地把一件事切成几块，而是每个子目标必须要能被验证，不然 Agent 很容易出现「我觉得这一步应该算完成了」这种自我感觉良好的判断，而实际情况根本不是这样。

模式 14 · 进度评估

这一块我觉得值得单独强调一句：Agent 系统一个很容易踩的坑，是把「忙碌」当成了「进展」。它可能一直在生成看起来很合理的动作——调用工具、写代码、发消息——但现实世界的状态根本没有任何实质性的改善。

💡 进度判断这件事，尽量要依赖外部可验证的信号（测试通没通过、数据库状态变没变），而不是让模型自己给自己打分说「我觉得差不多了」。这两者的可信度差得很远。

模式 15 · 约束满足

Agent 找到的不该是「任意一个能解决问题的方案」，而是「在 Token 预算、时间、权限、合规、调用频率限制之内能解决问题的方案」，一旦踩过界，就该触发回滚重新规划（回到模式 11），而不是硬着头皮往下走。

Coding Agent 是这一类循环最典型的应用场景：接到需求先出计划（模式 11），写代码、跑测试，通过了就用模式 14 检查一下整体进度再接着做下一个任务，没通过就分析原因重写，重写几次还不行就回头重新规划，整个过程中把学到的东西写进记忆（回到第二类）——这跟眼下不少长周期编程 Agent 的工程实践思路是一致的：任务得拆成能持续往前推的小单元，靠规划、执行、验证、状态交接这几步撑起长时间的运行。

07EXPLORATION LOOP

### 第四类：探索循环——一条路走不好，那就多走几条

前面三类都是在一条既定路径上不断修正，这一类不一样，它的核心思路是：一次生成不够好，那就同时探索几条路径，再挑一条最好的。

模式 16 · 分支探索

最直接的做法：同一个问题并行生成几个不同的方案，评估完之后留下最好的那个。这在做产品方案、架构设计、创意类内容的时候特别有用，因为这类问题往往没有唯一正确答案，多几个视角反而更容易碰出好方案。

模式 17 · 树搜索

比分支探索更进一步：不是简单地「一次生成多个答案就完事了」，而是让看起来靠谱的路径继续往下展开，不靠谱的路径尽早剪掉——思路上跟 MCTS、Beam Search 这些经典搜索算法是相通的。

模式 18 · 辩论

让两个角色分别扮演正方和反方，互相攻击对方的论点和假设，最后由一个裁判角色给出结论。这个模式的价值不在于让两个 Agent 演一场戏，而在于逼着不同立场的假设互相碰撞，很多藏在单一视角里没被发现的漏洞，一辩就露出来了。

复杂研究类任务经常会把这几个模式串起来用：先把研究目标拆成几个子问题（模式 13），用模式 16 并行探索多条搜索路径，拿到的证据用模式 18 互相质证，评估完之后用模式 17 把最有希望的分支继续往下展开，最后再综合成一份结论。

08SYSTEM LOOP

### 第五类：系统优化循环——从优化任务，到优化系统本身

前面四类循环，优化的对象都是「这一次任务做得好不好」。最后这一类不一样，它盯的是做任务的系统本身。

💡 这一类建议放到最后再考虑。原因很简单：你得先有一套跑得比较稳定的循环，攒了足够多的历史数据，才谈得上「优化」这件事，不然就是在优化一个还没验证过有没有用的系统，容易做无用功。

模式 19 · 提示词自优化

回看历史执行结果，分析哪些失败模式反复出现，对 Prompt 做一些调整，再拿新旧两个版本做 A/B 对比，跑赢了才换成新版本。也就是说 Prompt 不再是人写死一次就完事，而是变成一个可以持续迭代的参数。

模式 20 · 工作流自重构

系统盯着自己的运行数据——哪个节点失败率高、哪个模型太贵、哪一步耗时最长、哪些步骤其实没什么用、哪些环节其实可以并行跑——然后自动去替换模型、增加或者砍掉某个评估环节、调整路由逻辑、改变并发数量。这时候被优化的对象已经从「某一次输出」变成了「整套工作流」。

09WHEN NOT TO LOOP

### 什么时候不该上循环

20 个模式说完了，得泼一盆冷水：循环不是越多越聪明，大部分时候恰恰相反。

之前见过一个真实的例子，一个团队做内部 FAQ 机器人，场景其实特别简单——员工问报销流程、请假规则这类固定问题。但他们照着某篇讲 Agent 架构的文章，硬是给这个场景套了模式 3、模式 8、模式 17 三层组合。结果原本两秒能出的答案，变成了四十秒，调用成本翻了十倍不止，用户满意度却没什么变化——因为这类问题本来就不太会出错，你花大力气去防一个根本不太发生的风险，纯粹是浪费。

每加一个模式，都要多花 Token、多等几秒延迟、多一层调试的复杂度、多一种可能出错的状态。这些成本是实打实的，而它带来的收益，只有在任务本身足够复杂、足够容易出错、足够值钱的时候才划算。

所以真正该问的问题从来不是「这个模式酷不酷」，而是：先想清楚值不值，再决定要不要加。

∞THE END

### 回到开头那个客服 Agent

前面提到的那个电商客服的例子，后来那个朋友加了两个东西：模式 2（工具调用失败就重试，连续失败超过阈值就直接转人工，不允许自己编答案），再加模式 8（记下「知识库接口超时」这种场景对应的处理方式）。改完之后编答案这种情况基本消失了。

没有换模型，也没有加复杂的架构，就是从 20 个模式里挑了最合适的两个，给它套了一个会检查、会重试、知道什么时候该认怂的循环。

这大概就是这篇文章想说的核心意思：模型决定的是这一轮能做到什么程度，而循环决定的是，这一轮做错了之后，系统还能不能变好。

Prompt 决定 AI 第一次怎么做，Loop 决定 AI 做错以后会不会变好。
