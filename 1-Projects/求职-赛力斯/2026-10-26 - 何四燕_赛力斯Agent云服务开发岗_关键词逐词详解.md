# 第一部分：Agent 工程化

## 1. LangChain 0.2.0

**是什么**：把 LLM 调用拆成可组合组件的框架——模型封装、Prompt 模板、Tool/Agent 编排、Retriever、Memory、Callback。0.2.0 是 2024 年的版本，**与 0.1 有明确 API 断裂**（下面第 8 条会讲这个坑）。

**你项目里怎么用的**：
- `llm/llmFactory.py` 里 `class PingAnGPT(LLM)` —— **继承 LangChain 的 `LLM` 基类**，实现 `_call` / `_stream` 两个方法，把自有大模型网关包成一个"LangChain 模型"
- `Agent/base.py` 用 `create_structured_chat_agent` + `AgentExecutor` 跑 ReAct 循环
- `tools/APITool.py` 用 `BaseTool` / `StructuredTool` 定义工具
- `llm/llmFactory.py` 用 `ChatPromptTemplate` / `MessagesPlaceholder` 组装 Prompt

**面试怎么答**：
> "LangChain 我是用它当**框架底座**而不是全部自己写。具体来说，我们把自有的大模型网关继承成 LangChain 的 `LLM` 实现（`_call` 和 `_stream` 两个方法），这样 LangChain 的 AgentExecutor、Prompt 模板、Tool 抽象就都能直接复用。
> 但有一条原则：**业务代码不直接依赖 LangChain 的具体 API**——所有模型调用都收敛到我们自己的 LLM 工厂层。因为框架升版本我们踩过坑，0.1 升 0.2 时 API 有断裂，业务层如果到处直接 import LangChain，升级就是灾难。"

## 2. LangGraph 状态机编排

**是什么**：LangChain 之上的**图式编排**框架。把流程建模成节点（Node）+ 边（Edge）+ 状态（State），节点读 State 写 State，条件边决定下一步走哪。支持循环（Agent 的 ReAct 天然是循环）、支持中断与恢复（checkpoint）。

**和普通 Chain 的区别**（这句要说出来）：Chain 是**线性 DAG**（A→B→C，一次性），LangGraph 是**带环的有状态图**——可以 A→B→A 循环，可以按运行时数据分支，可以把中间状态存下来做断点恢复。

**你项目里怎么用的**（`flow/base.py`，1310 行，这是最硬的证据）：
```python
from langgraph.graph import StateGraph, END
from langgraph.graph.message import add_messages

class FlowState(TypedDict):
    messages: Annotated[list, add_messages]   # 消息累加器（自带 reducer）
    input_exts: Annotated[dict, merge_dict]    # 字典合并（自定义 reducer）
    node_values: Annotated[dict, last_dect]    # 覆盖语义
```
- 节点类型用 `add_node` 注册：`llm` / `knowledge` / `tool` / `text` / `end` / 条件分支
- 边用 `add_edge` 连，`compile()` 编译成可执行图
- **关键是 `Annotated[..., reducer]` 这个设计**——多个节点可能同时写同一个 state 字段，靠 reducer 定义合并语义（`add_messages` 是追加、`merge_dict` 是合并、`last_dect` 是后者覆盖）。**这正是"并发节点写共享状态"的标准解法**，车机场景多路并行采集时也一样。

**面试怎么答**：
> "编排我用 LangGraph，因为它天然适合 Agent 这种**带循环、有条件分支、有共享状态**的场景。
> 关键是 state 的 reducer 机制——我们定义了一个 `FlowState`，每个字段用 `Annotated` 声明合并语义：消息是追加、扩展变量是字典合并、节点结果是覆盖。这样多个节点往同一个 state 写的时候不会互相覆盖，行为是确定的。
> 我们后台配的流程定义会被**动态编译成图**，节点类型覆盖 LLM、工具、知识检索、条件分支和结束——**新增一个业务场景不用改编排代码**，只要在后台画好流程。"

**加分补充（面试官会点头）**：LangGraph 的 **checkpoint 机制**让流程可以中断/恢复/回溯——你可以说"我们当时是自研了状态机，但回头看 LangGraph 的 checkpoint 和 human-in-the-loop 是我们缺的，企业级场景出问题时能回放定位是刚需"。

## 3. 配置驱动的 Tool 动态 Schema 注册

**是什么**：工具（Tool）= 名称 + 描述 + 参数 schema + 执行逻辑。Function Calling 场景下，模型只会"输出参数"，**真正的执行和参数校验在你的服务端**——所以参数 schema 必须是严格结构化的。

**"动态 Schema"**：不手写每个工具的 Python 类，而是**根据配置在运行时生成 Pydantic 模型**。

**你项目里怎么用的**（`tools/APITool.py`）：
```python
class HttpApiBaseTool(BaseTool):
    def __init__(self, name, description, tool_params_schema, url, tool_resp_schema):
        super().__init__()
        tool_params_schema = convert_pp_json(tool_params_schema)      # 配置格式归一
        input = create_dynamic_model(f"DyInput", tool_params_schema)  # ★ 运行时生成 Pydantic 模型
        self.args_schema = input
        self.tool_resp_schema = tool_resp_schema                        # 响应结构也声明
```
- `create_dynamic_model` 用 `create_model()` 按参数字典动态建 Pydantic BaseModel
- LangChain 的 `BaseTool.args_schema` 决定了**发给模型的 Function Calling 参数声明**和**框架侧的入参校验**
- 工具表来自 `agent_json['toolsInfo']` —— **后台配置**
- `create_http_resp_tools` / `create_flow_resp_tools` —— **工作流也能注册成工具**
- `convert_pp_json` / `convert_zk_json` 做配置→标准 JSON Schema 的归一

**为什么这很重要（面试要讲的业务价值）**：
> "运营要在后台新增一个工具，**不需要发版、不需要改代码**。以前一个接口对接要写一个 Python 类、走一次发版；现在后台配好接口、参数说明、响应结构，服务重启或热加载后工具就在表里了。对我们这种多 BU 使用的平台，这个提速非常明显。"

**面试怎么答**：
> "我们的 Tool 层是**完全配置驱动**的。运营在后台配 HTTP 接口 + 参数说明 + 响应结构，服务在运行时用 `create_dynamic_model` 动态生成 Pydantic 参数模型，注册进 LangChain 的工具表——**加工具零代码改动、零发版**。
> 三个细节值得说：
> ① **响应也做结构化裁剪**——我们声明了 `tool_resp_schema`，只把必要字段回灌上下文，否则一个接口返回几 KB JSON 很快就撑爆 token 预算；
> ② **工作流也能注册成工具**——`create_flow_resp_tools` 把一条 LangGraph 流程包装成一个 Tool，所以'工具'和'编排'在统一抽象下；
> ③ **参数格式归一**——`convert_pp_json` / `convert_zk_json` 处理不同后台来源的 schema 差异，避免每个工具各写一套。"

## 4. Function Calling / Tool Calling

**是什么**：模型不直接返回文本，而是返回**结构化的调用意图**（工具名 + 参数 JSON）。Function Calling 是 OpenAI 起的名，Tool Calling 是 Anthropic/其他厂商的叫法，**本质是同一个机制**：模型输出一个"我要调这个函数、参数是这些"的信号，由你的应用去真正执行，再把结果回灌给模型继续推理。

**关键认知（面试要讲对）**：
- **模型不执行任何东西**，它只是"申请调用"
- **参数校验是你的责任**——模型可能给出非法参数（类型错、幻觉参数名、越权取值）
- 工具**返回内容要受控**——原始大 JSON 进上下文会炸预算
- **工具描述就是 Prompt 的一部分**——description 写得好不好，直接决定选对率

**你项目里怎么用的**（`llm/llmFactory.py`）：
```python
data["tools"] = tools_list   # 工具声明发给模型
data["tools"] = self.tools_json
...
tool = {
    "name_for_human": item['name'],
    "name_for_model": item['name'],
    "description_for_model": item['description'],
    "parameters": [{"name":..., "description":..., "required":"True", "schema":{"type":...}}]
}
```
以及 `get_tools_prompt(prompt, tools)` —— **把工具声明拼进 Prompt 文本**，再配合 `tools_json` 一起发给后端大模型网关（平安 PA-GPT 用的是文本协议，不是原生 Function Calling）。

**面试怎么答**（这段能显示你懂原理）：
> "Function Calling 的本质是**模型只输出调用意图，不执行任何东西**——真正的执行、参数校验、错误处理全在我们服务端。所以有三件事必须自己做：
> ① **参数校验**：模型可能给非法类型、幻觉出来的参数名，甚至越权取值，服务端必须按 schema 校验并拦截；
> ② **返回值受控**：我们声明了 `tool_resp_schema`，只把必要字段回灌上下文；
> ③ **description 即 Prompt**：工具描述写得好不好直接决定选对率，所以我们要求描述里写清'什么时候用、什么时候不用'。
> 我们这边模型网关用的是文本协议，所以工具声明我们是**同时**以 prompt 文本和 tools_json 两种形式传过去，保证对齐。"

## 5. Prompt 版本化

**是什么**：把提示词从代码里拿出来，当成**可管理的工程资产**——有版本号、能灰度、能 A/B、能回滚、能对比效果。

**为什么必须做**：Prompt 一改，效果就变；不版本化就**无法归因**（这次答得好是因为改了 Prompt 还是因为换了模型？），线上出问题也无法快速回退。

**你项目里怎么用的**：
- `Agent/base.py` → `set_prompt()` 从 `/app/prompt_backup.pkl` 加载
- **SHA256 完整性校验**（下一条详解）
- `get_tools_prompt(prompt, tools)` —— **Prompt 与工具 Schema 联动生成**，工具改了 Prompt 自动跟着重生成，避免两边不一致
- `forceFlow` 开关 —— 确定性强、风险低的场景强制走工作流，**跳过模型推理**

**面试怎么答**：
> "提示词在我们这儿是**版本化的工程资产**，不是散在代码里的字符串。三件事：
> ① **加载即校验**——每次加载校验文件哈希，不匹配直接拒绝启动，不会带着一个被改坏的 Prompt 上线；
> ② **Prompt 与工具 Schema 联动生成**——`get_tools_prompt` 保证 Prompt 里描述的工具和工具表里注册的是同一份，不会出现"Prompt 说有、工具表没有"的漂移；
> ③ **效果可归因**——Prompt 改动、模型切换、工具变更，都能对应到具体的埋点指标（命中、成功率、人工兜底率），这样才知道改动是变好还是变坏。"

## 6. SHA256 完整性校验

**是什么**：对文件算一个 256 位哈希，任何一个字节被改动，哈希就完全不同。代码里存一个"期望哈希"，加载前算一次比对。

**在 Agent 场景为什么重要（这是本题的核心价值）**：
Agent 的 Prompt 文件是**运行时加载的外部资产**，不是编译进代码的常量。这意味着：
- 有人改了 Prompt 配置文件 → **行为静默改变**，线上出问题极难定位
- Prompt 里如果被塞进恶意内容（Prompt Injection 的持久化形态）→ **全量会话被劫持**
- 生产环境误传了测试环境的 Prompt → 效果诡异且难查

**你项目里怎么用的**（`Agent/base.py`，真实代码）：
```python
SAFE_HASH = 'cda9dd02b1e8007189c755dbe174d7be7ebe6c0f41796733d5c0443d842c81c0'

class AgentBuilder:
    @staticmethod
    def verify_file_integrity(file_path, expected_hash):
        with open(file_path, "rb") as file:
            file_data = file.read()
            file_hash = hashlib.sha256(file_data).hexdigest()
        return file_hash == expected_hash

    def set_prompt(self):
        if not AgentBuilder.verify_file_integrity("/app/prompt_backup.pkl", SAFE_HASH):
            raise ValueError("The file's hash does not match the secure hash. Aborting to prevent security risk.")
```
**注意这个顺序**：先验哈希，**不通过直接 raise 拒绝加载**——是"fail fast"，不是"打个警告继续跑"。

**面试怎么答（这段含金量最高，务必讲）**：
> "这一条我觉得是 Agent 工程化里最容易被忽略但很关键的安全设计。
>
> 我们的 Prompt 是**运行时加载的外部文件**，这意味着它是一份**运行时资产**——它可能被误改、被传错、被塞入恶意内容。而 Agent 的 Prompt 一旦被污染，**影响的是全量会话**，不是单个请求。
>
> 所以我们在 `set_prompt()` 里做了一件事：**加载前先算 SHA256，和代码里内置的期望哈希比对，不匹配直接 raise 拒绝加载**。是 fail fast，不是打个 warning 继续跑。
>
> 这条还和下面那个反序列化防护配套——我们 Prompt 是 pickle 存的，加载要走反序列化，而 **pickle 反序列化本身是 RCE 风险**（能构造出执行任意代码的 payload）。所以我们自定义了 `SafeUnpickler`，**用白名单机制只允许指定的几类 LangChain Prompt 类型反序列化**，其余一律抛 `PickleUnpicklingError`。
>
> 哈希保证'文件没被改过'，白名单保证'就算被改了也炸不了'——两层防护。"

## 7. 多模型工厂与热切换

**是什么**：把"用哪个模型"从业务代码里抽出来，做成**工厂 + 配置**。业务只声明"我要一个支持 Function Calling 的模型"，具体是 ChatGLM / DeepSeek / PA-GPT 由工厂按配置创建。热切换 = 改配置即生效，不发版。

**为什么必须有（三个真实理由）**：
1. **降级**：主模型挂了/限流，自动切备用模型，**这是可用性兜底不是功能**
2. **成本**：不同场景用不同档位模型（简单意图用小模型，复杂推理用大模型）
3. **演进**：新模型上线要能灰度，不能"改代码 = 全量上线"

**你项目里怎么用的**（`llm/llmFactory.py`）：
```python
from llm.llmFactory import PingAnGPT
from llm.glmFactory import ChatGLM
from llm.DeepSeekFactory import DeepSeekGPT
from llm.DeepSeekLocalFactory import DeepSeekLocalGPT
from llm.glmFactoryForCall import ChatGLMFC
```
`Agent/base.py` 的 `set_llm()` 按配置分发：
```python
llmInfo = self.agent_json["llmInfo"]
llm_type = llmInfo["type"]
if llm_type == 'PA':
    self.llm = PingAnGPT(temp, max_token, instruction, tools_json, memory, args)
elif llm_type in ('DeepSeek-R1-Distill-Qwen-32B','DeepSeek-R1-BF16','DeepSeek-V3-BF16'):
    self.llm = DeepSeekGPT(llm_type, temp, max_token, instruction, tools_json, memory, args)
elif llm_type == 'DeepSeek-R1-Distill-Qwen-7B':
    self.llm = DeepSeekLocalGPT(...)   # 本地部署
```
`llm/llmFactory.py` 里还有 `llmFactory.py / chatGlmFactory.py / DeepSeekFactory / DeepSeekLocalFactory / glmFactory / glmFactoryForCall` **六个工厂**——不同模型、同一模型的不同接入方式（远程/本地）、不同协议（对话/Function Call）各自一个。

**再加两个配套机制**：
- **Token 缓存**：`SimpleCache(ttl=1800)` —— 调网关要带 access_token，获取 token 是一次网络调用+签名，缓存 30 分钟省掉重复开销
- **签名鉴权**：`get_sign(rsaPrivateKey, requestTime)` —— RSA PKCS1_v15 + SHA256 签名，`openApiRequestTime` 参与签名（防重放）

**面试怎么答**：
> "模型层我们是**工厂 + 配置**。业务侧只声明要什么能力，工厂按 `llmInfo.type` 分发到具体实现——我们当时有六个工厂：ChatGLM、DeepSeek（远程）、DeepSeek（本地部署）、PA-GPT 自研、以及 Function Call 专用版本和流式版本。
>
> 这么做解决三个问题：**降级**（主模型限流或挂了，切备用，是可用性兜底）、**成本**（不同场景不同档位）、**演进**（新模型灰度不改代码）。
>
> 配套两个细节：**Token 缓存**——网关的 access_token 获取要走一次 RSA 签名加网络请求，我们用 TTL 1800 秒的缓存把它省掉；**请求签名**——`openApiRequestTime` 参与 RSA 签名，这是防重放的必要设计。
>
> 最重要的是：**业务代码一行都不直接依赖任何一家模型 SDK**。所有模型调用收敛在这一层，升级、降级、换厂商都在这一层完成。"

## 8. RAG 混合检索 + Rerank 全链路

**是什么**：RAG = Retrieval-Augmented Generation，检索增强生成——先从知识库捞相关片段，再让模型基于片段回答，**解决模型不知道企业私有知识、幻觉、以及知识过期**三个问题。

**"混合检索"**：向量检索（语义相似）+ 全文检索（关键词精确匹配）**两路并行**。
- 向量检索强在"意思相近"（问"怎么退保"能命中"退保流程"）
- 全文检索强在"专有名词/编号/型号精确匹配"（问"保单号规则 R-2024-17"向量会漂，全文不会）
- 两路互补，所以要混合

**"Rerank"**：**召回阶段用便宜的方法捞很多（几十条），排序阶段用昂贵的模型精排取 Top-K**。这是成本/质量的标准权衡——Cross-Encoder 需要同时看 query 和 doc，能算出更准的相关性，但不可能对全库跑。

**你项目里怎么用的（完整链路，逐段都有代码）**：

| 阶段 | 实现 | 源码位置 |
|---|---|---|
| ① 切分 | 文档切片服务 | `controllers/document_splitter_server.py` |
| ② QA 对抽取 | 知识 QA 抽取与向量化调度 | `controllers/knowledge_server.py` |
| ③ 向量化 | `m3e-base`，**768 维**，L2 归一化 | `controllers/embedding_server.py` |
| ④ 双路存储 | **Milvus** 存向量 + **Elasticsearch 7.17** 存全文 | 架构文档 |
| ⑤ 检索 | `serarch_milvus()`（向量）+ `serarch_es()`（全文） | `tools/KnowledgeTool.py` |
| ⑥ 重排 | `serarch_milvus_rank()` → 调 rerank 服务 → `sort(key=score, reverse=True)` → 取 `topK` | `tools/KnowledgeTool.py` |
| ⑦ 组装 | 拼进 Prompt 交给模型 | `flow/base.py` |

**几个源码里的硬细节（讲出来很显专业）**：

**① 向量归一化**（`embedding_server.py`）：
```python
embedding = model.encode(content, normalize_embeddings=True)
```
L2 归一化 → **余弦相似度等价于内积**，Milvus 检索可以直接用 IP 索引，**检索更快且不需要额外算距离**。

**② QA 对的双 source 设计**（`KnowledgeTool.py`）：
```python
# 1 - QA 向量的是Q需要通过Q查询知识片段A  0 - 文章片段  3 - 索引
if str(Knowledge['source']) == "1":
    qIds.append(Knowledge['qa_id'])   # QA 型：存的是问，命中后回表取答案
else:
    docs.append(Knowledge['content']) # 文档型：直接取片段
```
**向量库里存问题和答案分离** —— 问句向量化，命中后回 MySQL 取答案正文。这是"客服标准问答对"的经典做法，**召回准确率远高于直接把长文档切碎入库**。

**③ 得分语义反直觉，要能解释**（源码注释）：
```python
# 传入的参数与实际的使用相反 0匹配度最高,越靠近1匹配度最低
limi_score = params['score']
```
Milvus 用 IP 距离，越小越相似。所以**阈值方向和直觉相反**，这是踩过坑才会写的注释。

**④ 租户隔离用 filter 表达式**：
```python
expr = "source in [0,1,3]"
```
配合 `f"knowledge_{knowledge_id}"` 的**按库隔离**（每个知识库一个 Milvus collection）——多租户场景下的标准做法。

**⑤ Rerank 模型选型**（`controllers/rank_server.py`）：
```python
model_id = '/opt/model/nlp_rom_passage-ranking_chinese-base'
pipeline_ins = pipeline(task=Tasks.text_ranking, model=model_id, model_revision='v1.1.0')
```
中文检索排序专用模型（ModelScope），**不是通用的 bge-reranker** —— 说明是针对中文客服语料调过的。

**⑥ 召回 → Rerank → TopK 的完整代码**：
```python
postdata = {"question": [content], "docs": docs}
rsp = requests.post(rank_url, postjson, ...)
if rsp.status_code == 200:
    data = json.loads(rsp.text)
    data.sort(key=lambda x: x['score'], reverse=True)
    if len(data) > topK:
        data = data[:topK]
    return data
else:
    return []      # ★ rerank 服务挂了 → 返回空，不阻断主链路
```

**面试怎么答**：
> "RAG 全链路我都做过：文档切分 → QA 对抽取 → 向量化 → 双路召回 → 重排 → 组装。
>
> 三个关键点：
> ① **混合检索**——Milvus 存向量、Elasticsearch 存全文，两路并行。向量强在语义（问'怎么退保'能命中'退保流程'），全文强在精确匹配（保单号规则编号）。我们用 Embedding 的时候做了 **L2 归一化**，这样余弦相似度等价于内积，Milvus 直接用 IP 索引，检索更快。
> ② **QA 对的存法**——我们向量库里把问和答是分开的：向量是问题，命中之后回 MySQL 取答案正文。客服标准问答对用这种方式，召回准确率比把长文档切碎入库高得多。
> ③ **召回和排序分离**——先用便宜的向量/全文召回几十条，再调 rerank 服务做 Cross-Encoder 精排取 Top-K。rerank 模型我们用的是中文检索排序专用模型，不是通用英文的。
>
> 另外有个细节我觉得挺关键：**rerank 服务失败时我们返回空列表而不是抛异常**，不阻断主链路——检索是增强，不是主链路的必要条件。这跟工具失败不中断主链路是同一个原则。"

## 9. 限流

**是什么**：控制单位时间内进入系统的请求数，超了就拒绝或排队。**保护的是下游**——尤其是大模型这种又贵又慢的依赖。

**分三级（你项目里 Redis 承担 session/缓存/限流）**：
- **全局限流**：整个模型网关的 QPS 上限（保护下游 API）
- **租户/用户级限流**：防止一个 BU 的批量任务打满所有人
- **会话级限流**：防止单个 Agent 死循环把配额打满

**你项目里怎么用的**：
- Redis 承担 **session / 缓存 / 限流** 三职（架构文档明确）
- `SimpleCache(ttl=1800)` 做 Token 缓存，**同时也是限流的实现载体**——缓存和限流都靠 Redis 的原子操作（`SETNX` / 计数 + 过期）
- 网关层（Spring Cloud Gateway）做 JWT 鉴权 + 路由 + 负载均衡

**面试怎么答**：
> "限流我们分三级：全局（保护模型网关和下游 API）、租户级（防止单个 BU 的批量任务打满所有人）、会话级（防止单个 Agent 死循环打满配额）。落地靠 Redis——我们 Redis 本来就承担 session 和缓存，限流是同一套基建上的第三个职责，用 Redis 的原子计数加过期实现。
>
> 限流在 Agent 场景和普通业务有一个本质区别：**大模型是又贵又慢的依赖**。普通接口被限流是用户体验问题，模型被限流是直接的成本和可用性问题。所以我们的限流不只是保护下游，本身就是成本治理手段。"

## 10. 分级超时

**是什么**：不是所有调用都用同一个超时值，而是**按重要性分级**——越关键、越容易慢的链路给越宽的预算，越次要的越早放弃。

**为什么分级（关键认知）**：一个 Agent 一次会话可能触发 5-10 次工具调用 + 2-3 次模型调用。如果每次都等满 30 秒，一个卡住的工具就能拖死整条链。**分级的本质是"预算分配"**——把总时间预算切开，每一层用自己那份。

**标准分级（你可以照这个讲）**：
| 层级 | 超时 | 失败处理 |
|---|---|---|
| 连接超时 | 1-2s | 直接失败 |
| 读超时（单次工具调用） | 3-5s | 视为工具失败，回灌失败 Observation |
| 单轮 Agent 总预算 | 10-15s | 中止本轮，输出已有信息 |
| 整体会话上限 | 30-60s | 降级为兜底话术 |
| 轮次上限 | 3-5 轮 | 防死循环 |

**你项目里怎么用的**：
- `DeepSeekLocalGPT` 的 `set_llm()` 里传了 `max_turns`（ReAct 轮次上限，防无限循环）
- 架构文档记录了 **"im-server WebSocket 注释掉的超时配置（response-timeout: 5000）——说明历史上出过 WebSocket 超时问题"** —— 这是真实的稳定性事故痕迹，讲出来很有说服力
- 大模型网关调用有 `max_token` / `max_new_tokens` 限制

**面试怎么答**：
> "超时我们分级，因为一次 Agent 会话可能触发 5-10 次工具调用加 2-3 次模型调用——如果每次都等满 30 秒，一个卡住的工具就能拖死整条链。
> 分级是：连接超时、读超时、单轮 Agent 总预算、整体会话上限，再加一个**轮次上限**（我们本地部署模型那块就配了 `max_turns`），防的是 ReAct 死循环。
>
> 每一级超时的处理不一样：工具超时 → 视为该工具失败，回灌失败信息让模型用已有信息回答；单轮超时 → 中止本轮，输出已有内容；整体超了 → 降级到兜底话术。
>
> 我们踩过 WebSocket 超时的坑——后来在配置里显式设了 response-timeout。**大模型场景的超时设置我认为是稳定性设计的第一道闸门**，比熔断还靠前。"

## 11. 熔断降级

**是什么**：**熔断** = 当某个依赖连续失败达到阈值，就**主动断开**它一段时间（直接快速失败，不再去打）；**降级** = 主路径不可用时切到备用路径。

**为什么要主动熔断（这是很多人答不出的点）**：
> **不熔断的代价更大**。下游已经挂了，你还在一个个请求等它超时——这叫"故障放大"。熔断是**牺牲可用性换稳定性**，让故障快速失败、快速自愈，同时保护自己的线程/连接不被拖垮。

**降级的层次（从轻到重）**：
1. 换备用模型（ChatGLM → DeepSeek）
2. 换降级策略（模型推理 → 规则匹配 → 缓存答案）
3. 只返回必要结果（部分功能可用）
4. 明确告知用户"该能力暂不可用"

**你项目里怎么用的**：
- **多模型工厂 = 天然的降级能力**——主模型类型失败，`set_llm` 里切到另一类实现
- **`forceFlow` 跳过模型**——确定性强、风险低的场景直接走工作流，**模型不可用时系统仍能工作**
- **Rerank 服务失败返回空列表**，不阻断主链路
- **工具异常不中断主链路**

**面试怎么答**：
> "熔断和降级我们是一套设计。熔断解决的是**故障放大**——下游已经不可用了，你还在一个个请求等它超时，这会把自己的连接池和线程也拖垮。熔断就是达到失败阈值就主动断开，快速失败。
> 降级我们有多层：换备用模型；把模型推理降级成规则匹配或缓存答案；再重就只返回部分结果；最后明确告诉用户该能力暂不可用。
> 我们天然有降级基础，因为**模型层是工厂化的**——ChatGLM、DeepSeek、PA-GPT 本来就是多实现，切换是配置问题。另外有个 `forceFlow` 开关，确定性强、风险低的场景**直接跳过模型走工作流**，所以模型整体不可用时系统还能跑。"

## 12. 失败回退

**是什么**：和降级相邻但不同——**降级是"换个方式继续做"，回退是"这一步失败了就退到上一个安全状态"**。

**在 Agent 场景的回退清单**（这是本条的核心，要背熟）：

| 失败点 | 回退动作 |
|---|---|
| 工具超时 | 视为该工具失败，**回灌失败信息**让模型用已有信息回答，不中断整条链 |
| 工具返回格式错误 | **按 schema 校验，校验失败视为工具失败**，脏数据绝不能进模型 |
| 工具调用引发异常 | 捕获，转成合法 Observation 回灌 |
| 检索为空 | 明确说"未检索到相关信息"，不硬编 |
| Rerank 服务挂 | 返回空列表，降级为纯向量召回结果 |
| 模型超时 | 切备用模型；再不行出兜底话术 |
| 写操作执行失败 | 幂等键 + 状态回查，避免半完成状态 |
| 流式中断 | 已输出的内容保留，标记为不完整回答 |

**你项目里怎么用的**：
- `serarch_milvus_rank()` 里 `rsp.status_code != 200 → return []` —— rerank 挂了降级为空结果
- `llm/llmFactory.py` 里工具 Observation 的提取与回灌机制 —— `self._extract_observation(prompt)` 从 Prompt 里抽 Observation
- `tools/config.py` 的 `get_tool_observation(sessionId)` —— **按会话缓存工具 Observation**
- `set_clean_flag` / `get_clean_flag` —— **每轮新请求清理上一轮的工具中间态**，保证一次请求内 history 完整

**面试怎么答（这段是全场高分区）**：
> "失败回退我在 Agent 场景总结了几条铁律：
>
> ① **工具失败不中断主链路**——超时或异常都转成一种合法的 Observation 回灌给模型，让它用已有信息回答或告知用户该能力不可用，而不是抛异常终止会话。
> ② **格式错误的数据绝不能进模型**——工具返回必须按 schema 校验，校验失败就当工具失败。因为脏数据会让模型**编出一个看起来很合理的错误答案**，这比直接报错危险得多。
> ③ **检索类组件失败可以降级为空，但不能伪造**——我们 rerank 服务失败时返回空列表，不阻断主链路；但如果最终没有检索到内容，答案里要明确说没检索到，而不是让模型自由发挥。
> ④ **每轮清干净上一轮的中间态**——我们的实现里有个 clean_flag 机制，新一轮请求会清理上次的工具调用中间过程，保证每次请求的 history 是完整干净的，不然上下文会被污染。
>
> 一句话总结：**辅助能力失败要降级，主链路失败要兜底，绝对不能让脏数据或幻觉进到用户面前。**"

## 13. 异步削峰（Kafka）

**是什么**：把**瞬时高峰**摊平到一段时间内处理。典型场景：晚上 8 点 10 万并发请求，但下游模型每小时只能处理 20 万次——用队列把瞬时流量缓存住，慢慢消化。

**在 Agent 场景的三个典型用途**：
1. **批量任务**：文档向量化、知识入库、批量重算——完全不需要实时
2. **埋点数据**：上报量大、时效性要求低，天然适合异步
3. **长任务解耦**：耗时的 Agent 任务先入队，接口立刻返回任务 ID，前端轮询/WebSocket 推进度

**为什么用消息队列而不是线程池**：
- 线程池：进程重启**任务丢失**
- MQ：消息**持久化**，消费者可以重启、可以多机水平扩展、可以重试

**你项目里怎么用的**：
- 架构文档明确：`ksp-backend` 使用 **Kafka（topic: `kfk-topic`）**，`ksp-kg` 使用 **MQS** —— **不同场景选不同 MQ，不是全场一个**
- Kafka 还被用作**事件总线**：业务事件发布 → 多个下游订阅（通知、统计、数据同步）
- 数据中台项目也有 Kafka（`kafka` 用于异步数据同步）

**面试怎么答**：
> "异步削峰我们用 Kafka，但**不同场景选不同 MQ**——不是全场一个：知识服务和数据同步走 Kafka（topic `kfk-topic`），知识图谱那条链路走 MQS。
>
> Agent 场景我们主要用 Kafka 做三件事：① **批量任务**——文档向量化、知识入库、批量重算，完全不需要实时，入队慢慢消化；② **埋点上报**——量大、时效要求低；③ **长任务解耦**——耗时的 Agent 任务先入队，接口立刻返回任务 ID，前端通过 WebSocket 推进度。
>
> 为什么不用线程池：线程池在进程重启时**任务就丢了**，MQ 的消息是持久化的，消费者可以重启、可以多机扩、可以重试。对我们这种模型调用成本高的场景，**异步还有一个额外价值——把并发压力从"同步等待模型"变成"排队削峰"，峰值时延会稳很多。**"

## 14. 流式输出保首字时延

**是什么**：模型不是一次性返回完整答案，而是**逐 token 生成、逐段推送**。前端边收边渲染/边播报。

**关键指标区分（这是本题的核心，务必讲清）**：
| 指标 | 定义 | 意义 |
|---|---|---|
| **TTFT（首字时延）** | 从请求发出到第一个 token 到达 | **用户感知的"多久开始说话"** |
| **总时长（TPOT 聚合）** | 到完整答案 | 用户感知的"多久说完" |

**为什么车机语音场景 TTFT 是第一指标**：
> 语音交互里，用户**先听到声音**才决定要不要继续听下去。TTFT 3 秒 vs 1 秒，体感是"这车反应好慢" vs "还行"。**总时长反而不敏感，因为用户可以在它说完之前就打断。**

**你项目里怎么用的**：
- `tools/config.py`：
```python
streamer_dict = {}
def set_streamer(sessionId, streamer): streamer_dict[sessionId] = streamer
def get_streamer(sessionId): return streamer_dict.get(sessionId)
```
**按 sessionId 管理输出通道**，一个会话一条流。
- `llm/llmFactory.py` 里推流：
```python
streamer = tools.config.get_streamer(sessionId)
yld_dict = {"sessionId": sessionId, "msgType": "content", "content": resp_result}
streamer._put(json.dumps(yld_dict, ensure_ascii=False))
```
**注意这个设计**：`msgType` 区分消息类型——`content` 是内容，其他类型可以是状态/节点切换。
- `llm/llmFactory.py` 里 `query_qa_stream()` 走**流式接口**（`/chatgpt/dialog/stream`），`chunk_size=102` 逐块读；网关侧提供 `query_qa`（一次性）和 `query_qa_stream`（流式）两个接口
- `flow/base.py` 的 `Selector.conditions()` 里也有 `streamer` 的节点级推送——**工作流每个节点的产出都能实时推**

**面试怎么答**：
> "流式这块我理解**首字时延 TTFT 才是车机语音场景的第一指标**，不是总时长。因为语音交互里用户是先听到声音才决定要不要继续听，TTFT 3 秒和 1 秒体感差别巨大；但总时长反而不敏感，用户可以在它说完之前打断。
>
> 我们的实现是**按 sessionId 管理输出通道**——`tools/config.py` 里维护 `streamer_dict`，一个会话一条流。模型返回后按 `{'sessionId':..., 'msgType':'content', 'content':...}` 的消息体推送，`msgType` 用来区分内容和其他状态消息。工作流那边更进一步，**每个节点的产出都能实时推**，用户能看到'正在检索知识''正在调用工具'。
>
> 网关侧我们提供了两个接口——一次性返回和流式——让上层按场景选。
>
> 顺带说一句，流式还有个隐性价值：**首 token 一到就可以启动 TTS 播报**，把'等模型'和'合成语音'两个耗时串行变并行。这在车载场景是实打实的体验提升。"

## 15. Flask + gevent 协程模型

**是什么**：Flask 是 Python 的同步 WSGI 框架——每个请求占一个线程。而 Agent 请求的**绝大部分时间都在等 I/O**（等模型、等工具、等数据库），CPU 空闲。gevent 用**协程（greenlet）+ monkey patch** 把这些 I/O 等待变成非阻塞，一个线程能同时处理成百上千个请求。

**为什么 Agent 场景特别需要**：
> "Agent 请求的时延不在计算，在等待——等模型推理、等工具 HTTP、等向量库检索。**等待期间线程什么都不干，纯浪费。**"

**你项目里怎么用的**（真实代码，注意细节）：
- `controllers/chatglm_server.py`、`deepseek_server.py`、`flow_server.py`、`pagpt_server.py` 全部 `from gevent.pywsgi import WSGIServer`
- `llm/llmFactory.py` 里 `from gevent.pywsgi import WSGIServer`
- `app.py`：
```python
from gevent.pywsgi import WSGIServer
# from gevent import monkey
# monkey.patch_all()
```
⚠️ **注意这个细节**：`monkey.patch_all()` **在 app.py 里是注释掉的** —— 说明当时 gevent 是在**各个 controller 自己的进程里**启用的（每个模型服务独立进程），而不是全局 patch。这是一个**架构选择**，面试可以讲：
> "我们是**每个模型服务独立进程**，每个进程内用 gevent 的 WSGIServer 起，Python 层不做全局 monkey patch——因为 patch 会影响所有库（包括那些用 C 扩展的），拆进程更可控，也方便按模型分别做资源隔离和扩缩容。"

- `flask` + `Blueprint` 组织 15 个 controller（chatglm / deepseek / pagpt / embedding / knowledge / flow / agent / rank / doc_convert / document_splitter / milvus / classification …），`app.py` 统一注册 Blueprint

**面试怎么答**：
> "Python 侧我们用 **Flask + gevent**。原因是 Agent 请求的时间**不在计算，在等待**——等模型推理、等工具 HTTP、等向量检索，等待期间线程完全空闲。gevent 用协程把这些 I/O 等待变成非阻塞，一个线程能扛更多并发。
>
> 架构上我们是**每个模型服务独立进程**，每个进程内用 gevent 的 WSGIServer 起，**不做全局 monkey patch**——因为全局 patch 会影响所有库（包括 C 扩展的），拆进程更可控，也方便按模型分别做资源隔离和独立扩缩容。
>
> 对比一下：Java 侧我们用 Spring Cloud Gateway + Spring Boot 的线程池模型，微服务之间靠 Feign 调用。**两边是异构的——Java 侧扛业务服务，Python 侧扛 AI 推理，通过 HTTP 网关互通。**"

## 16. LLM 工厂层（多模型热切换 / Token 缓存 / 签名鉴权）

> 多模型工厂与热切换已在第 7 条详述，这里只补 **Token 缓存** 和 **签名鉴权** 两块。

### Token 缓存

**是什么**：调用大模型网关需要先取 `access_token`，而取 token 是一次完整的网络请求 + RSA 签名计算。**token 本身有效期 30 分钟**，所以在有效期内复用，就省掉了每次请求一次签名 + 一次网络往返。

**你项目里怎么用的**（`llm/llmFactory.py`）：
```python
class SimpleCache:
    def __init__(self, ttl=1800):     # 1800秒 = 30分钟
        self.cache = {}
    def set(self, key, value):
        expiry_time = time.time() + self.ttl
        self.cache[key] = (value, expiry_time)
    def get(self, key):
        if key in self.cache:
            value, expiry_time = self.cache[key]
            if time.time() < expiry_time:
                return value
            else:
                del self.cache[key]
        return None
    def cleanup(self): ...   # 主动清理过期项

cache = SimpleCache(ttl=1800)

def query_qa(data):
    token = cache.get("token")
    if token:
        cache.cleanup()
    else:
        token = get_token()
        cache.set("token", token)
```
**设计评价（面试可以主动说，显得有反思）**：
> "这个 SimpleCache 是**进程内内存缓存**——好处是零网络开销，坏处是**多实例下每个实例各持一份**，且实例重启就丢。对我们来说 token 30 分钟过期、重新获取成本不高，这个取舍是划算的。但如果要做得更严谨，会放 Redis 做分布式缓存，或者直接做**带抖动的提前刷新**避免 30 分钟边界上的并发击穿。"

**主动讲改进点比假装完美更赢得信任** —— 这条建议用。

### 签名鉴权

**是什么**：请求网关时，用**私钥对请求时间戳做签名**，网关用公钥验证。核心防的是**篡改**和**重放**。

**你项目里怎么用的**：
```python
def get_sign(rsaPrivateKey, requestTime):
    binary_key = binascii.a2b_hex(rsaPrivateKey)
    private_key = RSA.import_key(binary_key)
    h = SHA256.new(requestTime.encode('utf-8'))
    signer = PKCS1_v1_5.new(private_key)
    return signer.sign(h).hex().upper()
```
配套的请求头：
```python
{
  'X-Auth-Type': 'App_Token',
  'openApiCode': 'API026840',          # 接口编号
  'openApiCredential': 'CRE00000085',  # 凭证编号
  'openApiRequestTime': request_Time,  # 毫秒时间戳
  'openApiSignature': signs,           # 签名
  'appKey': ..., 'appSecret': ...
}
```
**关键设计（必须讲出来）**：
> **`requestTime` 参与签名**——这意味着**签名每次请求都不同**，即使请求体完全一样，攻击者也无法复制一个合法签名去重放。这比"签请求体"更强，因为网关可以校验时间戳新鲜度，直接拒绝超出窗口的请求。

**面试怎么答**：
> "LLM 工厂层除了多模型热切换，还有两个配套机制：
>
> **Token 缓存**——网关的 access_token 要走一次 RSA 签名加网络请求才能拿到，有效期 30 分钟，我们做了 TTL 1800 秒的缓存把它省掉。这个实现是**进程内内存缓存**，好处是零网络开销，坏处是多实例各持一份、重启就丢。对我们来说重新获取成本不高、取舍划算，但更严谨的做法是放 Redis 或者做**带抖动的提前刷新**，避免 30 分钟边界上并发击穿。
>
> **签名鉴权**——用 RSA 私钥对 `openApiRequestTime` 这个毫秒时间戳做 PKCS1v15 + SHA256 签名，网关用公钥验签。这里有个设计要点：**时间戳参与签名，所以签名每次都不一样**，攻击者无法复制一个合法签名去重放；网关还能校验时间戳新鲜度，直接拒掉超出时间窗口的请求。**只签请求体是不够的**，那样重放是可行的。"

# 附：三组"容易混淆"的辨析（面试官爱挖）

| 容易混 | 区别 | 一句话记法 |
|---|---|---|
| **限流 vs 熔断** | 限流是**我主动不让你进**（保护下游）；熔断是**下游挂了我不打了**（防故障放大） | 限流看**流量**，熔断看**失败率** |
| **降级 vs 回退** | 降级是**换条路继续走**；回退是**退回上一个安全状态** | 降级向前走，回退往后退 |
| **Token 预算 vs 上下文窗口** | 上下文窗口是**模型能吃多少**（硬约束）；Token 预算是**你打算给它多少**（工程约束） | 窗口是物理上限，预算是你的策略 |
| **KV Cache vs Token 缓存** | KV Cache 是**模型推理侧的前缀缓存**（GPU 显存）；Token 缓存是**网关 access_token 缓存**（应用层） | 一个在 GPU，一个在应用 |
| **TTFT vs 总时长** | TTFT 到第一个 token；总时长到完整答案 | 语音场景看 TTFT |
