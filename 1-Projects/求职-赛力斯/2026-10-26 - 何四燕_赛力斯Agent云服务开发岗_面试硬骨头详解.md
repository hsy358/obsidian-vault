## 〇、先定调：面试官在这个岗位上真正想验证什么

赛力斯这个 JD 的 7 条职责，翻译成一句话是：

> **"车机上的 Agent 靠云端大脑供能——云端要能扛住车机侧的实时调用、要记住每个用户/车的上下文、要能下发 Tool 和 Skill、要能埋点看效果、要能在弱网下自洽。"**

所以面试官的三大恐惧是：
1. **车机场景比 App 场景更苛刻** —— 时延敏感、网络不稳、端侧算力有限、用户在车上（语音打断、并发指令、注意力窗口短）
2. **上下文是 Agent 的命门** —— 上下文塞爆、记错、丢状态、跨设备不一致
3. **高并发 + 大模型的组合爆炸** —— 一个车厂几万台车在线，每台车都可能同时在对话、导航、空调、娱乐

你的破局点就一句话：**"我在平安云做一个每天被几千坐席使用的 Agent 平台（平安版 Coze），guyu 的架构和这个岗位是同构的，只是我的'端'是 PC 坐席、你的'端'是车机。"**

# 一、【最难】上下文（Context）管理 —— JD 第 5 条 + 第 1 条

> 面试官问法大概率是："座舱 Agent 的上下文怎么管理？端云怎么切？超过 token 怎么办？"

## 1.1 先把"上下文"拆开讲（这是拉开差距的地方）

多数候选人回答"就是 history + prompt"。**你要给出分层模型：**

```
┌─ L0 固定层（编译期确定，缓存友好）
│   System Prompt（人设/角色）+ 工具 Schema 声明
├─ L1 会话态层（单次会话，随 sessionId）
│   最近 N 轮原文对话 + 当前工具调用轨迹
├─ L2 检索层（每轮动态注入）
│   RAG 召回片段 + 场景引擎状态（车机当前状态：车速/档位/温度/导航目的地）
├─ L3 长期记忆层（跨会话，持久）
│   用户偏好、常用目的地、习惯用车设置、历史决策
└─ L4 规则/护栏层（每次必查）
    合规约束、禁答词、未成年人/驾驶分心限制
```

**关键判断：L0/L1/L4 变化慢 → 应该做 KV Cache 命中；L2/L3 每次变 → 放在 prompt 尾部或走独立检索。**

## 1.2 为什么分层就是性能工程（面试加分点）

大模型推理的时延 ≈ `prefill(输入) + decode(输出)`。
- prefill 与输入长度**线性相关**，且**前缀相同可命中 KV Cache**（prefix caching）
- 所以把**稳定内容放最前面、变动内容放最后**，是纯赚的时延优化

> 你的 guyu 真实做法（可引用）：
> `guyu_python/zhishiku/llm/llmFactory.py` → `query_qa()` 里把 **Redis 中的 `AGENT_VARS_DESC&{sessionId}`（变量/画像描述）和 `docs_content&{sessionId}`（会话级知识片段）在调用前拼到 user message 末尾**，
> 也就是 —— **"稳定 system instruction 在前，动态会话变量与知识片段在最后"**。这个结构本身就是 L0/L2 分层的雏形。

## 1.3 Token 预算怎么控（必答，给具体机制）

标准答案骨架：

| 机制 | 做法 |
|---|---|
| **预算分配** | 给 L0/L1/L2/L3/L4 各自设 token 上限，总预算 = 模型窗口 × 安全系数（如 0.7） |
| **滑动窗口裁剪** | L1 保留最近 K 轮；更早的轮次**摘要化**（不是直接丢） |
| **工具轨迹压缩** | 工具返回的原始 JSON 很大 → 只保留关键字段 + 摘要，长内容转存对象存储，只留引用 ID |
| **工具 Schema 裁剪** | 工具从几十个裁到相关的 5-8 个（按场景/意图动态裁）→ 直接减少 L0 长度 |
| **检索 top-k 收敛** | 先召回 50 → Rerank → 取 Top 3-5 进 prompt（宁缺毋滥） |
| **溢出保护** | 超预算时优先级丢弃顺序：低价值检索片段 → 老工具轨迹 → 老对话；**永不丢 L0/L4** |

> guyu 真实做法（很能打）：
> `llmFactory.py` 里历史是**从 MySQL 查**的：
> `SELECT content FROM agent_history_session WHERE session_id=? ORDER BY created_date LIMIT 10`（最近 10 条）
> 且有**摘要记忆**第二路：`SELECT topic,content FROM agent_history_session_total ... LIMIT 10`
> 代码注释写得很清楚：**"history 由两部分组成：数据库历史 + 数据库总结"** —— 这就是"原文 + 摘要"双层记忆，**和上面 L1 摘要化完全同构**。
> 另外 `self.memory == '1'` 是一个开关，控制是否拼入总结记忆 —— 面试官会喜欢这种"**可开关的记忆策略**"设计。

## 1.4 长会话"记忆污染"怎么处理（深水区，答这题显得真做过）

四种手段：

1. **写入门槛**：不是所有对话都进长期记忆。只提取"稳定偏好类"事实（"他习惯坐副驾"、"常用公司地址"），用规则+小模型抽取，置信度阈值入库。
2. **写后校验**：入库前做冲突检测——新记忆与已有记忆矛盾时，不直接覆盖，而是标记候选，由运营/规则确认或做时间衰减。
3. **作用域隔离**：记忆必须带 `tenant / user / vehicle / session` 四级作用域标签，**跨用户绝对不可见**（合规红线，座舱场景是隐私重灾区）。
4. **遗忘机制**：TTL + 访问衰减 + 容量上限淘汰（LRU/LFU），防止记忆无限膨胀导致召回噪声。

> **车机专属加分点**：驾驶场景的注意力窗口短，记忆要"少而准"。可以说：
> **"语音场景下我倾向于让长期记忆偏保守——宁可少记不错记，因为错误记忆会持续污染后续所有对话，而正确记忆收益是边际递减的。"**

## 1.5 面试官可能追问的两个陷阱

**Q：上下文里塞了工具 Schema，模型选错工具怎么办？**
A：三层防御 —— ① Schema 里把 description 写"什么时候用/什么时候不用"（你 guyu 里 `get_tools_prompt` 就是把 name-description-args 拼给模型）；② 场景级裁剪工具集；③ 兜底路由：模型选错时用**意图分类器**兜底（guyu 有 `classification.py` 意图分类 + `forceFlow` 强制走工作流开关）。

**Q：会不会出现 Prompt Injection（车机语音场景尤其危险）？**
A：工具权限分级（只读/可写/敏感操作）；外部内容（导航文本、用户语音转写、第三方 API 返回）一律视为**不可信数据**注入到隔离区；敏感操作（开空调、导航、支付）必须**二次确认**；记录完整 Tool 调用审计日志。

# 二、【最难】端云同步 —— JD 第 5 条 + 端云协同架构（加分项）

> 面试官问法："上下文在端和云之间怎么同步？弱网怎么办？"

## 2.1 先讲职责切分原则（这是判断力的体现）

| 放端侧 | 放云端 |
|---|---|
| 实时感知（语音唤醒、ASR 端侧）、低时延决策 | 大模型推理、复杂 RAG、Tool 服务 |
| 缓存的最近 N 轮对话（离线可用） | 长期记忆、用户画像、知识库 |
| 离线场景的降级能力（车没网 → 本地兜底话术/本地规则） | 编排、调度、版本管理、埋点回流 |

**原则一句话：端侧保"可交互与可降级"，云端保"能力上限与数据沉淀"。**

## 2.2 三种同步策略（讲清楚就赢了）

1. **状态复制（State Replication）**
   上下文是有序增量，云端维护"权威版本 + 版本号"，端侧只带 `lastVersion` 请求增量。
   - 云端返回 `delta + newVersion`
   - 端侧能续传（断网时缓存待发队列）
   - 幂等：以 `sessionId + seq` 去重

2. **事件溯源（Event Sourcing）**
   端侧只发"发生了什么"（用户说了什么、调了哪个 Tool、看到什么结果），云端重放出状态。
   - 优点：可回放、可审计、天然适合埋点归因
   - 代价：实现复杂度高，实时读需快照加速

3. **写本地 + 异步回传（Local-first）**
   端侧本地写（车机断网常态），联网后批量/增量回传云端，云端做幂等合并。
   - 冲突策略：**Last-Write-Wins 不适合车机**（例如"我把空调调到 24 度"vs"系统自动节能到 26 度"，按时间戳覆盖会丢掉语义）→ 应为**语义级合并**（数值取用户显式指令优先，状态取系统最新）

> **可以主动说**：座舱场景要特别区分**"用户显式指令" vs "系统自动策略"**，二者在冲突时优先级不同——这是我从保险/政务场景带来的经验（规则引擎 + 兜底策略的优先级设计），在车上同样成立（用户说"我有点冷" ≠ 用户说"温度调到 24"）。

## 2.3 弱网/断网的降级链（面试官最爱听）

```
网络正常 → 端侧云端协同（完整能力）
    ↓ 弱网（延迟高/丢包）
切本地：优先本地意图（导航/空调/多媒体/电话）+ 本地缓存回答
    ↓ 断网
端侧离线 Agent：本地规则 + 本地小模型/缓存话术 + 车机原生功能直调
    ↓ 恢复
端侧补传事件 → 云端幂等合并 → 记忆回填 → 上下文版本对齐
```

**关键话术**：**"车机 Agent 的可用性底线是'离线也能开空调、导航'——所以端侧必须持有一份可独立工作的能力子集，云端是增强器不是唯一大脑。"**

# 三、【硬骨头】记忆（Memory）体系 —— JD 第 4、5 条

## 3.1 记忆分型（照抄 ChatGPT/Claude 的业界分法，面试最稳）

| 类型 | 生命周期 | 存储 | 例子 |
|---|---|---|---|
| **工作记忆 Working** | 单次请求 | Prompt 内存 | 当前轮工具调用中间态 |
| **情景记忆 Episodic** | 会话/跨会话 | MySQL + 向量库 | "上周他问过某产品" |
| **语义记忆 Semantic** | 长期 | 知识库 + SQL | "他是平安客户，VIP" |
| **程序记忆 Procedural** | 长期 | Prompt/Skill 资产 | 业务规则、操作流程 |

**加分表述**："我们把记忆做成**平台可配的策略**（guyu 里 `memory` 开关 + `agent_history_session` / `agent_history_session_total` 双表），不是硬编码。"

## 3.2 记忆的读写时机（很多人答不上）

- **写**：对话结束 / 达到阈值 / 显式确认（"记住我以后都走高速"）→ 抽取 → 去重 → 冲突检测 → 落库
- **读**：每轮请求组装上下文时 → 按作用域取候选 → 语义相关性过滤（记忆也要 Rerank，别把不相关记忆塞进去）→ 按预算裁剪 → 注入

**踩坑提醒（可以主动讲，显真实）**：guyu 的记忆检索是 `LIMIT 10` 的**最近优先**，不是**相关度优先**。这是早期实现的简化，在座舱场景必须改成"相关度 + 时效 + 重要度"复合排序 —— **主动讲改进点，比假装完美更能赢得信任。**

## 3.3 知识库检索（RAG）在车机场景的适配（JD 加分项 2）

guyu 真实链路（可完整复述）：
```
文档 → 切分(document_splitter_server.py) → QA对抽取 → 向量化(embedding_server.py, m3e-base)
   → Milvus 存向量 + ES 存全文 → 检索(Milvus 向量 + ES 全文) → Rerank(rank_server.py, bge-reranker HTTP 服务)
   → 组装 prompt → LLM → 答案
```
**车机场景的三个改造点（这才是加分）**：
1. **知识要绑定车辆状态域**（当前车型/配置/年份/版本）—— 避免答非所问
2. **Rerank 服务必须本地化/就近**，不能每次跨公网调一次（时延）
3. **召回结果要能"说不知道"** —— 车机错误的语音回答代价远高于文字（驾驶分心）→ 置信度阈值 + 兜底转人工/转本地功能

# 四、Tool 服务与 Skill 提示词 —— JD 第 1 条

## 4.1 Tool 服务的工程化（你有真实代码，超强）

> 引用 guyu `tools/APITool.py`：
> - `HttpApiBaseTool(BaseTool)` —— 继承 LangChain `BaseTool`
> - **`create_dynamic_model(f"DyInput", tool_params_schema)` 动态生成 Pydantic args_schema** —— 工具参数是**配置驱动**的，运营在后台配接口，代码不用改就能新增工具
> - `tool_resp_schema` 声明响应结构 → **工具返回也做结构化裁剪**（不是把整个 JSON 塞回上下文）
> - `convert_pp_json` / `convert_zk_json` 做参数格式归一
> - **`create_http_resp_tools` / `create_flow_resp_tools`：工作流本身也能注册成一个 Tool** → 工具和编排同构

**这一段是全场最值钱的**。你可以直接说：

> "我们的 Tool 层是**配置驱动 + 动态 Schema** 的：运营在后台配一个 HTTP 接口 + 参数说明 + 响应结构，服务动态生成 LangChain 的 Pydantic 参数模型并注册进工具表，Agent 侧不需要改一行代码。Tool 还能调另一个**工作流**——所以『工具』和『编排』在统一抽象下。
> 另外 Tool 返回值也做了结构化，只把必要字段回灌上下文，避免原始 JSON 撑爆 token。"

## 4.2 Tool 调用的稳定性（面试必问）

- **超时**：分级超时（连接/读/总），并有**整体 Agent 轮次上限**（`max_turns`，guyu 里 DeepSeekLocalGPT 传了 `max_turns`）→ 防死循环
- **幂等**：写操作类 Tool（导航下单、设置变更）必须带幂等键（sessionId + actionId）
- **失败回退**：工具异常**不能中断主链路** → 降级为"告知用户该能力暂不可用"或走兜底答案
- **权限分级**：只读 / 可写 / 敏感（开车门、支付）→ 敏感动作强制二次确认
- **灰度与版本**：Tool 定义带版本，灰度按车型/用户/城市维度放量，可回滚

## 4.3 Skill 提示词工程（JD 第 1 条 + 第 7 条）

**别只说"我写 Prompt"，要说成"提示词是版本化的工程资产"：**

| 手段 | 做法（可对应 guyu） |
|---|---|
| **版本化 + 完整性校验** | guyu `Agent/base.py`：`verify_file_integrity()` 校验 prompt 文件 SHA256，**哈希不匹配直接拒绝加载**（防篡改/防错发） |
| **安全反序列化** | `SafeUnpickler` 白名单机制——只允许特定 LangChain Prompt 类反序列化，其他一律 `PickleUnpicklingError` —— 这是**真实的 RCE 防护**，讲出来含金量极高 |
| **Prompt 与工具联动生成** | `get_tools_prompt(prompt, tools)`：工具 Schema 变更时 Prompt 同步重生成，避免两边不一致 |
| **强制路径** | `gen_args['forceFlow'] == True` → 跳过模型直接走确定性工作流（低风险/高确定性场景省时延和钱） |
| **A/B 与效果度量** | 灰度 + 埋点（命中/成功/人工兜底率）驱动迭代 |

> **`forceFlow` 这一条要重点讲**，它同时命中 JD 的"Skill 提示词开发"和"效果优化"——**不是所有问题都该交给模型决策**，能用规则/工作流确定解决的，就不烧 token、也不出错。车机场景尤其如此。

# 五、【硬骨头】高并发调度与稳定性 —— JD 第 2 条

## 5.1 分级模型（把"并发管理"讲成体系，而不是"加机器"）

```
                    ┌─ P0 实时交互（车机语音对话、导航变更）
请求 → 优先级队列 →─┼─ P1 准实时（异步任务、批量向量化、报表）
                    └─ P2 离线/准离线（埋点回流、知识重算、模型微调数据）
```

**分级依据**：SLA 承诺 + 端侧可容忍时延 + 是否可降级。

## 5.2 四个必答机制

| 机制 | 落地方式 |
|---|---|
| **限流** | 令牌桶（单用户/单车/全局三级）；Redis 计数（guyu Redis 就承担 session/缓存/限流） |
| **优先级调度** | 优先级队列 + 老化（Aging，防低优先级饿死）+ 配额（保底配额防单一场景打满） |
| **超时熔断降级** | 依赖调用分级超时 → 熔断（连续失败率阈值）→ 降级（备用模型/缓存答案/规则兜底） |
| **异步化** | 长任务走 Kafka（guyu 里 `ksp-backend` 用 Kafka，topic `kfk-topic`）削峰；流式返回（SSE）给前端，避免请求线程长时间占用 |

> **guyu 真实细节可讲**：
> - Flask + **gevent monkey patch**（`llmFactory.py` 里 `from gevent.pywsgi import WSGIServer`）→ 协程并发扛 IO 等待
> - **流式输出**：模型返回通过 `streamer` 对象推到前端（`tools/config.py` 的 `streamer_dict` 按 sessionId 管理），`msgType: content` 消息体 → 端侧"文字转语音"可以边生成边播，**首字时延**大幅优化
> - Kafka + MQS 双 MQ（`ksp-backend` 用 Kafka，`ksp-kg` 用 MQS）→ 不同场景选不同 MQ
> - Nacos 做配置中心 + 服务发现；Gateway 做 JWT 鉴权 + 限流 + 负载均衡

**首字时延（TTFT）这个概念一定要提**——车机语音场景，用户感知的是"多久开始说话"，不是"多久说完"。能说出这句话，专业度立刻上一个台阶。

## 5.3 稳定性保障（面试官追问"出过事故吗"）

诚实讲一个真坑（guyu 真实）：**Embedding 服务把 `cuda:0` 硬编码**，无 GPU 节点直接崩；LangChain 0.1→0.2 API 变更、Pydantic v1→v2 schema 迁移。
→ 结论话术：**"大模型应用的稳定性，一半的坑不在算法，在环境依赖和版本契约。所以我们把模型调用统一收敛到 LLM 工厂层（llmFactory），做模型热切换、Token 缓存、签名鉴权、参数归一，业务代码不直接依赖任何一家 SDK。"** —— 这段直接对应 guyu 的 `llm/llmFactory.py` 里 ChatGLM / DeepSeek / PA-GPT 多工厂 + `SimpleCache(ttl=1800)` token 缓存 + RSA 签名鉴权。**非常硬。**
