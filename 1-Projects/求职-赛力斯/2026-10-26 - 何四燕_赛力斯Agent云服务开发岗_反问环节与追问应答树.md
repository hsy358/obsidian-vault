# 反问环节：5 个问题 + 追问应答树

> **写于 2026-10-26**
> **原则**：反问不是"提问环节"，是**最后一次表达判断力的机会**。
> 每个问题后面都附了"面试官可能的追问 + 你该怎么接"，避免问完就冷场。

---

## 〇、先记住反问的三条铁律

1. **不问薪资福利**（放到 HR 面），技术面问这个直接掉分
2. **不问"公司文化"这种虚的**，要问**具体的技术现状、痛点、指标**——你的回答要让面试官觉得"这人已经在想象怎么干活了"
3. **必留一个"我已经准备好上手了"的钩子**：问完最后一句要能自然接上"所以这个岗位我很有信心"

---

## 一、5 个反问（按提问顺序 = 按价值顺序）

### Q1【最高价值·边界题】目前座舱 Agent 的端云职责是怎么划分的？

> 端侧跑什么、云端跑什么？哪些能力是端侧必须持有一份的（比如离线也要能用）？

**为什么问这个**：直接命中 JD 第 1、5 条和加分项"端云协同架构设计"，而且面试官会认为你在思考**架构边界**而非只关心写代码。

**面试官可能的追问 + 你怎么接**：

| 追问 | 你的接法 |
|---|---|
| "我们目前端侧主要做感知和低时延，云端做编排和工具，你的看法？" | "方向是对的。补一句：**云端做编排不代表端侧是薄的**——端侧至少要持有一份可独立工作的能力子集，因为车机断网是常态。底线是'离线也能开空调、导航'。我在企业级 Agent 平台上的做法是，端侧做高频确定性请求，云端做复杂推理和跨域数据。" |
| "你觉得端云切分最大的难点在哪？" | "**一致性**。不是切在哪，而是**上下文在端云之间怎么保持版本一致**。我的做法是云端维护权威版本号，端侧带 lastVersion 拉增量，断网时本地队列补传、按 eventId 幂等合并。冲突上不能用 Last-Write-Wins——'用户显式说调温到24度'和'系统自动节能到26度'按时间戳覆盖就丢了语义，得做语义级合并。" |
| "你在座舱场景有经验吗？" | "**行业我没做过，我不装。**但座舱 Agent 的三大难题——上下文端云一致、弱网降级与补传、大模型调用的时延与稳定性——这三块我在平安云 Agent 平台上全踩过。汽车行业的业务知识我需要补，但技术底层是通的。" |

### Q2【规模题】Agent 云端服务目前的量级？

> 日活会话量、峰值 QPS、模型调用量级、日均 Token 消耗大概什么水平？

**为什么问这个**：量级决定技术选型（要不要自己做限流/排队/多模型路由/成本治理）。**同时这是你最需要小心的一题——问的时候要注意措辞，不能显得在评估"你们太小/太大"而显得势利。**

**措辞模板**（照抄）：
> "我想了解一下量级，因为不同量级下，Agent 云端的瓶颈点很不一样——千级会话主要是**功能正确性**，十万级开始**限流与排队**是主要矛盾，到百万级就要考虑**多模型路由和成本分层**。我想知道这个岗位进来后面对的是哪一档。"

**追问应答**：

| 追问 | 你的接法 |
|---|---|
| "我们量级不大，主要是内部精品功能" | "那稳定性压力小，反而**架构的可扩展性和代码质量**更重要——因为量级会涨。我的习惯是**先把分层留好**（工具层/编排层/模型层解耦），量级上来时不用重构。guyu 就是这么做的：工具层配置驱动动态 Schema，模型层多工厂热切换，业务代码不绑任何一家 SDK。" |
| "我们量级很大，峰值几百万" | "那调度就是主战场，我会重点看：**分级队列 + 老化机制 + 单车/单用户/全局三级限流 + 熔断降级 + 首字时延（TTFT）优化**。车机语音场景用户感知的是'多久开口说话'，不是'多久说完'，所以流式输出是刚需而不是加分项。" |
| "模型成本压力很大" | "这个我做过。三个杠杆：**① 路由**（简单意图走小模型/规则，别都上大模型）；② 缓存（我做过 token 缓存和 SimpleCache TTL 缓存，TTL 1800 秒）；③ 减少无效调用——我们有个 `forceFlow` 开关，能用确定性工作流解决的场景**直接跳过模型**，不烧 token 也不出错。" |

### Q3【Tool 体系题】Tool 体系是自研协议还是基于 MCP / Function Calling 标准？

> 现在工具规模到什么量级？Tool 定义、注册、版本管理是怎么做的？

**为什么问这个**：这是 JD 第 1 条的核心，也是你**最强**的地方，主动问等于把舞台让给你。

**追问应答**：

| 追问 | 你的接法 |
|---|---|
| "我们自研的，工具是后台配的" | "那我们的做法应该很接近。我这边的 Tool 层是**配置驱动 + 动态 Schema**：运营在后台配 HTTP 接口 + 参数说明 + 响应结构，服务用 `create_dynamic_model` 动态生成 LangChain 的 Pydantic 参数模型并注册进工具表，**加工具不用改一行代码**。另外 Tool 返回值也做结构化裁剪——只把必要字段回灌上下文，不然原始 JSON 很快撑爆 token。还有一个设计是**工作流本身也能注册成 Tool**，所以工具和编排是同构的。" |
| "基于 MCP" | "MCP 是个好的标准化方向，能解决工具描述和调用协议的一致性问题。我补充一点**协议之外**的工程问题：一是**工具版本与灰度**——工具定义要带版本，能按车型/用户/城市维度放量、可回滚；二是**权限分级**——只读/可写/敏感三级，敏感动作（支付、解锁）必须二次确认；三是**失败回退**——工具异常不能中断主链路。" |
| "工具怎么防止模型选错？" | "三层防御：**① 工具数量按场景动态裁剪**（从几十个裁到相关的 5-8 个）；**② description 写清'什么时候用/什么时候不用'**；**③ 兜底路由**——模型选错时用意图分类器接管，我们有 `forceFlow` 强制走确定性工作流的开关。座舱场景再加一条：敏感工具的参数做白名单校验，防注入。" |

### Q4【痛点题·最高性价比】你们在上下文和记忆上目前最大的痛点是什么？

> 是上下文塞不下、记忆记不准，还是端云不一致？

**为什么问这题**：面试官对"你懂我们"最有共鸣的时刻。而且**他的回答会直接告诉你面试后面会问什么**——如果他说"记忆老记错"，那你 §记忆污染 那套必须提前背熟。

**追问应答**：

| 面试官答 | 你的接法（必须接住这个话头） |
|---|---|
| "记忆老记错，用户说一次记住偏好，下一次又忘了/记混了" | "这个问题本质是**记忆的写入策略和作用域**没做对。我们踩过类似的坑：早期是 `LIMIT 10` 取最近 10 条塞进上下文——**最近优先，不是相关度优先**，用户提过一次的需求隔了几轮就沉下去了。座舱场景我会改成**相关度 + 时效 + 重要度**复合排序，并且写入侧做四件事：写入门槛（只抽稳定偏好类）、冲突检测（矛盾不直接覆盖）、作用域隔离（tenant/user/vehicle/session 四级，跨用户绝不可见）、遗忘机制（TTL + 访问衰减 + 容量淘汰）。" |
| "上下文太长，token 成本高" | "分层 + 预算 + 裁剪三层做。重点是**把稳定的放开头**——大模型 prefill 与输入长度线性相关，但**前缀可命中 KV Cache**，所以 L0（System Prompt + 工具 Schema）稳定不动、动态检索片段放最后，是纯赚的时延优化。然后是三级裁剪：工具集按场景从几十个裁到 5-8 个；召回 50 条先 Rerank 再取 Top 3-5；工具返回只留关键字段、长内容转存对象存储留引用 ID。溢出时丢弃优先级：低价值检索片段 → 老工具轨迹 → 老对话，**永远不丢 System Prompt 和护栏**。" |
| "端云不一致，端侧看到的和云端不一样" | "用**状态复制 + 事件溯源**的组合：云端维护权威版本号，端侧带 lastVersion 拉增量；端侧离线时事件写本地队列，恢复后补传，按 eventId 幂等合并。冲突上**不能用 Last-Write-Wins**——用户显式指令和系统自动策略语义不同，得分层合并。" |
| "我们还没想清楚，想听你的方案" | （**这是最好的情况**，直接给框架，别再问）："我建议分三步走：**先定义上下文分层**（固定/会话/检索/记忆/护栏），**再定每层的存储与生命周期**（Redis 短期态、MySQL 情景、向量库语义、Prompt 资产程序性），**最后做端云契约**（版本号 + 增量 + 幂等键）。落地顺序上先做分层和预算裁剪——见效最快、成本最低；端云一致性放到第二阶段，因为要配合车型节奏。" |

### Q5【指标题·收尾钩子】这个岗位的考核指标更偏业务落地，还是偏平台能力？

> 是看场景上线数、采纳率这类业务指标，还是看 QPS、时延、可用性这类平台指标？

**为什么问这题**：这是**收尾题**，问完必须能自然接上"所以我准备好了"。

**追问应答**：

| 追问 | 你的接法 |
|---|---|
| "偏业务，场景能不能落地、用户用不用" | "那我的重心会放在**场景的确定性交付**上：每个场景有明确的成功判据（完成率、采纳率、主动关闭率），上线后用埋点闭环迭代。我做惠企平台时就是这条路——政策匹配规则 + 审批流自动流转 + 兑现进度可视化，兑现周期从 30 天缩到 7 天，靠的就是每一步都有可观测指标和迭代闭环。" |
| "偏平台能力，稳定性、时延是硬指标" | "那我会把**可观测性和降级**做在前面：全链路 Trace（工具调用轨迹 + Token 消耗 + 检索耗时）、分级超时与熔断、失败回退、KV Cache 命中、流式输出保首字时延。我这边有现成的实践——知识库平台的 Trace、工具异常兜底、Token 缓存都是生产跑过的。" |
| "两个都看" | "那我按**平台保底 + 场景突破**来排优先级：先把稳定性底座打稳（不塌），再选 1-2 个高价值场景做深，把端云协同、上下文治理的完整链路跑通——这样既拿到平台指标，也拿到业务案例。" |

## 三、收尾话术（面试最后 30 秒，说完这句话就收）

> "谢谢，我今天问的这几个问题，其实是想确认这个岗位是**要我做平台工程**，还是**做场景功能**。从刚才聊的来看，端云边界、工具体系、上下文治理这三块正好是我这两年一直在做的——guyu 那套东西换成车机场景，**上下文分层、Tool 动态注册、端云增量同步**这三块是直接能复用的，我需要补的是汽车业务和座舱交互本身。**如果有机会加入，我可以从上下文和 Tool 层这两个底座先切进去，用一个具体场景把链路跑通。**"

## 四、绝对不能问的 8 个问题（踩雷清单）

| ❌ 别问 | 为什么踩雷 |
|---|---|
| "咱们公司加班多吗？" | 技术面问这个 = 不专业 |
| "薪资能给多少？" | HR 面才问，技术面问直接出局 |
| "有没有股票？" | 同上 |
| "公司有多少人？" | 你已经在面试了，问这个显得不关心岗位本身 |
| "能远程办公吗？" | **例外**：base 上海是你真实顾虑，但**技术面不要问**。留到和 HR/招聘沟通时问（或者在 Q1 用"端云职责"把上海/异地问题软化带过） |
| "你们的技术栈是不是很老？" | 显得挑剔 |
| "还有什么是我要准备的吗？" | 把准备责任推给面试官，很业余 |
| "我觉得这个岗位挺重要的" | 空话，浪费一次机会 |

> **特别提醒**：Q1 里问"端云职责"其实能软化你的异地顾虑——面试官回答时你可以说"我目前在南京，如果团队在上海，是否支持周期性出差或混合办公？这一块我需要了解一下"。**在技术面尾声问这个，比在 HR 面问显得更职业。**
