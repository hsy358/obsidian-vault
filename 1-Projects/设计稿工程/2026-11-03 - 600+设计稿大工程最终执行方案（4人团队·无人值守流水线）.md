# 600+ 设计稿大工程：最终执行方案

> **已确认约束**
> - 需求文档：**Nation**（平台待确认，Source 适配器化处理）— 有权限链接

> - 目标：持续跑代码、**准确率高**、**不需要人一直盯着**

## 0. 给何大人的 6 条决断（先看这个）

1. **要不要自建系统？→ 要，但只建"薄编排层"，不造轮子。**
   叫它 **Forge**。它不是 Agent 框架，只做四件事：**Ingest（需求+设计→规范）/ Dispatch（派单）/ Verify（验收门禁）/ Watchdog（看护）**。
   执行器用现成的（OpenClaw / Claude Code / Codex），测试用现成的（Playwright + pixelmatch），状态用 Postgres。
   **范围控制是生死线**：Forge 第一版 ≤ 2 周交付，只做"能自己跑起来 + 门禁会红"。

2. **不要 fork `dsh-superagent`。** 它是 TypeScript + DSH Bundle、且只做"单个 GitHub 仓库的编程 agent"、只认 GitHub/飞书两个 Source。我们要 600 页 + Nation + Figma + 多模块，**借它的领域模型，不抄它的代码**。

3. **Figma 有权限 = 最大的加速杠杆已解锁。** 必须走 **Figma Dev Mode MCP / REST API**，把"从图里猜数值"变成"从变量里读数值"。这一条决定 Token 层是 1 天还是 5 天。

4. **准确性不靠人眼，靠门禁。** 设计稿截图 = 基线；CI 自动 diff，超阈值**卡住合入**。人只做两件事：**裁定设计冲突** + **抽检**。

5. **不需要人一直盯着，但需要人做 3 个决策点**：Token 定稿、组件库定稿、每个分片放量前的首次验收。其余全自动。

6. **用"分片 + 隔离 worktree + Agent 编排"放大 4 人产能**：4 个人 → 4 个并行分片流 → 有效并发 12~16 个 Worker（Agent 跑，人是瓶颈不是 Agent）。

## 1. 核心判断：为什么必须建系统，而不是"人用 AI 写代码"

600 页的规模下，人工在环的四种模式都会崩：

| 模式 | 崩在哪 |
|---|---|
| 人一页页提示 Agent | 人是瓶颈，600 页 × 30 分钟 = 300 人时，且质量随疲劳下降 |
| 人一页页 review Agent 产出 | 同样 600 页 review，且人眼判断"像不像"不可靠 → 变成橡皮章 |
| 只做一次"生成全部页面" | 组件没对齐 → 600 页各自长歪 → 全量返工 |
| **建流水线** | 一次性成本（2~3 周），之后边际成本极低，**质量由门禁保证而非人力保证** |

**判断依据**：本工程有 3 个特征让"建系统"的 ROI 极高 ——
① **重复度极高**（600 页共享 30 个组件）→ 复用收益线性放大；
② **有客观验收标准**（设计稿像素）→ 可以机器判；
③ **输入源已数字化**（Figma + Nation 都有 API）→ 不需要人工录入。

## 2. Forge：系统设计

### 2.1 总体架构

```
┌────────────┐  ┌────────────┐
│  Figma     │  │  Nation    │   ← Source（两个适配器，可换）
│  (MCP/API) │  │  (REST/MCP)│
└─────┬──────┘  └─────┬──────┘
      │  Trigger        │
      ▼                 ▼
┌───────────────────────────────────────────────┐
│  Forge · Ingest                              │
│  Figma → page spec JSON + 设计稿 PNG 基线      │
│  Nation → 需求条目 → 字段/流程/权限            │
│  合成 → spec/pages/*.json + spec/tokens.json │
└───────────────────┬───────────────────────────┘
                    ▼
┌───────────────────────────────────────────────┐
│  Forge · Dispatch（Router：无执行权）           │
│  按模块/布局模板切分片 → 建 Ticket+Mandate     │
│  → 派给 Worker（隔离 worktree + 独立 session）  │
└───────────────────┬───────────────────────────┘
                    ▼
┌───────────────────────────────────────────────┐
│  Forge · Verify（门禁）                        │
│  Playwright 截图 → pixel diff vs 基线           │
│  不过 → 触发修复回合（≤N）→ 不过则升级给人     │
│  build/lint/typecheck/单测 同一门禁            │
└───────────────────┬───────────────────────────┘
                    ▼
┌───────────────────────────────────────────────┐
│  Forge · Watchdog                             │
│  停滞检测 / 成本闸门 / 冲突检测 / 日报          │
└───────────────────────────────────────────────┘
```

### 2.2 领域模型：照搬 Super-agent（这是最值得抄的部分）

| 概念 | 本工程落法 | 为什么 |
|---|---|---|
| **Source** | `figma` / `nation` 两个适配器（可换：以后 Jira、飞书、企微） | Source 抽象化 = 换需求源不动核心 |
| **Trigger** | 一次不可变事件：Figma 某页更新 / Nation 某需求变更 / 视觉 diff 失败 | 幂等 + 可审计 |
| **Thread** | 一个页面的完整上下文：需求条目 + Figma 节点 + 讨论记录 | 一个页面的所有上下文聚合 |
| **Eval** | 评估"这条 Trigger 是否要开工/继续/停"（两层：准入 + 评估） | **判定权交给模型，但准入交给规则** |
| **Mandate** | 授权书：允许改哪些路径、diff 阈值多少、禁止动组件库 | **不可变、可审计**；改了范围 = 新 Ticket |
| **Ticket** | 一份被授权的工作单元 = 一个页面（或一个组件批次） | 状态自定，不跟随 Worker |
| **Assignment** | Ticket ↔ 某次 Worker 执行（可多次、可换执行器） | 支持重试/换模型/人工接管 |
| **Subscription** | Worker 订阅自己那个页面的 Figma 节点 + Nation 条目 + PR | **后续讨论直达 Worker，不过 Router** |
| **Policy** | 版本化的授权规则（谁能派单、允许多高阈值、哪些路径冻结） | 规则变 → 在跑的 Ticket 收到通知 |
| **Channel** | 回写通道：Nation 评论 / Figma 评论 / PR / 飞书 | 结果回原处，人在哪看就在哪看 |

**核心三条**（照抄 Super-agent 的精髓）：
1. **Router 无执行权**：Router 只做"这个 Trigger 该派给谁"，**不写代码、不拆解任务**。
   → 避免"模型觉得这页太小不值得委派"导致的长尾（Super-agent 实测 p95 29.5 → 15.7 分钟）。
2. **事件先代码过滤、后模型判断**：Figma 的无关事件、重复事件在进模型前就滤掉。
   → Router 决策成本实测 6.4s → 1.6s/次，缓存 token 省 23%。
3. **后续讨论绕过 Router**：Worker 订阅自己的 Thread，人在 Nation/Figma 上追加评论 → 直接进 Worker 上下文。

### 2.3 技术选型（默认，可按现有规范覆盖）

| 组件 | 选择 | 理由 |
|---|---|---|
| 编排服务 | **Python 3.12 + FastAPI**（或 TypeScript，看团队） | 4 人团队，架构师定语言；Python 生态做调度/图像对比快 |
| 状态库 | **PostgreSQL 16**（外网托管实例） | 需要事务 + 唯一约束（幂等）+ JSONB（存 spec）+ 全文检索（需求检索） |
| 队列 | **同一 Postgres 的表队列（SKIP LOCKED）** 或 Redis BullMQ | 第一版别引新组件；量大再换 |
| 设计稿抓取 | **Figma REST API + Dev Mode MCP** | 变量/组件/节点树/导出 PNG |
| 需求抓取 | **Nation REST/MCP**（若为 Notion → `@notionhq/client` v5.12 + API `2026-03-11`） | 页面/块/数据库查询 |
| 执行器 | **OpenClaw / Claude Code / Codex**（何大人已有 AgentSpace + AgentRouter） | 现成的；Forge 只调 CLI |
| 视觉验证 | **Playwright（Docker）+ pixelmatch + SSIM** | 自建，**不上 SaaS**（数据在外网但也别把设计稿发第三方） |
| 任务源 | **Postgres 表**（不用 Jira/Linear） | 先少一个系统；架构师要看板就做个只读 UI |
| 通知 | **飞书 / 企业微信机器人** | 架构师和 3 个开发都在飞书的可能性高；退而求其次用邮件 |
| 代码托管 | **GitHub（私有仓）+ worktree 隔离** | Worker 必须在独立分支/worktree |
| CI | **GitHub Actions**（或内网 CI） | 门禁落点 |

> **一条硬规则**：Forge **不自己写代码生成逻辑**。代码由执行器（Claude Code/Codex/OpenClaw）写，Forge 只负责"给什么任务、在哪写、怎么验、不过怎么办"。

### 2.4 数据模型（Postgres DDL 草稿）

```sql
-- Source 与事件
create table source (
  id text primary key,             -- 'figma' | 'nation'
  kind text not null,              -- 适配器实现名
  config jsonb not null,           -- token / project id / 监听范围
  policy_version int not null default 1
);
create table trigger (
  id text primary key,             -- 幂等键：source + 外部 id + 版本
  source_id text references source(id),
  external_id text not null,       -- figma nodeId / nation pageId
  kind text not null,              -- 'figma.frame.updated' | 'nation.page.changed' | 'visual.diff.failed'
  payload jsonb not null,
  created_at timestamptz not null default now(),
  unique (source_id, external_id, kind)
);

-- 线程（一个页面的上下文聚合）
create table thread (
  id text primary key,             -- page id / figma node id
  module text not null,            -- 所属业务模块（分片依据）
  layout_template text,            -- 命中的布局模板
  spec jsonb,                      -- 规范化后的页面规格
  baseline_png text,               -- 设计稿基线图路径
  updated_at timestamptz not null default now()
);

-- 授权与工单
create table policy (
  id text primary key,
  version int not null,
  rules jsonb not null,            -- 允许路径、diff 阈值、冻结路径、token 预算
  created_at timestamptz not null default now()
);
create table mandate (
  id text primary key,
  policy_version int not null,
  scope jsonb not null,            -- 允许改动的路径集合
  strength text not null,          -- explicit | inferred | not_admitted
  basis jsonb not null,            -- 命中的规则 + 发起人身份
  revoked_at timestamptz
);
create table ticket (
  id text primary key,
  thread_id text references thread(id),
  mandate_id text references mandate(id),
  status text not null,            -- open | ended | stopped
  created_at timestamptz not null default now()
);
create table assignment (
  id text primary key,
  ticket_id text references ticket(id),
  executor text not null,          -- 'claude-code' | 'codex' | 'openclaw' | 'human:xxx'
  worktree text not null,          -- 隔离工作目录/分支
  status text not null,            -- pending | running | ended
  attempt int not null default 1,
  started_at timestamptz, ended_at timestamptz
);

-- 订阅（Worker 只看自己该看的）
create table subscription (
  ticket_id text references ticket(id),
  thread_id text references thread(id),
  kind text not null,              -- 'own' | 'context'
  primary key (ticket_id, thread_id, kind)
);

-- 验证结果
create table verification (
  id text primary key,
  ticket_id text references ticket(id),
  attempt int not null,
  kind text not null,              -- 'visual' | 'build' | 'lint' | 'typecheck' | 'test'
  passed boolean not null,
  diff_ratio numeric,              -- 视觉差异比例
  report jsonb,                    -- 差异图路径、失败原因
  created_at timestamptz not null default now()
);

-- 审计（不可变）
create table audit_log (
  id bigserial primary key,
  at timestamptz not null default now(),
  actor text not null,
  action text not null,
  subject text not null,
  detail jsonb
);
```

### 2.5 状态机

```
Thread (页面)
   │ Ingest 生成 spec + 基线图
   ▼
Ticket: open ──(人 stop)──→ stopped
   │  │ Assignment: pending → running → ended
   │  └─ 失败重试：attempt+1（≤3），超限 → 升级人工
   ▼
Verification 循环（每轮）
   ├─ 通过 → Ticket ended → 进下一片
   └─ 失败 → 生成差异图 → 回喂 Worker（≤N 轮）→ 仍不过 → 升级人工 + 记入"设计冲突/缺失"清单
```

## 3. 四个子系统：具体怎么做

### 3.1 Forge · Ingest（需求 + 设计 → 规范化 Spec）

**输入**
- Figma：项目文件 → 页面 Frame 节点树 → 每个 Frame 对应一个"页面"
- Nation：需求条目 → 模块归属、字段、流程、权限、验收标准

**Figma 侧具体动作**（有权限 → 全部自动化）
```bash
# 1) 拉文件结构（Pages → Frames），建立 frame → 页面 的映射
GET /v1/files/{file_key}/nodes?ids=...        # 或 GET /v1/files/{file_key}?depth=2
# 2) 拉设计变量（颜色/字号/间距/圆角/阴影）—— token 的唯一真源
GET /v1/files/{file_key}/variables/local
# 3) 拉组件定义（组件名 + props + 变体）
GET /v1/files/{file_key}/components
# 4) 导出设计稿 PNG 基线（deviceScaleFactor=2，指定 nodeId）
GET /v1/images/{file_key}?ids={nodeId}&format=png&scale=2
# 5) 需要精确间距时，走 Dev Mode MCP（code snippet / layout data）
```
**Figma MCP 的额外价值**（官方说法可直接引用）：
- 能告诉 LLM **"这个红色具体是哪个变量"**（而不是"很多红色 token 之一"）→ 生成代码更准、**更省 token**
- 能直接给出变量在代码里的**确切写法**（code syntax）→ Agent 不用猜 class 名
- 选中 frame 可直接转代码（Code to canvas / Figma Make）→ 作为**参考实现**而非最终产出

> ⚠️ **权限确认**：Dev Mode MCP 需要 **Dev 或 Full seat**（Professional / Organization / Enterprise 计划），桌面版 MCP 需要组织策略允许。**先确认 seat 等级**，否则只能走 REST API 降级方案。

**Nation 侧具体动作**
- 若为 Notion：`@notionhq/client` v5.12 + `notionVersion: "2026-03-11"`；
  `search()` 找数据库 → `databases.query()` 按状态筛 → `blocks.children.list()` 递归取正文 → 映射为 Spec 字段
- **统一成同一个 Spec Schema**（不管 Nation 是什么平台）：

```jsonc
// spec/pages/<pageId>.json
{
  "pageId": "figma-node-123",
  "module": "account-management",
  "title": "用户列表",
  "requirement": { "nationId": "nation-page-9", "text": "...", "acceptance": ["..."] },
  "figma": { "nodeId": "123:456", "baselinePng": "baselines/123-456.png", "frameName": "用户列表/默认" },
  "layout": "list-page",                 // 命中的布局模板
  "components": [ { "figmaComponent": "Button/primary", "states": ["default","hover","disabled"] } ],
  "dataFields": [ { "name": "用户名", "type": "string", "required": true } ],
  "states": ["loading", "empty", "error", "no-permission"],
  "interactions": [ { "trigger": "click", "result": "open-modal" } ],
  "assets": [ { "type": "icon", "figmaNodeId": "789:012" } ]
}
```

**Ingest 还要产出两份"人需要看的东西"**（自动生成，人只审阅）：
1. `design-inventory.md`：页面清单 + 组件清单 + **冲突清单**（同组件不同画法）
2. `spec-conflicts.md`：**需求 ↔ 设计不一致清单**（Nation 说的和 Figma 画的不一样）

> **这两份清单是整个工程最值钱的人力投入方向** —— 人的时间应该花在"消除歧义"上，而不是"逐页写代码"。

### 3.2 Forge · Token 层（把变量变成代码里的唯一真源）

```
Figma Variables ──REST──→ tokens.json ──生成──→ tokens.css (CSS 变量)
                                    ├──→ tailwind @theme 映射
                                    ├──→ DESIGN.md（给 Agent 看的设计契约）
                                    └──→ 回写 Figma（REST PUT variables/code syntax）
```

**执行顺序（不可颠倒）**
1. 拉全部 local variables + components → 生成候选 `tokens.json`（含**使用频次**，高频的必须是语义 token）
2. **架构师裁定一次**：命名语义化（`surface/default` 而非 `gray-100`）、合并同色、标注"哪些是语义层"
3. 生成 `tokens.css` + Tailwind 映射 + `DESIGN.md`
4. **Lint 门禁**：禁止裸 hex / 裸 px 间距（自定义 ESLint 规则 `no-raw-values`）
5. 后续 Figma 侧改 token → **Webhook 触发同步**（REST PUT 回写 code syntax）

**`DESIGN.md` 写法（给 Agent 看的，不是给人看的）** —— 这是让 600 页不走样的关键：
```md
# 设计契约
## 色彩
- 页面底色：bg/page (var(--bg-page))；卡片面：bg/surface；分隔线：border/base
- 禁止使用：任何非语义色；禁止硬编码 rgba(0,0,0,x)
## 间距
- 8pt 栅格；页面左右边距 24；卡片内边距 16/24；表单项间距 16
## 字体
- 标题 20/600；正文 14/400；辅助 12/400；行高 1.5
## 组件使用规则
- 列表页必须用 DataTable 组件，不得自建 <table>
- 空态必须用 <EmptyState>，不得自定义
## 禁止事项
- 不得修改 src/components/** （组件改动走独立 PR）
- 不得引入新的 UI 依赖
```

### 3.3 Forge · Dispatch（分片 + 派单 + 隔离执行）

**分片策略（决定成败）**
- 按**模块**切（不按页面切）：同模块页面共享组件与布局，落同一片 → 减少合并冲突
- 每片 **5~15 页**，且尽量**同布局模板聚拢**（同模板的一次性还原，第二次几乎零成本）
- 每片一个 Ticket 组 = 一个"分片任务"，配一个 `Mandate`（含允许路径）

**Worker 执行协议**
```
1. 在独立 worktree/分支工作：  git worktree add .worktrees/shard-07 -b feat/shard-07
2. 上下文只喂必要的：
   - 该片页面的 spec JSON
   - DESIGN.md（设计契约）
   - 相关组件的 story 与截图（不喂全库）
   - 该片的 Figma 基线图（逐页）
   - 上一轮失败时的 差异图 + 差异清单
3. 明确的作业契约（写进 Assignment）：
   - 只改 src/app/<module>/**
   - 不许改 src/components/**、tokens/**
   - 不许新增 UI 依赖
   - 每页必须通过 pnpm verify:visual --page=<id>
4. 执行器跑 → 产出 PR → Forge 触发 Verify
5. Verify 不过 → 回喂差异 → 同一 Assignment 内重试（attempt+1，≤3）
```

**Worker prompt 模板骨架**（给执行器的标准指令）
```
你负责还原 shard-07 的 8 个页面。规则：
- 只允许修改 src/app/account/**，其他路径只读
- 组件只允许从 src/components/** 导入；发现缺失 → 写 TODO 并继续，不要自造
- 每页完成后运行 pnpm verify:visual --page <id>，必须通过
- 令牌/间距/颜色一律用 tokens 里的语义名，禁止字面量
- 页面用到的每个组件，参考 stories/ 中对应 story 的截图
- 提交信息格式：feat(account): restore <pageName>
[页面的 spec 与基线图见附件]
```

**并行度控制**
- 4 人团队 → 建议**同时开 4 个分片**（每人盯 1 片）
- 每片内 Agent 并行度 ≤ 2（同一 worktree 串行写代码，避免冲突）
- 全局并发 Worker 上限 **8**（外网 API 限流 + 成本）

### 3.4 Forge · Verify（准确性的唯一来源）

**这一层不能省，也不能简化成人眼看图。**

```
① 截图：  Playwright 容器，固定 viewport(1440/375)、deviceScaleFactor=2、
          固定字体、禁动画、等字体与图片加载完成
② 掩码：  mask 动态区域（时间戳/随机头像/图表/动效）—— 否则假阳性淹没真问题
③ 比对：  pixelmatch（精确）+ SSIM/感知哈希（抗噪），双通道都过才算过
④ 分级：  差异分类（颜色/间距/字号/结构），生成差异图（红=缺失 黄=多余 蓝=色差）
⑤ 回喂：  「设计稿 + 我的截图 + 差异图」三图并排 → 视觉模型 → 迭代修改
⑥ 升级：  重试 ≤3 次仍不过 → 挂起该页 + 通知人（附差异图）
```

**门禁必须真的红**（Week 1 的验收标准之一）：故意改坏一个像素，CI 必须挂。
**不要在整页上判**，组件级 + 页面级双层：
- 组件级基线（每组件每状态一张）→ 防"改共享组件全站崩"
- 页面级基线（每页一张 vs Figma）→ 对设计稿保真

**阈值策略**：先松后紧。全页 < 0.5% 起步，组件级 < 0.2%；跑 20 页后按真实噪声调。
（理由：阈值过严 → 大量假阳性 → 团队开始"申请豁免" → 门禁作废。）

### 3.5 Forge · Watchdog（不用人盯的关键）

| 监控项 | 阈值 | 动作 |
|---|---|---|
| **停滞检测** | Worker 同一页 > 20 分钟无新提交/无 diff 变化 | 标记 stalled，通知架构师 |
| **重试超限** | 同页重试 3 次仍不过 | 挂起 + 归类（设计冲突 / 缺组件 / 规格缺失）+ 通知 |
| **成本闸门** | 单页 token 超预算 / 全局日预算 | 暂停新开片 + 告警（防 2056 那种 Token Plan 爆掉） |
| **重复失败聚类** | 同一类 diff 错误在 ≥3 片出现 | 说明是**组件库问题**，不是页面问题 → 升为组件修复任务 |
| **冲突检测** | 两个分片改了同一组件/同一 token | 冻结 + 仲裁（架构师决策） |
| **每日简报** | 每天固定时间 | 已完成页数 / 挂起页 / 失败聚类 / 成本 / 明日计划 → 飞书 |

**日报模板（飞书卡片）**
```
📊 进度：已完成 42/600 页（7%）
✅ 昨日合入：11 页 | ⏳ 进行中：3 片（14 页）
⚠️ 挂起：4 页（设计冲突 2 / 缺组件 1 / 规格缺失 1）
🔁 高频失败：DataTable 列宽对齐（7 页命中）→ 已升级为组件修复
💰 昨日 token：约 X 万 | 预算余量 Y%
```

## 4. 4 人分工（架构师 + 3 开发）

| 角色 | 主责 | 关键交付 |
|---|---|---|
| **架构师**（1 人） | ① 技术选型与仓库骨架 ② Token/组件**定稿裁定** ③ Forge 编排层 ④ 门禁与 CI ⑤ 冲突仲裁 | `tokens.json` 定稿、`DESIGN.md`、组件库定稿、Forge v1、CI 门禁 |
| **开发 A** | 组件库（原子批 + 复合批）+ 视觉回归底座 | 30 个组件（story + zod + 截图基线）、`scripts/visual/**` |
| **开发 B** | Forge · Ingest（Figma + Nation 适配器）+ Spec Schema | `forge/ingest/**`、冲突清单生成器 |
| **开发 C** | 布局模板 + 试点分片 + 作业手册 | 8~15 个布局模板、首批 10~20 页、`PLAYBOOK.md` |

**分工的关键设计**：
- **组件库与页面还原分离**：组件库是"地基"，页面是"流水线"。A 把地基修好之前，页面还原放量会全崩。
- **架构师不写页面**：他的时间在裁定和仲裁。
- **所有人共享同一个 `PLAYBOOK.md`**（作业手册）：每片 Worker 的 SOP 写在里面，人改了它，所有 Agent 立刻跟着改。

**人力的真实投入预估**

| W2（组件+试点） | 50% | 80% | 40% | 60% |
| W3-4（放量） | 60%（仲裁+质检） | 30%（组件维护） | 30% | 70%（盯片） |

## 5. 详细步骤：Week 0 → Week 8

### Week 0（3 天）：**打通一根线**（不要先建系统）

> **原则：先让"一个页面自动跑通"，再谈系统。** 这是 Super-agent「先跑 1 个端到端验证再放量」的直接应用。

| 日 | 动作 | 验收 |
|---|---|---|
| D1 | 拿 Figma 链接 + Nation 链接，建 Spec Schema；手工拉 1 个页面的 Figma 数据 | `spec/pages/<id>.json` 有值；Figma 变量拉下来了 |
| D1 | 拉全部 Figma variables → 生成候选 `tokens.json`（带使用频次） | 架构师看到清单 |
| D2 | **搭视觉回归最小闭环**：Playwright 截图 → pixelmatch → 差异图（红/黄/蓝） | 能对 1 个页面出差异图 |
| D2 | 人肉手写 1 个页面（组件 + 页面），故意写得不完美 | 有 diff 差异 |
| D3 | **验证门禁会红**：CI 里跑 diff，超阈值 → 失败。**并演示能绿** | ✅ 门禁红绿都验证过 |

**Week 0 的红线**：门禁没红过，**不许开始写第二个页面**。

### Week 1（5 天）：组件库 + 视觉回归正式化 + Forge 骨架

| 日 | 动作 | 产出 |
|---|---|---|
| D1 | 架构师：仓库骨架、Monorepo 或单仓结构、ESLint 门禁（禁裸值）、CI 骨架 | 仓库可跑 |
| D2 | 开发 A：视觉回归正式化（mask、SSIM、差异分类、HTML 报告） | `scripts/visual/**` |
| D2 | 开发 A：3 个样板组件（Button / Input / DataTable）+ story + 基线截图 | 样板 + 基线 |
| D3 | 开发 B：Figma 适配器（文件树 → 页面清单 → PNG 导出 → spec） | Ingest 可跑 |
| D3 | 开发 B：Nation 适配器 → 需求条目 → spec 合并 | Ingest 全通 |
| D4 | 架构师：Forge 骨架（Postgres + 表 + Ingest 调度） | `forge/` 目录 + 数据库 |
| D4 | 全体：Token 定稿会（1 小时，把设计方拉上）→ `tokens.json` v1 + `DESIGN.md` v1 | 冻结 Token |
| D5 | 开发 C：8~15 个布局模板（列表/详情/表单/仪表盘/审批/树/报表…） | 模板层 |

### Week 2（5 天）：组件库补齐 + 试点分片

| 日 | 动作 | 产出 |
|---|---|---|
| D1–D3 | 开发 A：补齐剩余 25 个组件（含状态 story + 基线截图）；开发 C 配合做组合组件 | 组件库 ~30 个 |
| D2 | 架构师：Forge Dispatch（Router + Ticket + Mandate + worktree 隔离 + Assignment） | 能派单 |
| D3 | 架构师：Forge Verify 接入 CI（PR 触发 → 截图 → diff → 回写状态） | 门禁自动跑 |
| D4 | 开发 B：Forge Watchdog（停滞/重试/成本/日报） | 飞书日报 |
| D4–D5 | 开发 C：首批试点 10~20 页（1~2 个分片），跑通"派单→写码→diff→修复→合入" | **第一批页面合入** |

**Week 2 验收（关键）**：一条页面从"进入队列"到"合入主干"**全程无人干预**。

### Week 3–4：放量 + 后端契约并行

- 按模块开 4 个分片（每人 1 片），每片 5~15 页
- 后端并行：Nation 需求 → OpenAPI → mock（MSW）→ 前后端解耦
- 每日飞书日报 + 每周 30 分钟复盘会（改 `PLAYBOOK.md`）
- **组件库变更窗口**：每周固定 2 个时段集中合入组件改动，避免污染基线

### Week 5–8：收尾与常态化

- 补齐剩余页面（按模块推进，队列自动续跑）
- 交互与动效补全（设计稿通常没有 → 组件库统一补）
- 联调、权限态、无权限/异常态补齐
- 交付文档（架构说明 + 运行手册 + 复盘）

**产能预估（保守）**：Week 3 起，4 片并行，每片每周 10~15 页 → **每周 40~60 页**，600 页约 **10~15 周**（含后端与联调）。若试点后 diff 一次通过率 > 60%，可再压到 8~10 周。

## 6. 仓库结构（建议）

```
project/
├─ apps/web/                      # 前端
│  ├─ src/app/<module>/           # 页面（Worker 只改这里）
│  ├─ src/components/             # 组件（页面 PR 禁改）
│  ├─ src/tokens/                 # tokens.css
│  ├─ stories/                    # Storybook
│  └─ DESIGN.md
├─ forge/                         # 编排层（架构师主战场）
│  ├─ forge/
│  │  ├─ sources/{figma,nation}/ # Source 适配器
│  │  ├─ domain/                  # Ticket/Mandate/Policy/Assignment 纯领域层
│  │  ├─ dispatch/                # Router
│  │  ├─ verify/                  # 视觉/构建门禁
│  │  ├─ watchdog/
│  │  └─ api/                     # FastAPI
│  ├─ migrations/
│  └─ tests/
├─ spec/                          # Ingest 产物（版本化，可 diff）
│  ├─ pages/*.json
│  ├─ tokens.json
│  ├─ inventories/design-inventory.md
│  └─ conflicts/spec-conflicts.md
├─ baselines/
│  ├─ figma/<nodeId>.png          # 设计稿基线（真源）
│  └─ shots/<pageId>.png          # 实现截图
├─ scripts/visual/                # 截图 + diff + 报告
├─ .github/workflows/verify.yml
└─ PLAYBOOK.md                    # 作业手册（人改，Agent 跟着改）
```

**关键：`spec/` 与 `baselines/` 都进版本库。** 好处：
- 设计稿变更 = spec diff = **能看懂"哪一页的设计变了"**
- 基线图进仓库 = 视觉回归可复现、可回溯
- spec 变更触发 Agent 增量重做对应页面 → **增量迭代，不是全量重来**

## 7. 门禁配置（示意）

```yaml
# .github/workflows/verify.yml
name: verify
on: [pull_request]
jobs:
  visual:
    runs-on: ubuntu-latest
    container: { image: "mcr.microsoft.com/playwright:v1.5x-jammy" }
    services:
      postgres: { image: postgres:16, env: { POSTGRES_PASSWORD: p } }
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: pnpm i --frozen-lockfile
      - run: pnpm build && pnpm typecheck && pnpm lint && pnpm test
      # 视觉：组件级 + 页面级
      - run: pnpm verify:visual:components
      - run: pnpm verify:visual:pages --base=baselines/figma
      # 差异图作为 artifact 上传，便于 Forge 回喂
      - uses: actions/upload-artifact@v4
        if: always()
        with: { name: visual-diffs, path: reports/visual/** }
```

**Forge 侧的行为**：PR 创建 → Forge 读 CI 结果 → 不通过则**把差异图 + 失败清单**喂回该 Ticket 的 Worker → attempt+1。

| # | 风险 | 概率 | 对策 | 谁 |
|---|---|---|---|---|
| 1 | **Figma seat 等级不够**，MCP 不可用 | 中 | 降级到 REST API（拉 variables/nodes/images 仍可）；代码片段靠人工补到 `DESIGN.md` | 开发 B |

| 7 | **Token 成本超预期 / 套餐上限** | 中 | 每页 token 预算 + 全局日闸 + 失败 1 次即通知不重试 + 强模型只用在页面还原 | 架构师 |
| 8 | **并行分支冲突** | 中 | Token/组件冻结期；组件改动走每周固定窗口 | 架构师 |
| 9 | **需求与设计不一致**（Nation 说的 ≠ Figma 画的） | 高 | `spec-conflicts.md` 自动产出；业务口径以 Nation 为准，视觉以 Figma 为准，冲突显式标注 | 产品 + 架构师 |
| 10 | **战线拉太长，2 周建不出系统** | 中 | **Week 0 的红线**：门禁没红过不写第二页；Forge v1 只做 Ingest+Verify，Dispatch 先手工 | 架构师 |

## 10. 一句话给团队

> **这个工程的胜负手不在"谁能更快写出页面"，而在"谁先把验收标准变成机器能判的门禁"。**

## A.2 对主方案的 9 处增量修正（照单执行）

| # | 补丁 | 落点 |
|---|---|---|
| **1** | **门禁三层防失效**：Agent hook（拦截改保护文件 / 带失败项结束）+ git hook + CI，三层必须一致；加 **canary**（每轮故意注入一次违规，确认门禁会红）+ **attestations**（每次通过留证据）+ **parity**（比对本地/CI 工具版本，防漂移） | §3.4、§7 |
| **2** | **只保留一套门禁**：不要"设计一套门禁 + 代码一套门禁"两套并存。**统一为视觉 diff + build/lint/typecheck/test 一条流水线** | §3.4 |
| **3** | **Worker 交接用 10 字段 Packet**（指令 / 块引用 / claim 所有权 / 期望技能 / 执行器及理由 / prompt 路径 / 期望产物 / 提交命令 / 验证命令 / **禁碰文件清单**），而不是一段自然语言 prompt | §3.3 |
| **4** | **停手协议**：worker 遇 spec 缺陷、缺字段、环境缺失 → 输出 `NEEDS_COORDINATOR` 显式停手，**禁止 fallback 到"自己假设一个然后继续"**；缺字段先追问不猜 | §3.3、§3.5 |
| **5** | **进度只认外部可验证信号**：某页"完成"= 截图 diff 通过 + CI 全绿 + Ticket ended。**不允许模型自报进度** | §3.5 |
| **6** | **错误库**：按「场景 / 失败模式 / 根因 / 修复 / 验证」五段记录每次失败，**同时记成功模式**；每周把重复出现 ≥3 次的错误写回 `DESIGN.md` / 组件文档 | §3.5 |
| **7** | **人类注意力限流**：不做 600 页齐飞。**先 1 页端到端 → 三页先行 → 分批放量**；**面板只显示"需人处理"项**；每片评审用 P0/P1/P2 清单，**1-2 轮收敛、3 轮封顶** | §5 |
| **8** | **自审自跑禁止**：dispatcher 不兼任 reviewer；视觉 diff 判定由独立进程/独立模型做，**不喂给写代码的那个 Worker 自评** | §3.4 |
| **9** | **接力式派单**：不并发派满；每个分片完成并回报后再派下一片（跨片依赖时），并为每个 Ticket 设**终止协议**防死循环 | §3.3、§3.5 |

## A.3 「无人值守」三个必须有的兜底（缺一不可）

1. **大声失败（Rule 12）**：任何环节异常 → 立即失败并通知，**不许降级成"跳过这一步继续跑"**。
2. **Token 预算闸（Rule 6）**：Token 预算是硬约束，不是建议；超预算先暂停新开片，再告警。
3. **Watchdog 独立会话**：定时检查每个 Worker 是否**真在推进**（有提交、有 diff 变化），只报"停滞"和"需人处理"，不报流水账。
