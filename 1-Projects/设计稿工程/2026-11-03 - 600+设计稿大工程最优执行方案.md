# 600+ 设计稿大工程：最优执行方案

> 背景：何大人已有**需求文档 + 600 多张设计稿**，目标是把整个大工程的代码做出来，且要**快、准**。
> 本文给出一套可直接开工的流水线。**第 9 节的 6 个答案会决定细化版本**，但第 1 步（Token 层 + 视觉回归底座）无论答案如何都要先做。

---

## 0. 一句话结论

> **不要逐页手工还原。要做的是：先把 600 张稿子压缩成「一套 Token + 30 个组件 + N 种布局模板」，再用「视觉回归闭环」批量生成页面。**
> 速度来自**并行分片 + 复用**；准确性来自**像素级 diff 门禁**，不靠人眼。

这是过去两年"设计稿还原"从"体力活"变成"工程活"的分水岭：**Design Token 先行 + 组件级视觉基线 + CI 门禁**。

---

## 1. 先看清问题的真实形状

600+ 张设计稿 ≠ 600 个页面。真实结构通常是：

| 层 | 真实数量级 | 举例 |
|---|---|---|
| **Token**（颜色/字号/间距/圆角/阴影/层级） | 40 ~ 120 个变量 | `#2B5AED`、`14px`、`8px 栅格`、`radius-md` |
| **原子组件** | 15 ~ 30 | Button / Input / Select / Table / Modal / Tag / Avatar |
| **复合组件** | 10 ~ 25 | FormItem / DataTable / SearchBar / PageHeader / DetailField |
| **布局模板**（页面骨架） | 8 ~ 15 | 列表页 / 详情页 / 表单页 / 仪表盘 / 树形页 / 审批流页 |
| **页面实例** | 200 ~ 600 | 上述模板 × 数据 × 状态（空/加载/无权限/异常） |

**这个结构决定了三件事：**

1. **工作量不在页面数量，在组件数量。** 30 个组件做扎实，600 个页面是流水线活；组件没做扎实，600 个页面是 600 份返工。
2. **必须先抽 Token。** 不抽 Token 直接做页面 = 每页各自发明颜色/间距 = 后期统一改样式要动 600 个文件。**这是最大的返工来源。**
3. **状态设计稿通常不全。** 空态、加载态、错误态、权限态通常缺失（或者散落），必须由组件库统一补齐——这也要人审一次。

## 2. 核心架构：三层流水线 + 一个闭环

```
┌─────────────────────────────────────────────────────────────┐
│  L0  设计规格层（一次性，人审一次）                            │
│  design-tokens.json / tokens.css / 图标 SVG 资源库 / 字体     │
└───────────────┬─────────────────────────────────────────────┘
                ↓ 唯一真源
┌─────────────────────────────────────────────────────────────┐
│  L1  组件层（30 个左右，每个配视觉基线）                      │
│  src/components/**  +  Storybook story  +  截图基线           │
└───────────────┬─────────────────────────────────────────────┘
                ↓ 组合
┌─────────────────────────────────────────────────────────────┐
│  L2  页面层（批量并行生成）                                    │
│  src/app/**  按页面分片，独立分支                              │
└───────────────┬─────────────────────────────────────────────┘
                ↓
┌─────────────────────────────────────────────────────────────┐
│  ✅ 视觉回归闭环（准确性的唯一保障）                            │
│  Playwright 截图 → pixel diff vs 设计稿基线 → 差异图回喂 VLM   │
│  → 自动修复 → 迭代到阈值 → CI 门禁                             │
└─────────────────────────────────────────────────────────────┘
```

**关键设计：设计稿本身要变成"基线"**。设计稿截图作为基准图存进仓库，页面实现截图作为待测图，diff 不通过就卡住合入。没有这一步，"更准确"只是口号。

## 3. 六个阶段（可直接排期）

### Phase 0 · 素材归一与体检（0.5 ~ 1 天）

**做什么**
- 把 600+ 张稿分类：按模块 → 按页面 → 按状态（列表/详情/表单/弹窗…）
- 判定每张稿是**整页图**还是**组件图**（决定它进 L1 还是 L2）
- 若有 Figma 源文件/权限：走 **Figma MCP / Dev Mode API** 直接拉变量、组件属性、间距数值（**这是最大的加速器**，能把"反推 token"变成"读取 token"）
- 若只有图片：用 VLM 批量提取数值 → 生成"候选 token 表" → **人工裁定一次**

**产出**：`docs/design-inventory.md`（页面清单 + 组件清单 + 冲突清单）
**门禁**：所有 600 张都有归属，不允许"孤儿稿"

⚠️ **冲突清单**是这个阶段最有价值的产出：同一按钮在第 37 张和第 212 张画法不同 → 立刻列出来让设计师裁一次。**不裁，后面 600 页会各自长歪。**

---

### Phase 1 · Design Token 层（1 ~ 2 天）｜**最高杠杆的一步**

**做什么**
```
tokens/
  color.json     # 语义色（不是原始色）：bg/page、bg/surface、text/primary、
                 # text/secondary、border/base、action/primary、status/success...
  typography.json
  spacing.json   # 8pt 栅格
  radius.json / shadow.json / motion.json / zIndex.json
```
- 语义色而非原始色 → 换主题时只改一层
- 同步产出：`tokens.css`（CSS 变量）+ Tailwind v4 `@theme` 映射 + **Figma Variables 双向同步**（设计侧改，代码侧跟着改）
- **同时产出 AI 可读的 `DESIGN.md`**（给 Agent 看的设计契约：颜色怎么用、间距规则、组件组合约定、禁止事项）

**为什么要 `DESIGN.md`**：Claude Code / Codex / OpenClaw 这类 Agent 读代码比读人话快。`DESIGN.md` 是**给 Agent 的设计规范**，把"设计系统的隐性知识"显性化成 Agent 一次就能吃进去的契约。这正是 vault 里《Open Design》一文讲的 `DESIGN.md = 团队品牌契约` 的用法。

**产出**：`tokens/` + `DESIGN.md` + `tokens.css`
**门禁**：任何页面代码里出现**裸 hex 值 / 裸 px 间距** → lint 报错（用 ESLint 自定义规则或 `stylelint` + `no-raw-values`）

---

### Phase 2 · 组件库（3 ~ 5 天）｜**质量的真正所在**

**做什么**
- 30 个左右组件，分两批：**原子批**（Button/Input/Select/Tag/Table/Modal/Drawer/DatePicker…）→ **复合批**（SearchBar/PageHeader/FormItem/DataTable/DetailPanel/PermissionWrapper/EmptyState/LoadingState…）
- 每个组件：
  - `props` 用 **zod schema 定义**（不只是 TS 类型）→ 既是运行时校验，也是**给 AI 看的契约**
  - 每个状态一个 **Storybook story**：default / hover / focus / disabled / loading / error / empty
  - 每个状态一张 **视觉基线截图**（`__screenshots__/`）
- 数据交互层：`MSW` / mock server + OpenAPI 契约先行

**这里直接抄两篇 vault 文章的结论：**
- **《Loop Engineering》**：交付前必须有一轮**批判性评审**（生成 → 挑毛病 → 重写）。组件层尤其要：让另一个角色/另一次会话评审每个组件，而不是"生成完就算"。
- **《Claude Code 的 Harness 架构》**：组件规范要写成**可被 Agent 检索的结构化文档**（编号文档、渐进式概念引入），不是一篇大而全的说明书。

**产出**：`src/components/**` + `stories/**` + 每组件截图基线
**门禁**：组件有 story、有截图基线、有 zod schema —— 三缺一不算完成

---

### Phase 3 · 视觉回归底座（1 ~ 2 天，与 Phase 2 并行）｜**准确性的地基**

**做什么**
```
scripts/
  visual/
    capture.ts     # Playwright 截图：固定 viewport、deviceScaleFactor=2、固定字体、
                   #   disable animations、等待字体与图片加载完成
    diff.ts        # pixelmatch + 感知哈希双通道
    triage.ts      # 按区域/类型分类差异，输出差异图（红/黄叠加到设计稿上）
    report.ts      # 生成 HTML 报告 + 失败用例的差异图
```
**四个必须做对的细节（决定成败）**：
1. **像素 diff 必须先做 mask**：动态区域（时间戳、随机头像、动画、图表数据）必须遮罩，否则全是假阳性 → 团队会开始无视红灯 → 门禁作废
2. **按组件级截图，不只按整页**：整页截图差异一大片，无法定位；组件级（每组件每状态）是"能落地到具体代码行"的粒度
3. **同时做像素 diff + 结构 diff**：像素给精确度，结构（SSIM/感知哈希）抗噪，两者都过才算过
4. **基线图必须由设计稿生成**，不是"第一次实现截的图"——否则就变成"实现 vs 实现"，等于没测

**产出**：`scripts/visual/**` + `tests/visual/**` + CI job
**门禁**：这个 CI job 必须**真的卡合入**（不是"提醒"）

---

### Phase 4 · 页面批量还原（并行，主体工作量）

**分片策略**（决定速度）：
- 按**模块**切（不是按页面切）—— 同模块页面共享组件与布局，分片时保证同模块尽量落同一片，减少合并冲突
- 每片 5 ~ 15 个页面，一个片一个独立分支/工作目录
- 一个片 = 一个 **Assignment**（对照 Super-agent 的概念）

**每页的标准作业流程（SOP）**：
```
1. 读：页面 PRD 片段 + DESIGN.md + 相关组件的 story（不看全库，只看需要的）
2. 排：先定"这个页面属于哪个布局模板"，复用模板 → 填内容
3. 写：只写页面组装代码，不新造组件（发现缺组件 → 提 Issue，不许就地造）
4. 跑：本地 dev server → Playwright 截图 → diff
5. 修：把「设计稿 + 我的截图 + 差异图」三张图一起喂回视觉模型，让它**看着差异图改**
6. 判：diff 阈值达标 + 类型/lint/构建通过 → 提交 PR
7. 记：在 Ticket 上记录"这个页面用到了哪个模板、哪些组件"
```

**第 5 步是"更准确"的关键**：不要让模型"凭记忆再写一遍"，要让它**看着差异图改**。视觉模型对静态可测量属性（间距、层级、密度、对比、对齐）判断强，但对交互态/动效/帧外内容无能为力——所以差异修复要**只让它管静态像素**。

**关键约束**：**截图要给组件级裁剪图，不要只给 1080p 整页**。整页图上小字在标准档模型上已经"降质"，裁到组件能保住小字准确率。

**产出**：`src/app/**` + 每页一个 PR
**门禁**：本片所有页面 diff 达标 + build/lint/typecheck/vitest 全绿 + **组件库零改动**（组件改动必须走独立 PR，否则基线会被污染）

---

### Phase 5 · 联调与交付（需求文档 → 后端契约）

需求文档在这条线上的用法：
- **抽实体与字段** → 数据模型
- **抽业务流程与状态机** → 页面状态逻辑（列表页的筛选、分页、批量操作怎么走）
- **抽角色与权限** → `PermissionWrapper` 组件 + 无权限态
- **抽接口清单** → OpenAPI → 前后端并行

**建议：前后端并行**，用 OpenAPI + mock server 解耦。后端还没好不影响前端还原进度。

## 4. 技术选型建议（默认值，可按现有规范覆盖）

| 层 | 建议 | 理由 |
|---|---|---|
| 框架 | **React 19 + TypeScript**（或 Vue 3，若团队/规范要求） | 生态与 Agent 熟悉度最高 |
| 构建 | **Vite** | 快，Agent 改配置少踩坑 |
| 样式 | **Tailwind CSS v4 + CSS 变量** | token 与 class 一一对应，Agent 改样式成本最低；`@theme` 直接映射 tokens.json |
| 组件底座 | **shadcn/ui**（源码进仓库，可改） | 关键：**不要用 npm 包的成品组件库**（改不动、Agent 改不了、token 融不进去） |
| 契约 | **zod** 定义组件 props + 接口 | 运行时校验 + AI 可读的契约 |
| 组件文档 | **Storybook**（Vite 版，轻） | 每个状态一个 story + 截图基线同源 |
| 视觉回归 | **Playwright + pixelmatch**（自建，不上 SaaS） | 政务/金融客户数据不出内网，合规 |
| Mock | **MSW** | 接口未就绪不阻塞前端 |
| 状态 | Zustand / TanStack Query（按需） | 别过度设计 |
| CI | GitHub Actions（或内网 GitLab CI） | 门禁落点 |

> **一条硬规则**：**组件库必须源码进仓库**（shadcn 方式），不允许依赖不可改的二进制组件包。这是 Agent 能不能改得动的分水岭。

## 5. Agent 编排：把 Super-agent 的架构用上

前一笔记已分析 DeepSeek Super-agent（见 `2026-11-03 - DeepSeek Super-agent - 设计分析与德勤借鉴点.md`）。这个工程正好是它的**教科书级用例**：

| Super-agent 机制 | 在本工程的落法 |
|---|---|
| **Router 无执行权** | 一个 Dispatcher 只做"页面分片 → 派给哪个 Worker"，**不写代码、不拆解任务**。避免模型自己判断"这页太小不用委派" |
| **隔离 session + 隔离目录/分支** | 每个分片一个 Worker，一个 git 分支，互不干扰 |
| **事件驱动 + 先代码过滤** | 视觉 diff 失败 = Trigger → 直接喂给对应 Worker 修，**不经过 Router** |
| **Subscription 订阅** | Worker 订阅自己那几页的 PR/截图/报告，后续讨论直达它 |
| **Watchdog 停滞检测** | 独立会话定时检查每个 Worker 是否真在推进（防"假活"） |
| **Ticket / Mandate / Policy** | 每个页面一个 Ticket；Mandate = 「只改 `src/app/xxx`，不许改组件库，diff 阈值 0.02」——**授权范围写进契约** |
| **Observe 模式** | 前期先让 Worker **只记录**"我本来会怎么改"，人工核对后再放开 |
| **"不要用它来制造产量"** | **明确禁止**：批量生成相似页面而不做 diff 验证。产能不来自"生成得快"，来自"返工少" |

**Loop Engineering 的循环嵌入**（vault《Loop Engineering 20 种设计模式》）：
- **质量改进循环**：生成 → 批判性评审 → 重写 → 再评审（组件层用）
- **收敛循环**：diff → 修 → 再 diff（页面层用，**硬门禁**）
- **护栏循环**：lint/typecheck/build 每次迭代都跑（每次都跑代价大 → 分级：每轮跑快的，合并前跑全的）
- **知识沉淀循环**：每个页面的踩坑写回 `DESIGN.md` / 组件文档 —— 后面 600 页越来越准

**执行器选型**（何大人已有基础设施）：
- 主执行器：**OpenClaw / Claude Code / Codex** 任一（何大人机器上 `AgentSpace` + `AgentRouter` 已通）
- 视觉审查：**VLM**（可用 `image` 工具/多模态模型）负责"看差异图改"
- 编排：**Super-agent 式 Router/Worker**（先手工编排 3~5 个 Worker 验证，再自动化）
- ⚠️ **先跑 1 个页面做端到端验证**（1 周内出可点击页面 + 一条真会卡合入的 diff 门禁），再放量。**不要一开始就 600 页齐飞。**

## 6. 准确性工程：三个硬手段 + 一条铁律

| 手段 | 做什么 | 防住什么 |
|---|---|---|
| **① 像素级 diff 门禁** | 设计稿 = 基线，CI 自动比对，超阈值卡合入 | "看起来差不多"的敷衍实现 |
| **② 组件级隔离截图** | 每组件每状态一张基线图 | 共享组件改动引发的**级联回归**（改了按钮，全站 600 页挂掉且功能测试全绿） |
| **③ 差异图回喂自评** | 设计稿 + 截图 + 差异图三图并排喂 VLM 迭代修 | "再写一遍"的幻觉式修复 |

**铁律**：**组件库基线不可被页面级 PR 污染**。页面 PR 改组件 → 该 PR 必须回滚组件改动、另开组件 PR、重跑全部基线。否则基线失真，门禁变成摆设。

**阈值建议**：像素 diff 比例 < 0.1%（全页）/ < 0.05%（组件级）起步，先跑 20 个页面量真实噪声水平再调。**宁可先松后紧**，一上来就 0 会让团队直接绕过。

## 7. 速度工程：三招 + token 预算

1. **Token 先行**（省下最大的返工）
2. **组件库一次做对**（30 个组件 = 600 页的地基）
3. **分片并行 + 隔离分支**（Router/Worker，见第 5 节）

**模型分级（省 token 又保质量）**：
| 任务 | 用什么 |
|---|---|
| Token/组件的数值提取、批量格式化、脚本生成 | 便宜快模型 |
| **页面还原、差异修复** | **最强视觉模型**（这部分质量决定成败，不能省） |
| 评审、总结、文档 | 中档 |

**成本闸门**：每片设 token 预算上限；Watchdog 检测"同一页反复修 >N 轮仍不达标" → 停下来叫人（这正是 Super-agent 的"按影响停手，不按努力停手"）。

## 8. 风险清单与对策

| # | 风险 | 对策 |
|---|---|---|
| 1 | **设计稿本身不一致**（同组件多版本） | Phase 0 出**冲突清单**，人工裁定一次；不裁定不进入 Phase 1 |
| 2 | 图标/插画资源缺失或被 AI 手绘 | **强制 Figma 导出 SVG 资源库**；禁止 agent 手绘图标 |
| 3 | 状态稿缺失（空/错/无权限/加载） | 组件库统一补齐 + 人工确认语义；页面只允许组合，不许自定义状态 |
| 4 | 视觉回归假阳性太多 → 团队无视 | 动态区域 mask + 组件级粒度 + 阈值先松后紧；报告要能直接定位到代码行 |
| 5 | 需求文档与设计稿对不上 | Phase 0 一并做**需求-页面映射表**，冲突标出交给产品裁定 |
| 6 | 接口未定 → 前端空转 | OpenAPI 契约先行 + MSW mock，契约变了前端改 mock 即可 |
| 7 | 并行分支互相冲突（改同组件/同 token） | **组件库与 Token 冻结**：并行期只读；确需变更走"组件 PR"通道，串行合并 |
| 8 | Agent 批量产出低质页面 | 门禁 + "不要用它来制造产量" + 质量抽检（每片抽 10% 人工看） |
| 9 | 字体/资源加载导致截图不稳定 | CI 容器内**预装并锁定字体**，禁用动画，固定网络字体 |
| 10 | Token 消耗超预算（见 MEMORY 里 MiniMax 2056 教训） | 分级模型 + 每片预算上限 + 失败 1 次即通知不重试 |

## 9. 需要何大人确认的 6 个问题（决定方案细化）

1. **设计稿是 Figma 源文件还是图片？** 有 Figma 权限/Token 吗？→ 决定能否自动化抽 Token（**最大的加速杠杆**）
2. **技术栈是否已被指定？** 前端框架、后端语言、数据库、既有规范（是否已有项目要接着做）
3. **需求文档的形式与范围？** PRD/表格/原型图？覆盖哪些模块？和 600 张稿的映射关系
4. **交付形态**：纯前端？还是含后端 + 联调 + 部署？是否需要部署到客户内网
5. **周期与人力**：期望多久交付？几个人可用？（决定分片数与并行度）
6. **合规约束**：数据能否出内网？视觉回归是否必须自建（我默认自建）？是否有等保/信创要求

> 收到这 6 个答案后，我可以把本文细化为：**具体仓库结构 + 完整文件清单 + 分片排期表 + 每阶段验收标准 + CI 配置草案**。
