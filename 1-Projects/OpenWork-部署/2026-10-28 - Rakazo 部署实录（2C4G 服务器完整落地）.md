## 二、踩过的坑（都是真坑）

### 坑 1：GHCR 在国内被限速到 ~16 KB/s ⭐⭐⭐

**现象**：`docker pull ghcr.io/elie222/rakazo/app:edge` 反复 TLS handshake timeout，39 层里卡在 29 层不动。

**根因实测**：
```
GitHub CDN (pkg-containers.githubusercontent.com) 实测速度：16 KB/s
最大层 761 MB → 按此速度需 13 小时
```
- DNS 解析到 **IPv6**（`2606:50c0:8003::154`），但本机**无 IPv6 出口**（`ping6: Network is unreachable`）→ 加 `-4` 也无改善，问题在限速不在 IPv6
- 断点续传（`curl -C -`）能累积但**每轮只有几百 KB**
- 腾讯云 registry-mirror（`mirror.ccs.tencentyun.com`）**不代理 ghcr.io**（403）
- `docker.m.daocloud.io` / `ghcr.nju.edu.cn` / `dockerproxy.net` / `ghcr.1ms.run` / `ghcr.m.daocloud.io` **全部不可用**
- Docker Hub 上**没有** elie222/rakazo 镜像

**✅ 唯一可用的解法**：
```
ghcr.chenby.cn/elie222/rakazo/app:edge     ← 可用
ghcr.chenby.cn/elie222/rakazo/computer:edge ← 可用
```
拉完后回写官方 tag（compose 里引用的就是官方名）：
```bash
docker tag ghcr.chenby.cn/elie222/rakazo/app:edge      ghcr.io/elie222/rakazo/app:edge
docker tag ghcr.chenby.cn/elie222/rakazo/computer:edge ghcr.io/elie222/rakazo/computer:edge
```

### 坑 2：改了 `/etc/docker/daemon.json` 直接把 Docker 搞挂 ⭐⭐⭐

**现象**：加了 `"http-timeout": 600` → dockerd 启动失败 → `Start request repeated too quickly` → **三个生产容器全挂**。

**根因**：**`http-timeout` 不是 dockerd 的合法配置项**，daemon 直接拒绝启动。

**教训**：
1. 改 daemon.json 前**必须** `cp` 备份（`/etc/docker/daemon.json.bak.<ts>`）
2. 改完先 `dockerd --validate --config-file=...` 或 `systemctl restart` 后**立刻** `systemctl status` 检查
3. 失败时用 `journalctl -u docker -n 25` 看原因（报错很直白）
4. 修复：`systemctl reset-failed docker` 再启动
5. **更稳的做法**：不要动 daemon.json，Docker 拉取重试本来就支持逐层续传

### 坑 3：`DB_POOL_MAX=5` 让 worker 无限重启 ⭐⭐

**现象**：worker 反复 Restarting，日志：
```
Error: DB_POOL_MAX must be at least 6 for the Graphile worker
```
**修复**：`DB_POOL_MAX=6`（官方硬性下限）。

### 坑 4：nginx 路由写错，API 全 404 ⭐⭐

**真相**：Rakazo 的 oRPC **不在 `/api/` 下**，而是：
- `/rpc/<namespace>/<procedure>` —— oRPC 用**斜杠**分隔（不是点）
- `/api/auth/*` —— Better Auth 认证
- `/api/v1/bots/*` —— webhook

**正确写法**：
```nginx
location ~ ^/(rpc|api)/ {
    proxy_pass http://127.0.0.1:3100;
    proxy_buffering off;   # SSE 流式响应
}
```
**踩坑细节**：我最初试了 `/rpc/bots.list`（点分隔）→ 404；试了 `?input={json}` GET → 也 404；**正确是 `/rpc/bots/list`** + POST + `{"json":{}}`。

### 坑 5：5173 端口被占 ⭐

`/etc/nginx/nginx.conf` 内嵌了 yuanzhi 前端的 server 块（`listen 5173`，且文件是二进制编码，grep 需 `tr -d '\000'`）。Rakazo 改用 `RAKAZO_WEB_PORT=5180`。

**⚠️ 前端 bundle 里写死了 `http://127.0.0.1:5173/rpc`**（仅桌面端模式用，浏览器端用 `window.location.origin`，所以改端口不影响 Web）。

### 坑 6：`git reset --hard` 覆盖本地新版本（vault 同步时踩的）

用 GitHub Contents API 兜底推送后，执行 `git reset --hard origin/master` **把本地新版覆盖回远端旧版**（因为远端那个 commit 不在本地 git 历史里）。
**正确做法**：API 兜底后**不要 hard reset**，用 `git reset --soft`；需要恢复就从远端 API 拉回内容再提交。

```bash
SANDBOX_MAX_COMPUTERS_PER_USER=1
RAKAZO_COMPUTER_MEMORY=900m
RAKAZO_COMPUTER_CPUS=1

SANDBOX_COMMAND_TIMEOUT_MS=120000

# 安全
SIGNUPS_ENABLED=false    # 部署后立刻关闭公开注册
```

| 服务 | mem_limit | pids_limit |

| api | 1536m | 256 |

## 六、结论：2C4G 能不能跑 Rakazo？

**能跑，但要按「精简模式」部署。**

| 维度 | 结论 |
|---|---|
| **最小可用配置** | 2C4G + 无沙箱（纯对话/例程调度），稳态 ~500MB |
| **本机实测** | 2C4G + **带 docker 沙箱**（1 个 screen，900m 限额）→ ✅ 可跑，可用内存 ~780MB |
| **硬上限** | 同时只能开 **1 个**沙箱桌面（`SANDBOX_TEAM_SCREEN_LIMIT=1`）；多开会 OOM |
| **真实瓶颈** | **不是内存，是磁盘**（镜像就吃掉 8.2GB）+ **GHCR 拉取速度** |
| **生产建议** | 升配 **4C8G** + 系统盘扩到 **100G**，能把多 bot 并发和桌面沙箱都放开 |
