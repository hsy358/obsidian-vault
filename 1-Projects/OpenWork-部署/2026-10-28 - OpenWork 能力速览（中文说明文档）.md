# OpenWork 能力速览（中文说明文档）

> 整理自官方文档 https://openworklabs.com/docs/start-here/get-started
> 抓取时间：2026-10-28
> 官方仓库：https://github.com/different-ai/openwork

---

## 一句话定位

**OpenWork 是「Claude Cowork」的开源替代品**——由四件套组成：桌面应用、Web 应用、AI Gateway、MCP Gateway。
核心口号：**掌控你自己的 AI 栈**（你的文件、你的模型、你的 skills、你的使用者），本地免费、无需登录。

---

## 四大组件

| 组件 | 说明 | 关键点 |
|---|---|---|
| **桌面应用** | macOS / Windows / Linux 客户端 | MIT 协议，**50+ 模型供应商**或本地模型 |
| **Web 应用** | 浏览器里的完整 OpenWork 工作区 | 零安装，OpenWork 托管 |
| **AI Gateway** | 模型请求路由 + 计量服务 | 统一接供应商，控制访问/限额/花费 |
| **MCP Gateway** | 一个托管 MCP 服务器 | 把组织的 skills + 连接带进 Claude Code / Codex / Cursor |

> **注意区分**：
> - **AI Gateway** 路由的是**模型**
> - **MCP Gateway** 共享的是**skills 和连接**（不是模型）
> - **OpenWork Models** 是官方托管推理订阅（无需自带 key，单独计费）

## 四步上手（个人）

1. **安装** — 下载对应平台客户端
   - macOS：`brew install --cask openwork`
   - ⚠️ **不要跑 `npx openwork`**，npm 上叫 `openwork` 的是另一个项目
2. **选文件夹** — OpenWork **只在你授权的文件夹内工作**（沙箱边界）
3. **选模型** — 三选一：
   - 用 ChatGPT 订阅登录（Plus / Pro）
   - 填 API Key（Anthropic / 任意 OpenAI 兼容端点）
   - 跑本地模型（Ollama / LM Studio，无需 key、无需云账号）
4. **跑任务** — 官方建议第一句：`Summarize this folder.`（总结这个文件夹）

> 桌面应用**无需登录**即可使用；登录 OpenWork Cloud 只是额外加一层：组织共享、托管工作区、政策管控。

## 核心概念：Connector / Connection / Skill / Plugin / Library

这是理解 OpenWork 的关键一张表（官方原文翻译）：

| 单元 | 含义 | 什么时候用 |
|---|---|---|
| **Connector 连接器** | 组织独立添加的 MCP 服务（不包在 plugin 里） | Agent 需要在某个系统里**动手操作**，你连接一次即可 |
| **Connection 连接** | 你自己登录的那个连接器实例，**每人一份** | 你登录后，Agent 才能**以你的身份**在该系统里操作 |
| **Skill 技能** | 任务匹配时 Agent 加载的**书面指令** | 某件可重复的活需要一份**操作手册** |
| **Plugin 插件** | 一个**打包件**——技能 + MCP server + 其他组件，打包分发 | 几块相关的东西**要一起走** |
| **Library 资源库** | 你当前可用的全部元素的清单（桌面应用 + Cloud 控制台） | 想查看/管理**已有什么** |

**设计理念**：
- 用 **Connector** 触达系统
- 用 **Skill** 描述系统规则（如：工单要怎么开、优先级怎么改、某个动作会出问题怎么绕）
- 用 **Plugin** 把技能打包成可分发的单元
- 底层一切都是 Plugin——让 OpenWork 创建技能时，它其实生成的是「只含这一个技能的小 plugin」，所以大多数人不用纠结"技能还是插件"

**个人技能 vs 系统技能**：系统技能（描述工单系统怎么用）应该全组织共享；个人/工作流专属技能可以留在个人手里。

## AI Gateway（模型网关）

**一句话**：供应商接一次，决定谁能用哪些模型，看到花了多少钱。**成员只管选模型，永远不接触 key。**

**配置 5 步**：
1. **加供应商** — Cloud 控制台 `AI Gateway > AI Providers > Add provider`，从目录里选
2. **定权限** — `Everyone in the organization` 或指定团队/个人；可选全部模型或部分
3. **限模型**（可选）— 选 `Only models you provide`，成员就不能自己加 key
4. **设花费上限** — 按团队或个人设每日/周/月 USD 金额，用完可暂停或告警
5. **测试** — 成员在客户端选模型发提示词，授权模型自动同步

**支持供应商**：OpenAI、Anthropic、Google、**Google Vertex AI**（含 Vertex 上的 Claude）、Azure OpenAI、Microsoft Foundry（Claude）、Amazon Bedrock / Bedrock Mantle、Mistral、OpenRouter、LiteLLM，以及兼容目录供应商。
另外可直连 **LiteLLM 代理**、**Bifrost**（可共存）。

**四大能力**：
- **Key 留在服务端** — 组织凭据集，或每人各自的凭据（Vertex 用 Google 登录、Bedrock 用 AWS IAM Identity Center、Foundry 用 Entra ID、LiteLLM 用个人 key）
- **按团队授权** — 模型分组 → 授权给组织/团队/个人
- **花费限额** — 硬上限 + 可选提额申请
- **按人统计** — 每人一把 key，token 和成本可归因

**⚠️ 成本是估算值**，不是供应商账单——基于上报 token × 公开价格，或供应商返回的成本。

**其他特性**：
- **Auto Model Routing** — 让 OpenWork 为每个 prompt 自动挑合适的模型
- **用量计数** — 无 usage 上报时的估算逻辑

## MCP Gateway（技能网关）

**一句话**：一个托管 MCP 服务器，把组织的 skills、plugins、connections 带进任何 MCP 客户端。

**服务器 URL**（唯一一个，加到任意 MCP 客户端）：
```
https://api.openworklabs.com/mcp/agent
```

**只暴露 2 个工具**（刻意精简，客户端工具列表不膨胀）：
- `search_capabilities` — 找出共享给你的 skills / plugins / workflows / connections
- `execute_capability` — 执行 search 返回的确切能力名

**接入命令一览**：

| 客户端 | 命令 |
|---|---|
| Claude Code | `claude mcp add --transport http openwork https://api.openworklabs.com/mcp/agent` |
| Codex | `codex mcp add openwork --url https://api.openworklabs.com/mcp/agent` |
| VS Code | `code --add-mcp` + URL |
| Cursor | 设置里粘贴 URL，OAuth 登录 |
| ChatGPT | 设置 > MCP servers 粘贴 URL，OAuth 登录 |
| Gemini CLI | `gemini mcp add --transport http openwork https://api.openworklabs.com/mcp/agent` |
| OpenCode | 配置里加远程 MCP 条目 → `opencode mcp auth openwork` |
| Claude Desktop / Windsurf / Zed | 走 `mcp-remote` |

**客户端支持状态（官方声明，重要）**：
- ✅ **OpenCode** — Verified（原生远程 MCP OAuth 端到端通过）
- ⚠️ **其余全部是 "Setup only"** — Codex / Cursor / ChatGPT / Claude Code / VS Code / Windsurf / Zed / Gemini CLI 均**未完成原生验证**
  - Cursor 有个例外：允许 `cursor://anysphere.cursor-mcp/oauth/callback`，但走精确白名单 + 强制 PKCE S256
  - Claude Code / Claude Desktop / Gemini CLI：**"Native proof not complete"**（原生验证未完成）
  - Windsurf / Zed：需通过 `mcp-remote`

> **这个信号很重要**：文档里唯一 Verified 的是 **OpenCode**（也就是 OpenWork 底层的 agent 运行时）。其他客户端的接入是"配置上能跑"而非"官方验证过"。

**OAuth / Token 细节**：
- 远程 **Streamable HTTP MCP** + OAuth
- 受保护资源：`https://api.openworklabs.com/mcp/agent`（RFC9728 protected-resource metadata 发现）
- 授权服务器 / 登录源：`https://app.openworklabs.com/api/auth`
- authorize 与 token 请求**必须且只能带一个** `resource` 值
- 公共客户端**强制 PKCE**，**只支持 S256**
- 重定向 URI 必须是 HTTPS 或 HTTP loopback（RFC 8252）；私有 scheme 拒绝，Cursor 这类原生回调走精确白名单
- Access token 是 **EdDSA 签名的 JWT**，issuer=`https://app.openworklabs.com/api/auth`，audience=`https://api.openworklabs.com/mcp/agent`，**45 分钟过期**
- Refresh token 是**不透明轮换** grant，30 天不活跃窗口，30 秒轮换重叠期；只存 hash，重放（overlap 期内）会再发一个后继，overlap 期后重放返回 `invalid_grant` 并**吊销整个 token 家族**
- **权限每次调用都重新校验**（session + membership）→ 移除成员或吊销 session 立即切断 MCP 访问

**Token scopes**：
- `mcp:read` — 发现、连接状态探测、只读原生 API 操作
- `mcp:write` — **调用外部 MCP provider 工具必需**。即使工具自己声明 `readOnlyHint: true` 也一样——**provider 的提示不被信任为授权依据**
- ⚠️ 现有的只读 token **不会自动升级**，要调 provider 工具需重新授权

**MCP Apps**：部分结果以交互式 `ui://` 视图返回（如连接登录请求、工作流结果）；不支持 App 的客户端得到可读的降级内容。Provider 的 `structuredContent` 保留，OpenWork 的扩展放在带命名空间的 `_meta` 键里。

**自建的 App 就是自己的 MCP Server**：让 Agent 造一个 app/dashboard/交互视图，它会走内置的 `build-an-app` skill——找到所需工具 → 调 `prepare_app` 拿到已接线的 starter → 调 `create_app` 发布（传 React 源码 + 文本降级 + 工具清单）。

## 自托管（Self-host）

**什么时候需要自托管**：想让 OpenWork 跑在自己的服务器 / VPC / 私有云，桌面端远程连过来。
**不需要**自托管的情况：想要托管工作区、团队 Collections、共享供应商 → 用 OpenWork Cloud。

**部署方式**：

| 方式 | 适用 |
|---|---|
| Docker Compose（仅拉镜像） | 单机评估，最快上手 |
| Helm on Amazon EKS | AWS 生产（配 RDS MySQL） |
| Helm on Azure AKS | Azure 生产（Azure Database for MySQL） |
| Helm on Google GKE | GCP 生产（Cloud SQL for MySQL） |
| Terraform modules（beta） | AWS ECS Fargate / Cloud Run / Azure Container Apps（都在 `dev` 分支） |
| 自有容器平台 | 用官方发布的镜像 + 服务边界 |

**服务拆分**：
- **OpenWork app** — 桌面端或 Web 客户端
- **OpenWork server** — 工作区运行时 + API（桌面端自带本地 server；自托管 server 为 web 客户端提供运行时）
- **Den web** — 登录 + 组织管理的前端
- **Den controller** — 认证、团队、访问控制、配发的控制面
- **OpenWork Gateway** — 可选的模型路由 + 计量服务（`ee/apps/gateway`），**不是** `den-gateway` Web 代理

**镜像与端口（自己维护容器部署时）**：
- `openwork-den-web` → 端口 **3005**
- `openwork-den-api` → 端口 **8788**
- `openwork-inference`（可选，Gateway）
- 来自 GHCR，MySQL 8 兼容数据库，两个 hostname 前都要 HTTPS

> **⚠️ 与本机现状直接相关**：我们的部署正是 `openwork-server web --port 8788`，与官方 Den API 端口一致。官方 Helm 安装：
> ```bash
> helm upgrade --install openwork-ee oci://ghcr.io/different-ai/charts/openwork-ee \
>   --version <chart-version> \
>   -f values.prod.yaml
> ```
> `--version` 必须显式 pin（旧 chart 可能默认浮动 tag `latest`）。**数据库迁移要在 Den API 接流量之前完成。**

**关键限制（对我们尤其重要）**：
> 桌面应用**不提供** Share workspace / Connect to remote workspace，它的内置 server **只监听 loopback**。
> 我们现在做的「公网暴露 + nginx 反代 + 自建登录页」是**官方不支持的路径**，属于自己扛的扩展。
> 官方支持远程接入的方式是：自托管 **Den**（web + controller）走 Web 客户端，或桌面端连自托管 server（需确认版本是否支持）。

**网络规划**（官方有专门页面，别照抄概览）：
- 私有网络部署 / 气隙部署（完全隔离）/ 出站网络访问清单 / 证书信任与代理 / 企业桌面端分发（MDM + `desktop-bootstrap.json`）/ 安装包分发 / 网络诊断

**降级策略**：`GATEWAY_ENABLED` 和 `deploymentCapabilities.aiGateway` 是安装配置检查项——**单靠旧的 `inference.enabled: true` 不会启用 Gateway 管理**，且 OpenWork Models 计费是独立的。

## 给德勤项目的借鉴点（我的观察，非官方）

> OpenWork 本身**不是**德勤项目的框架选择（那仍是 Hermes Agent v0.14）。但 OpenWork 的**产品结构**有几处值得抄：

1. **Connector / Connection / Skill / Plugin / Library 五层抽象** — 德勤执行器抽象层可以直接对齐这个模型。特别注意 **Connection 是"每人一份的登录态"** 这一层，正好对应德勤「客户身份透传」的需求。
2. **AI Gateway vs MCP Gateway 职责分离** — 模型走一个网关、skills 走另一个网关，边界清晰。执行器抽象层可以照此切：**模型路由层** 和 **能力暴露层** 分开。
3. **MCP Gateway 只暴露 2 个工具**（search + execute）— 这个「工具列表不膨胀」的设计非常克制，德勤交付给客户时也能用：**一个 search_capabilities 让 Agent 现场查自己有什么**，比预先塞 200 个工具进 context 更省 token。
4. **provider 提示不被信任为授权依据**（`readOnlyHint: true` 也要 `mcp:write`）— 安全基线的一条，DSH 那边的「记忆是数据不是指令」是同一类原则。
5. **权限每次调用重新校验**（session + membership），移除成员立即断权 — 对应德勤的「客户人员离职/换岗，Agent 权限需即时收回」。
6. **Access token 45 分钟 + refresh token 轮换 + 30 天不活跃窗口 + 重放吊销整个 token 家族** — 这套 token 生命周期参数可直接作为德勤 MVP 的安全设计基线。
7. **`ee/` 两年后转 MIT 的承诺**（Stewardship 机制）— 商业合作谈判时值得留意这类"开源核心 + 付费控制面 + 承诺回流"的模式。
