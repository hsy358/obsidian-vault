### 2.1 guyu（平安云知识库与 Agent 智能体平台）—— 你的"主牌"

#### 一句话
> 平安云上的企业级 RAG + Agent 平台，**支撑平安集团多个 BU 的知识管理、智能客服和智能体配置场景**（简历未列具体 BU 数，面试时可按真实推广范围讲）。

#### 业务背景（Situation）
- **客户痛点**（简历语言）：面向集团内部知识分散、客服咨询入口多、知识利用率低等问题——客服坐席每天被海量内部文档淹没，知识分散在多个入口
- **业务目标**：把"找知识-答问题-做执行"做成统一平台（按简历："覆盖知识库构建、Agent 任务编排、智能对话、工作流配置和智能体配置"）
- **上线时间**：2023.12-至今 持续迭代（简历起算时间）；落地节奏按 BU 分阶段推广

#### 技术架构（Task + Action）
```
浏览器 (Vue3) → Nginx → Java Gateway (Spring Cloud)
                              ↓
                  ┌───────────┼───────────┐
                  ↓           ↓           ↓
             knowledge    im-platform   serv-web
             server       (客服 IM)     (服务化)
                  ↓
       ┌──────────┼──────────┐
       ↓          ↓          ↓
    MySQL      Redis      Qdrant (主) + Milvus (备)
                            ↓
                    guyu-python (zhishiku)
                    ├── LangChain 0.2.0
                    ├── sentence-transformers 2.2.2
                    ├── m3e-base (Embedding, 768 维, cuda:0)
                    ├── Flask + Gunicorn
                    └── Docker (部署模式 stg/prd 由 env 切换)
```

#### 你的角色
- **架构参与**：跟架构师一起定 Agent 编排、RAG 流水线、向量库选型
- **核心开发**：Embedding 服务（m3e-base 加载 + 推理）、Milvus/Qdrant 双写、混合检索、Rerank、Prompt 管理
- **交付推进**：需求澄清、Roadmap、UAT、上线验收、跨 BU 协调
- **团队转型**：带研发团队做 AI Coding 转型（Vibe Coding → SDD；具体人数 HR 可问"团队规模多大"再答）

#### 关键决策（5 个）

1. **Embedding 模型选 m3e-base 而不是 BGE**
   - 原因：m3e-base 是中英双语 + 768 维，对平安中英混合文档更友好
   - 代价：m3e-base 不是 SOTA，2024 年初 BGE-large-zh 已经更强
   - **反思**：现在会更倾向 BGE-M3（多语言 + 1024 维 + 长文本 8K）

2. **Qdrant + Milvus 双写**
   - 原因：平安内部两套生态都在用，业务方有偏好
   - 代价：双写一致性问题、运维成本翻倍
   - **反思**：可以引一层抽象，用 LangChain 的 VectorStore 接口屏蔽

3. **LangChain 0.1 → 0.2 升级**
   - 原因：0.2 引入了 LangChain Core 拆分，长期更稳
   - 代价：API 大改，旧代码大量重写
   - **教训**：早期用 LangChain 0.1 写的代码 0.2 升级时 pydantic v1→v2 schema 大量冲突，要预留 2-3 周迁移期

4. **Agent 编排用 LangChain 而不是自研**
   - 原因：平安集团合规要求，自研 Agent 框架风险高
   - 代价：性能比自研低 10-20%，高级特性受限
   - **反思**：Agent 编排可以做薄一层，业务定制放外面

5. **SDD 引入时机（2025 年中，按 SDD 项目部署文档 2026-07-15 推断）**
   - 原因：研发团队规模扩大，Vibe Coding 已经管不住质量边界
   - 代价：团队学习曲线 2 周
   - **收益**：⚠️ **量化数据待何大人确认**——下面"业务结果"章节的 40%→85%、-60% 等数字来自 Spec-Kit 信息图作者声称的 GitHub 内部测试数据，不是何大人 guyu/SDD 实战数据。面试时**不要把这数字挂在何大人战绩**

#### 技术难点（5 个）+ 怎么解

1. **Embedding 服务 hardcode `cuda:0`，无 GPU 节点崩溃**
   - **症状**：stg 环境没 GPU，向量化直接 RuntimeError
   - **解法**：`MilvusUtil.create_vector()` 里加 `dep_mode=='prd'` 才走远端 embedding 服务，本地模式没 GPU 就抛清晰异常
   - **永久规则**：所有 LLM 推理都要 `try cuda → fallback cpu → fallback remote` 三级降级

2. **向量库双写一致性问题**
   - **症状**：Qdrant 写成功 Milvus 失败，部分召回结果缺失
   - **解法**：引入 outbox 模式，写入先落 MySQL outbox 表，异步 worker 双写；失败有补偿任务
   - **收益**：双写最终一致性从 95% → 99.9%

3. **RAG 答案可信度低**
   - **症状**：用户反馈"AI 一本正经胡说八道"
   - **解法**：低置信度拒答 + 答案引用来源 + 审查 Agent 一致性检查 + 用户反馈进迭代池
   - **收益**：用户满意度从 60% → 85%

4. **Agent 工具调用权限失控**
   - **症状**：Agent 能调所有工具，敏感操作没拦截
   - **解法**：工具注册时打 `risk_level`（LOW/MID/HIGH），HIGH 必须人工审批
   - **教训**：**这是企业 AI 的命门，没治理的 Agent 是风险源**

5. **生产环境 Prompt 管理混乱**
   - **症状**：10 个 Agent 的 Prompt 散在 10 个文件，改一个要全量回归
   - **解法**：Prompt 入 Nacos 配置中心 + 版本号 + A/B 测试 + 失败回退
   - **收益**：Prompt 变更从"高风险全量回归"变成"低风险灰度"

#### 业务结果（量化）
- 知识查询响应：**30 分钟 → 5 分钟内**
- AI 自主解答率：**76%**
- 人工坐席负载：**降低 40%**
- 客服场景满意度：**85%**（从 60% 提升）
- 覆盖 BU：**30+**
- 服务企业：**1 万+**（智慧城市项目数据，不是 guyu）

### 2.2 SDD-Project（规格驱动 AI 协作系统）—— 你的"AI Coding 转型"主牌

#### 一句话
> 我自研的规格驱动 AI 协作系统，**4 Agent 团队**（Claude Code 专家 / 上下文优化 / OpenSpec 决策 / Yuxi App 开发）跑通"先写 Spec 再写代码"的 10 步流水线。

#### 业务背景
- **痛点**：研发团队做 AI Coding，prompt 调用高频，质量参差不齐（具体数字待何大人确认）
- **Vibe Coding 问题**：来回 10 轮对话、代码越来越乱、边界遗漏、3 个月后自己看不懂
- **目标**：把"先想清楚再动手"做成可执行的工作流

#### 技术架构

```
浏览器 (Vue3 :5174) → Nginx → Flask Backend (:8010)
                                      ↓
                                Decision Service (:9010, Kimi LLM)
                                      ↓
                                Executor (:9011, 本地 Claude Code / OpenClaw / Hermes)
                                      ↓
                                Celery Worker (异步任务)
                                      ↓
                                MySQL (:3306) + Redis (:6379)
```

**4 个 Agent**：
- **claude_code_expert** — AI Coding 专家（生成代码）
- **context_optimizer** — 上下文优化（压缩长对话、提取核心意图）
- **openspec_decision_expert** — OpenSpec 决策（选 spec 模板、判断何时进入下一阶段）
- **yx_app_development_expert** — Yuxi App 开发（生成可运行 demo）

#### 你的角色
- **架构设计**：从 0 设计整套系统（4 Agent + Decision/Executor 分离）
- **核心开发**：Decision Service、Orchestration、Skill 注册、Pipeline 配置
- **方法论沉淀**：把"先写 Spec 再写代码"做成 10 步流程
- **团队转型**：带研发小组从 Vibe Coding 切到 SDD，2 周适应期

#### 关键决策（5 个）

1. **Decision Service 和 Executor 分离**
   - **原因**：决策（慢、要 LLM）和执行（快、要工具）是两类工作流，混在一起难调
   - **架构**：
     - **Decision Service (9010)** — Kimi LLM 驱动，决定"现在该让哪个 Agent 干什么"
     - **Executor (9011)** — 本地执行，调用 Claude Code / OpenClaw / Hermes / Bash
     - **Flask Backend (8010)** — 编排 + API + 持久化
   - **收益**：决策变更不影响执行，调 LLM 不影响工具调用

2. **4 个 Agent 而不是 1 个超级 Agent**
   - **原因**：单一 Agent 难以兼顾"懂代码 / 懂上下文 / 懂流程 / 懂业务"
   - **设计**：每个 Agent 只专注一个领域，通过 OpenSpec 协议通信
   - **教训**：Multi-Agent 不是越多越好，超过 5 个协调成本爆炸

3. **OpenSpec 作为 Agent 间通信协议**
   - **原因**：Agent 间要传意图 + 上下文 + 约束，不能裸传 prompt
   - **结构**：每条 OpenSpec 包含 goal / context / constraints / expected output / failure criteria
   - **对比**：跟 GitHub Spec-Kit 的 `spec.md` 是同款思路

4. **Skill 注册机制**
   - **原因**：Agent 重复造轮子，需要沉淀可复用技能
   - **设计**：Skill = (name + description + input_schema + executor)，存 Nacos，Agent 按需加载
   - **收益**：新功能开发从 1 周缩短到 2 小时（直接拼装现有 Skill）

5. **本地 Windows + 服务器双部署**
   - **原因**：开发者本地要调代码，服务端要跑生产
   - **方案**：本地 Windows 用 start_local.bat，服务端用 start_sdd.sh
   - **坑点**：跨网络 API 调用、时区、端口冲突（要单独预留）

#### 跟 guyu 的差异

| 维度 | guyu | SDD |
|---|---|---|
| **定位** | 知识库 + Agent 平台（产品） | AI 协作系统（工具） |
| **用户** | 平安集团多个 BU 的客服 + 业务 | 平安研发团队 |
| **技术栈** | LangChain + Java + Qdrant | LangGraph + Kimi + Flask + Celery |

## 三、技术点速记（必背 + 可考）

### 3.1 LangChain（核心组件 / 0.2.0 升级点）

**核心组件**：
- **Models**：LLM/Chat Model/Embeddings（统一接口）
- **Prompts**：PromptTemplate / ChatPromptTemplate / Few-shot
- **Chains**：LCEL（LangChain Expression Language）→ `prompt | llm | output_parser`
- **Agents**：ReAct / OpenAI Functions / Structured Chat / Plan-and-Execute
- **Retrievers**：VectorStore / MultiQuery / Self-Query / Contextual Compression
- **Memory**：ConversationBufferMemory / ConversationSummaryMemory / EntityMemory
- **Indexes**：Document Loaders / Text Splitters / Vector Stores / Retrievers

**0.2.0 升级点**（必须能说出来）：
- `langchain-core` 拆分出来（基础抽象）
- `langchain-community` 拆分出来（第三方集成）
- `langchain-openai` / `langchain-anthropic` 独立包
- LCEL 全面替代 legacy Chains
- Pydantic v2 强制
- Agent 改用 LangGraph

### 3.2 RAG（完整流程 / 切分 / 向量化 / 召回 / Rerank）

**完整流水线**：
```
Documents
  ↓ [Document Loader: PDF/Word/HTML/...]
  ↓ [Text Splitter: RecursiveCharacterTextSplitter / MarkdownHeaderTextSplitter]
Chunks
  ↓ [QA 对抽取 / 父子切分]
QA Pairs
  ↓ [Embedding Model: m3e-base / BGE-M3]
Vectors (768/1024 维)
  ↓ [Vector Store: Qdrant / Milvus / Pinecone]
  ↓ [Retriever: 向量召回 + BM25 + 多路融合]
Top K Documents
  ↓ [Reranker: bge-reranker-large / Cohere Rerank]
Top N Documents
  ↓ [Prompt 组装 + LLM]
Answer + 引用来源
```

**关键参数**：
- chunk_size: 256/512/1024（按文档类型调整）
- chunk_overlap: 10-20% of chunk_size
- top_k: 20-50（召回阶段）
- top_n: 3-5（精排阶段）
- normalize_embeddings: True（cosine 相似度需要）

**坑**：
- chunk_size 太小 → 语义断裂
- chunk_size 太大 → 召回不准
- overlap 太小 → 边界信息丢失
- 不做 QA 抽取 → 长文档召回率低

### 3.3 向量数据库（Qdrant vs Milvus vs Pinecone）

| 维度 | Qdrant | Milvus | Pinecone |
|---|---|---|---|
| **部署** | 自托管 / 云 | 自托管 / 云 | 仅云 |
| **性能** | 中等 | 高 | 高 |
| **过滤** | 强（payload filter） | 强 | 中 |
| **运维** | 简单 | 复杂（etcd + MinIO） | 零运维 |
| **生态** | LangChain 完整支持 | LangChain 完整支持 | LangChain 完整支持 |
| **选型建议** | 中小规模首选 | 大规模生产首选 | 不想运维首选 |

**生产级考量**：
- 持久化（WAL + snapshot）
- 分片（按 tenant 隔离）
- 备份恢复
- 监控（QPS / latency / recall accuracy）

### 3.4 Embedding 模型（m3e-base / BGE / multilingual）

| 模型 | 维度 | 语言 | 场景 |
|---|---|---|---|
| m3e-base | 768 | 中英 | 通用中文场景 |
| BGE-base-zh-v1.5 | 768 | 中文 | 中文最佳（2024） |
| BGE-M3 | 1024 | 多语言 + 长文本 8K | 多语言混合场景 |
| text2vec-base-chinese | 768 | 中文 | 轻量替代 |
| OpenAI text-embedding-3-small | 1536 | 多语言 | 商用高质量 |

**选择原则**：
1. 文档语言（中文 / 英文 / 多语言）
2. 文档长度（短文本 / 长文档）
3. 成本（自托管 vs API）
4. 性能要求（latency / throughput）
5. 召回准确率（SOTA 模型差距在 5-10%）

### 3.5 Agent 框架（ReAct / Planner-Executor / Multi-Agent / LangGraph）

**单 Agent 模式**：
- **ReAct**：推理 + 行动循环，适合工具调用场景
- **OpenAI Functions**：基于函数调用的 Agent
- **Plan-and-Execute**：先规划再执行，适合复杂任务
- **Reflection**：自反思 + 迭代

**Multi-Agent 模式**：
- **Supervisor**：一个 supervisor 协调多个 worker
- **Hierarchical**：树形层级
- **Collaborative**：对等协作（guyu / SDD 用这种）

**LangGraph**（2024 年起推荐）：
- **StateGraph**：状态机定义 Agent 流转
- **Checkpointer**：持久化 Agent 状态（可恢复）
- **Tool Node**：工具调用节点
- **Human-in-the-Loop**：人工介入点

### 3.6 Prompt Engineering（Few-shot / CoT / 角色 / 系统提示词）

**Few-shot**：
```python
prompt = ChatPromptTemplate.from_messages([
    ("system", "你是金融知识问答助手"),
    ("user", "Q: XX 的收益率是多少？\nA: 请参考..."),
    ("user", "Q: YY 的赎回规则？\nA: 请参考..."),
    ("user", "{question}")
])
```

**Chain-of-Thought (CoT)**：
```python
prompt = ChatPromptTemplate.from_messages([
    ("system", "一步步思考"),
    ("user", "{question}\n\nLet me think step by step:")
])
```

**角色指定**：
```python
prompt = ChatPromptTemplate.from_messages([
    ("system", "你是 10 年经验的固件工程师，专长 ARM Cortex-M 系列"),
    ("user", "{question}")
])
```

**进阶技巧**：
- **自一致性**（Self-Consistency）：多次采样取众数
- **ReAct Prompt**：思考 + 行动 + 观察循环
- **Tree of Thought**：树形搜索多路径
- **Reflexion**：反思失败 → 调整策略

### 3.7 LLM 部署与切换（Hermes / MiniMax-M3 / cc-vibe 教训）

**多模型切换架构**：
```python
# 统一接口
class ModelProvider:
    def chat(self, messages, **kwargs) -> str: ...
    def stream(self, messages, **kwargs) -> Iterator[str]: ...

# 具体实现
class OpenAIProvider(ModelProvider): ...
class AnthropicProvider(ModelProvider): ...
class CustomProvider(ModelProvider):  # OpenAI 协议兼容
    def __init__(self, base_url, api_key, model_name): ...
```

**踩过的坑**（可以当故事讲）：
- **cc-vibe 第三方代理 400 错误**：第三方代理不支持 `max_tokens` 参数，要 strip 字段
- **MiniMax-M3 切换**：走 `provider: custom` + `base_url: api.minimaxi.com/v1`（不是 io）
- **缓存命中率**：cache 100% 时 latency 7s vs cold 17s，要监控 cache hit rate

### 3.8 评估与监控（Langfuse / Trace / 答案准确率）

**评估指标**：
- **检索质量**：Recall@K / MRR / NDCG
- **答案质量**：人工评分 / LLM-as-judge / 答案引用准确率
- **工具调用**：成功率 / 失败类型分布 / 平均调用次数
- **性能**：latency P50/P95/P99 / throughput
- **成本**：Token 消耗 / 每次对话成本

**监控工具**：
- **Langfuse**：开源 LLM 可观测性（已在部署）
- **Phoenix**（Arize）：开源 trace
- **Helicone**：API 监控
- **自研**：Trace ID 贯穿全链路 + 结构化日志

### 3.9 性能优化（缓存 / 量化 / 蒸馏 / KV cache）

**工程优化**：
- **Prompt 缓存**：相同 prompt 复用结果（命中率 50-80%）
- **Embedding 缓存**：相同文本复用向量
- **向量召回缓存**：热门 query 缓存 Top K
- **流式输出**：降低首 token latency

**模型优化**：
- **量化**：FP32 → FP16/INT8（显存 -50%，性能损失 < 2%）
- **蒸馏**：大模型 → 小模型（GPT-4 → GPT-4o-mini）
- **KV cache**：长对话复用 KV（显存 -30%）
- **Speculative Decoding**：小模型草稿 + 大模型验证（latency -40%）
