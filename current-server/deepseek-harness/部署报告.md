## 部署流程

### 1. 选 npm 包而不是源码编译（关键决策）

**调研阶段 8/14 的判断**：源码 git clone + pnpm install + tsc -b 全编译——**TS 类型系统不一致**（host/client 分离 + Typert codegen + 4-stage build），tsc 二次编译时 30+ 文件报 `Property 'X' does not exist on TypertClientRemote` 错误，无法生成 `lib/bin.js`。

**解决**：直接用 npm 上已编译好的 `@deepseek-ai/dsh@0.1.0-rc.6`（跳过类型检查和打包），源码 git clone 保留为 `/data/.deepseek-harness.bak/` 作为补丁层。

### 2. 部署步骤（耗时 ~5 分钟）

```bash
# 1) 源码备份（保留可改源码）
mv /data/deepseek-harness /data/.deepseek-harness.bak

# 2) 装 npm 包
mkdir -p /data/dsh && cd /data/dsh
npm init -y > /dev/null
npm install @deepseek-ai/dsh@latest   # 532 包 / 4 分钟

# 3) pm2 后台保活
npm install -g pm2                    # 77 包 / 14 秒
pm2 start ./node_modules/.bin/dsh --name dsh-web -- web --host 127.0.0.1 --port 5180
# 验证: pm2 list → dsh-web online, pid 819991, mem ~140 MB

# 4) nginx 反代（独立 5181 端口避免与 default.conf catch-all 冲突）
sudo tee /etc/nginx/sites-enabled/dsh.conf > /dev/null <<'NGINX'
server {
    listen 5181;
    listen [::]:5181;
    server_name _;
    client_max_body_size 100M;
    access_log /var/log/nginx/dsh.access.log;
    error_log /var/log/nginx/dsh.error.log;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-Prefix /dsh;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 300s;
    proxy_send_timeout 300s;
    proxy_buffering off;
    location /dsh/ {
        proxy_pass http://127.0.0.1:5180/;
        proxy_set_header X-Forwarded-Prefix /dsh;
    }
}
NGINX
sudo nginx -t && sudo systemctl reload nginx

# 5) 开机自启
pm2 startup systemd    # 创建 /etc/systemd/system/pm2-root.service
pm2 save               # freeze 当前 process list

# 6) 自验（4 项）
curl -sI http://127.0.0.1:5181/dsh/                          # 200
curl -s   http://127.0.0.1:5181/dsh/assets/index-*.js        # 200 (442 KB)
curl -s   http://127.0.0.1:5181/dsh/plugins/.../client.js    # 200 (52 KB)
curl -s   http://101.33.212.119:5181/dsh/                    # 200 公网通
```

## 风险与教训

### 教训 1：源码编译失败是 monorepo 早期项目的典型病

`deepseek-ai/deepseek-harness` 是 **0.1.0-rc.6 pre-alpha monorepo**，TS 类型系统依赖：
1. host tsdown → 生成 `lib/types/*.js`（供 client import 用）
2. typert codegen plugin → 生成 remote 类型
3. client tsc → 编译 client plugin 包
4. cli tsdown → 打包 `lib/bin.js`

**任一阶段失败都会连锁**。这跟 8/11 OpenOPC 部署踩坑同模式：0.1.0 项目 + 复杂构建链 = 编译失败率高。**直接用 npm 包是当下最稳路径**。

### 教训 2：源码必须保留以便后续修改

虽然当前用 npm 包跑，但 **monorepo 源码本身是有价值的**：
- 调试 DSH 行为时可加 log
- 自定义 patch 层（DSH 设计支持 `--patch <path>` overlay）
- 提 PR / fork

源码备份在 `/data/.deepseek-harness.bak/`（117 MB），需要时 `mv /data/.deepseek-harness.bak /data/deepseek-harness && cd /data/deepseek-harness && pnpm install && tsc -b` 即可。

### 教训 3：nginx 子路径 vs 子域名选择（最终选子域名）

DSH SPA 用 **绝对路径** `/assets/...`、`/manifest.webmanifest`、`/plugins/...`。**最干净的方案是子域名**：

| 模式 | 实测结果 |
|---|---|
| **子路径 `/dsh/`**（首版尝试） | ❌ **失败**：浏览器请求 `/manifest.webmanifest`（无前缀）→ nginx location /dsh/ 不匹配 → fall through 到 nginx 默认 static → 404 |
| **子路径 + `location /` catch-all + rewrite**（二版尝试） | ❌ **失败**：rewrite 把 `/manifest.webmanifest` 改成 `/dsh/manifest.webmanifest` → DSH 后端不识别 prefix → fallback 到 SPA HTML（content-type 变成 text/html）|
| **子域名 `dsh.101.33.212.119.nip.io`**（三版 = 当前） | ✅ **完美**：DSH 直接 serve 在根路径，浏览器拿到的绝对路径直接命中 DSH，所有资源 200 + 正确 Content-Type |

**为什么子域名方案是唯一可行的**：
- DSH **不支持 `--base-path` 参数**（`dsh web --help` 只有 --host/--port/--trusted-host）
- DSH 后端对未知路径 fallback 到 SPA HTML（这是 SPA 设计，所有 404 都返回 HTML 用于 client-side routing）
- 因此 nginx 改写路径会导致 DSH fallback，**拿不到真实资源**

**子域名方案实现**：
```nginx
server {
    listen 80;
    server_name dsh.101.33.212.119.nip.io;  # nip.io 通配 DNS: *.101.33.212.119.nip.io → 101.33.212.119
    location / {
        proxy_pass http://127.0.0.1:5180;
    }
}
```

**用户访问方式**：浏览器打开 `http://dsh.101.33.212.119.nip.io/` —— **无需改 hosts**，nip.io 公共 DNS 自动解析到 101.33.212.119。

参考 2026-08-15 `semantica.conf`（同样模式 `semantica.101.33.212.119.nip.io`）。

### 自验必须包含"浏览器实际请求的 URL"（MEMORY 教训）

我首次自验时用 Python `urllib` 测的是 `/dsh/manifest.webmanifest`（带前缀），但**浏览器解析 SPA 内的绝对路径时不带前缀**。**自验必须包含浏览器实际发起的 URL**，否则会得到假阳性（200 OK 但浏览器实际 404）。

教训：所有 nginx 前缀反代场景，**自验脚本必须列出 3 种 URL 模式**：
1. 带前缀的（用户从入口点击的）✅ 我测了
2. **不带前缀的（浏览器解析绝对路径后的）** ❌ 我漏了
3. /（root）fallback（应到 SPA）✅ 我测了

### 教训 4："空白页"≠ 渲染失败 — 用 headless 浏览器实际加载验证

**真实空白 vs 假空白**：
- 你在浏览器看到"空白页"可能是浏览器**缓存了旧的 404 / SPA 初始 HTML** 或 **AdBlock/uBlock 类扩展拦截了 nip.io 子域名**
- 真正的"渲染失败"需要看：(a) DOM root 节点是否有内容；(b) 是否有 JS 运行时错误；(c) 关键 UI 元素是否出现

**自验工具升级**：用 puppeteer-core + 系统 chromium（headless: 'new'）真实加载页面：
- `document.getElementById('root').innerHTML.length` 看 SPA 渲染内容长度（DSH 空状态 = 25032 bytes）
- `document.body.innerText` 看可见文字（DSH = "Into the Unknown Preview Choose workspace"）
- `page.on('console')` + `page.on('pageerror')` 抓所有 console error / 运行时异常

**安装 chromium**（用于 headless 自验）：
```bash
sudo apt-get install -y chromium-browser  # 6MB / ~3分钟
```

**安装 puppeteer-core**（用系统 chromium）：
```bash
cd /tmp && npm install puppeteer-core  # 25 包 / 2 秒
```

### 教训 5：DSH SPA WebSocket 长连接 + nginx 配置

DSH 客户端通过 `/api/events.mux` `/api/events.host` 两条 WebSocket 通道跟后端通信，**默认 60s 超时会被 nginx 切断**。

nginx 必要配置：
```nginx
proxy_http_version 1.1;
proxy_set_header Upgrade $http_upgrade;
proxy_set_header Connection "upgrade";
proxy_read_timeout 3600s;
proxy_send_timeout 3600s;
proxy_buffering off;
```

**注意**：DSH 0.1.0-rc.6 WebSocket 实现**有 bug**——即使配置正确，浏览器 console 仍会持续打印 `WebSocket is closed before the connection is established` 和 `[web-runtime] connection lost, retry #N`。这是 DSH pre-alpha 已知问题，**不影响 SPA 渲染**（SPA 渲染完成后 WebSocket 失败只是降级到无实时数据）。

### 教训 6：`--trusted-host` 是子域名方案的必要配置

DSH 用 `--trusted-host` 配置 **browser-trust fence**，防止跨域 fetch / WebSocket。**子域名方案部署必须加 `--trusted-host`**：
```bash
dsh web --trusted-host dsh.101.33.212.119.nip.io --trusted-host dsh.101.33.212.119.nip.io:80
```
不加的话浏览器 console 会持续报 `403 Forbidden`，SPA 拿不到初始化数据。

## 服务器价值评估（再次）

部署后实测 DSH 跑的是一个 **Cordis 插件加载器**（40+ plugin bundle），浏览器打开是 DeepSeek Harness 自己的 Web UI。**对笔记本直接访问价值有限**——这个工具的核心场景是开发者本地 `npx dsh web` 跑 CLI 调试，**不是一个多人协作平台**。

但现在服务器上**确实可访问**，可以作为 DSH 架构的演示平台 / 二次开发基础。
