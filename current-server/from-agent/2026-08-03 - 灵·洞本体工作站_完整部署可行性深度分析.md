# 完整部署可行性深度分析

## 一句话结论

**⚠️ 完整部署（compose.production.yaml 全套 = Caddy 自动 TLS + 2 个域名）—— 当前服务器不支持**，3 个硬阻塞：
1. ❌ **没有第二个公网域名**（需要 2 个不同域名解析到 101.33.212.119）
2. ❌ **没有 Let's Encrypt / certbot**（Caddy 自动 TLS 需要 80/443 端口独占）
3. ❌ **端口全占**：80、443、8443、8080、3100、18080 已被现有服务占用

**✅ 但有 2 个变通方案能跑生产模式（去掉 Caddy，改用现有 nginx）** —— 见 §5。

## 3. 3 个硬阻塞（详细原因）

### 阻塞 ①：第二个域名

`compose.production.yaml` 要求 `ONTOLOGY_API_DOMAIN` ≠ `ONTOLOGY_STUDIO_DOMAIN`：
- 当前 IP `101.33.212.119` 是动态解析（DDNS？）还是静态？—— 没看到 DNS 配置
- 就算挂个 `*.example.cn` 也需要 DNS 服务商配合 A 记录
- **Caddy 自动 TLS 必须用真实可解析的域名**（自签证书会被浏览器拦截）

**真实情况**：我们只有 `101.33.212.119` 一个公网 IP，要变出 2 个域名意味着：
- 选项 1：申请真实域名（如 `ontology.hesiyan.cn` + `studio.hesiyan.cn`）→ 需要 DNS 解析
- 选项 2：用 nip.io / sslip.io 临时域名（不行，Caddy 不认）
- 选项 3：**用现有 nginx + 同一域名的子路径**（`101.33.212.119/api` 给本体，`101.33.212.119/studio` 给 Web）→ 牺牲 Caddy 自动 TLS，改手动 TLS 或 HTTP-only

### 阻塞 ②：Let's Encrypt / certbot

```bash
$ certbot certificates
/usr/bin/bash: line 1: certbot: command not found
$ ls /etc/letsencrypt/
ls: cannot access '/etc/letsencrypt/': No such file or directory
```

**Caddy 在 80 上完成 ACME http-01 挑战**：但 80 已被 nginx 占。如果 nginx 让位，本体 Caddy 才能拿 TLS；或者 nginx 配 80 转发 ACME 挑战给 Caddy。

### 阻塞 ③：端口冲突矩阵

```
端口    当前占用                          本体需求       冲突?
─────────────────────────────────────────────────────────────
80      nginx（公网入口，反代 Dify 等）    Caddy ACME     ❌ 强占
443     dify-nginx（0.0.0.0:443）          Caddy TLS      ❌ 强占
443/udp dify-nginx                        Caddy HTTP/3   ❌ 强占
8080    dify-nginx（0.0.0.0:8080→80）     api 直连        ❌ 强占
3100    yuxi-web-dev（0.0.0.0:3100）      web 容器内      ⚠️ 冲突
18080   agentteams-controller（0.0.0.0:18080→8080）  api loopback  ⚠️ 冲突
8443    onlyoffice                        （本体不用）     无冲突
```

**变通思路**：本体所有容器用 `expose` 内部端口 + 现有 nginx 在 80 上按路径反代，**完全跳过 Caddy**。

## 4. 备份 / 恢复 / 监控能力评估

### ✅ 现成可用

- **`backup` / `restore` 服务**（profile=operations）：脚本 `backup-production.sh` 自动打包 `postgres.dump` + `rdf.tar.gz` + `releases.tar.gz` + SHA256SUMS
- **健康检查**：`/api/v1/health/live` + `/api/v1/health/ready`（后者深度检查 PG + TDB2 + release 落盘）
- **指标端点**：Micrometer 在容器内 `9091`（`/actuator/prometheus`），但仅容器内可见
- **灾备验证**：脚本自带 SHA-256 校验

### ❌ 缺失

- **外部 Prometheus + Alertmanager**：enterprise-controls compose 自带，但 production compose **不包含**（需手动加）
- **异地备份**：脚本生成在 `./backups/`，没有云存储同步逻辑
- **日志收集**：stdout json 日志，无 Loki/ELK 接入
- **SIEM / 通知渠道**：完全缺失

## 5. 2 个可行变通方案

### 方案 A：现有 nginx 前面挂本体（**推荐**）

**思路**：保留本体 Caddy 在容器内，但**让 nginx 反代本体服务**。

```yaml
# compose.nginx-aware.yaml（基于 compose.production.yaml 改造）
services:
  postgres: ...        # 不暴露 host，docker 网络内部
  api:
    expose: ["8080"]   # 不映射 host port
    ...
  web:
    expose: ["3100"]   # 不映射 host port
    ...
  caddy:
    # 不暴露 80/443，改用 18080/18443
    ports:
      - "127.0.0.1:18080:80"     # 本机诊断
      - "127.0.0.1:18443:443"    # 本机 TLS
      - "127.0.0.1:18443:443/udp"
    ...
```

**新增 nginx 反代配置** `/etc/nginx/sites-available/ontology.conf`：
```nginx
# 本体 API 反代
location /api/ {
    proxy_pass http://127.0.0.1:18080/api/;
    # 透传 X-Actor-* + Gateway Token
    proxy_set_header X-Actor-Id "internal";
    proxy_set_header Authorization "Bearer $ont_ontology_gateway";
    proxy_set_header Host api.ontology.local;
    proxy_ssl_server_name on;
    proxy_pass https://127.0.0.1:18443;
}
location /studio/ {
    proxy_pass http://127.0.0.1:18080/;
    ...
}
```

**优点**：
- ✅ 不破坏现有 30+ 容器
- ✅ 走现有公网 IP `101.33.212.119`
- ✅ 不需要新域名（用路径前缀）
- ✅ 不需要 Let's Encrypt（HTTP-only，本机+反代间仍 HTTP 明文）

**缺点**：
- ⚠️ 走 HTTP（无 TLS 终点）—— 仅适用内网/受信任环境
- ⚠️ 失去 Caddy 自动安全头（需 nginx 手动配 CSP/HSTS）
- ⚠️ Caddy 的 `$ONTOLOGY_API_DOMAIN` / `$ONTOLOGY_STUDIO_DOMAIN` 要写假域名（生产配置脚本会校验 `.` —— 可以写 `api.local` / `studio.local`）

### 方案 B：完整公网生产（**等何大人提供域名**）

**前提**：您能提供 2 个域名（或子域名）+ DNS 解析。

```bash
# 1. 准备
api.hesiyan.cn → 101.33.212.119 (A 记录)
studio.hesiyan.cn → 101.33.212.119 (A 记录)

# 2. 安装 certbot（先停 nginx，腾 80）
apt install certbot
certbot certonly --standalone -d api.hesiyan.cn -d studio.hesiyan.cn

# 3. 改本体 Caddyfile 用已有证书（不用 ACME 自动）
# 或保留自动 ACME，让 Caddy 直接 listen 80（停 nginx）

# 4. 启动本体 Caddy
docker compose -f compose.production.yaml up -d caddy
```

**优点**：官方推荐路径，TLS / 头 / 自动续期都现成。
**缺点**：需要域名 + 改 nginx 端口（影响 Dify 等现有服务公网访问）。

## 8. 关键发现 / 风险

### 📌 我推荐的默认路径（A1）

```bash
# 1. 拉仓库（10 秒）
cd /root/projects && git clone --depth 1 https://gitee.com/lucas_YIN/ontology_platform.git ontology-studio
cd ontology-studio

# 2. 准备 .env（5 分钟）
cd services/platform-api
cp .env.example .env.production
sed -i 's/^POSTGRES_PASSWORD=.*/POSTGRES_PASSWORD='$(openssl rand -hex 32)'/' .env.production
sed -i 's/^ONTOLOGY_GATEWAY_TOKEN=.*/ONTOLOGY_GATEWAY_TOKEN='$(openssl rand -hex 48)'/' .env.production
sed -i 's|^ONTOLOGY_API_DOMAIN=.*|ONTOLOGY_API_DOMAIN=api.local|' .env.production
sed -i 's|^ONTOLOGY_STUDIO_DOMAIN=.*|ONTOLOGY_STUDIO_DOMAIN=studio.local|' .env.production

# 3. 验证配置（10 秒）
./scripts/validate-production-config.sh .env.production
# 注意：会校验 ONTOLOGY_API_DOMAIN != ONTOLOGY_STUDIO_DOMAIN，且包含 '.'
# api.local / studio.local 都满足

# 4. 构建镜像（30-60 分钟，含 Maven 首次依赖下载）
cd /root/projects/ontology-studio
npm run test:platform-api  # Java 单元测试
npm run test:studio-web    # Web 单元测试
npm run build:production-images  # 构建 ontology-platform-api:1.0.0 + ontology-studio-web:1.0.0

# 5. 修改 compose 文件：用方案 A 的 expose + 127.0.0.1 端口
# （见 §5 方案 A 完整 YAML）
# 然后启动
cd services/platform-api
docker compose --env-file .env.production -f compose.nginx-aware.yaml up -d

# 6. nginx 前面挂反代
cat > /etc/nginx/sites-available/ontology.conf <<'EOF'
server {
    listen 80;
    server_name _;
    client_max_body_size 200M;
    location /studio/ {
        proxy_pass http://127.0.0.1:18080/;
        proxy_set_header Host studio.local;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forward_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
    location /api/ {
        proxy_pass http://127.0.0.1:18080/api/;
        proxy_set_header Host api.local;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forward_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Actor-Id "gateway";
        proxy_set_header Authorization "Bearer <ONTOLOGY_GATEWAY_TOKEN>";
    }
}
EOF
ln -s /etc/nginx/sites-available/ontology.conf /etc/nginx/sites-enabled/
nginx -t && systemctl reload nginx

# 7. 验证
curl http://101.33.212.119/api/v1/health
# → 200 OK {"status":"UP","components":{...}}
curl http://101.33.212.119/studio/
# → 200 OK HTML
```

### ⚠️ 实施风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| **Maven 镜像在境内慢** | 首次构建可能 60+ 分钟 | 配阿里云 Maven 镜像（~/.m2/settings.xml） |
| **镜像拉取失败（gcr.io/distroless 是 Google）** | 构建卡住 | 配 docker registry mirror 或换 distroless 国内源 |
| **API OOM** | Spring Boot + Jena 默认 512MB-1GB | env 已设 3GB，足够；监控 + 自动重启 |
| **TDB2 单实例约束** | 不能横向扩展 | 官方明确"不要 scale api > 1" |
| **GPL-2.0** | 商业闭源风险 | 评估场景；纯研究/内部 Demo 可用 |
| **UAT 未执行** | 实际使用可能踩坑 | 仅用于 demo / 学习，**不**进客户交付 |
