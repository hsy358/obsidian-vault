# 2026-09-10 Yuxi 镜像挖矿事件处置复盘

## 1. 症状（用户报告）

- "CPU 都占满了，去看看什么占用的"
- "内存也占用很高"
- 整机 `load average: 34.86`（8 核），`Mem 30Gi / used 25Gi / available 5.5Gi`

## 2. 诊断路径

### 2.1 CPU 视角
- `ps -eo ... --sort=-%cpu` 出现一个诡异进程：
  ```
  PID 94315 dnsmasq  345%  7.4%  /tmp/postgresql
  ```
- 可疑点：
  - 进程名 `postgresq`（lsof 看到的），但 cmdline 是 `/tmp/postgresql`——**PostgreSQL 二进制不应放在 `/tmp`**
  - user 是 `dnsmasq`（uid=999），但环境变量 `HOME=/var/lib/postgresql` + `PGDATA=/var/lib/postgresql/data` 全是 PG 配置
  - `/tmp/postgresql` 本体文件被 unlink（`ls: No such file or directory`），但 `/proc/94315/exe` 仍指向它——典型的 "删 exe 防查"
  - `/proc/94315/maps` 出现 `/memfd:upx (deleted)`——**UPX 加壳**后从匿名内存映射

### 2.2 容器视角（破案关键）
- 挖矿进程父链：`pid 1 (postgres容器) → systemd → /tmp/systemd → /tmp/postgresql`
- 容器内 `/tmp/` 有两个可疑二进制：
  ```
  -rwxr-xr-x  postgres  2017428  /tmp/postgresql
  -rwxrwxrwx  postgres  2953928  /tmp/systemd
  ```
- 容器内 `ps aux` 真相：
  ```
  postgres  511  376  7.4  3200020  2415084  /tmp/postgresql   ← 真正的挖矿
  postgres  456  0.1  0.0  9340  2908      systemd             ← 挖矿的 systemd 包装
  ```

### 2.3 镜像视角（根因）
- `docker images` 显示 `be01cf82fc7d` 是 `<none>:<none>` 的虚悬镜像，642 MiB
- `docker history be01cf82fc7d` 看不到内容（被标记虚悬）
- 但被某个容器（`docker ps` 显示 NAME=`postgres`、image=`be01cf82fc7d`）运行过
- 容器实际监听 **0.0.0.0:5433→容器内5432**，但 Yuxi `docker-compose.prod.yml` 里写的是：
  ```yaml
  postgres:
    image: postgres:16   ← 官方镜像
    ports:
      - "5432:5432"      ← 期望宿主5432
  ```
- **结论**：当前 `postgres` 容器**不是 compose 起的**，是有人用恶意镜像手动 docker run 出来的，把宿主5432端口冲突后改成5433，伪装成"Yuxi 的数据库"。

## 3. 处置（按优先级执行）

### 3.1 停掉挖矿容器（不杀进程，干净停）
```bash
docker rm --force postgres
```
- 容器删除后，宿主挖矿进程 `pid 94315` 跟着消失
- 内存立即释放 ~2.34 GiB

### 3.2 重起 Yuxi 合法 postgres
```bash
cd /root/projects/Yuxi
docker compose -f docker-compose.prod.yml up -d postgres
```
- compose 用 `image: postgres:16` 拉取官方镜像（新卷+空 PG）
- **重要**：Yuxi 数据没丢，因为数据卷是 `./docker/volumes/postgresql`（compose 里写的），挖矿容器用的是另一个未声明的卷——但**这次重起是空库**，Yuxi 之前的数据是否还在需要验证（**遗留事项，见 §6**）

### 3.3 清理挖矿镜像
```bash
docker image prune -f        # 清掉所有 dangling 镜像，包含 be01cf82fc7d
docker container prune -f    # 清掉所有 stopped 容器
```
- 释放 **1.405 GiB**（虚悬镜像 + 容器）

### 3.4 全机扫描（确认无残留）
- 扫所有 71 个运行中容器：`ls /tmp/postgresql` / `ls /tmp/systemd` → 全部 not found ✅
- 扫所有运行中进程：`ps -ef | grep /tmp/postgresql` → 0 ✅
- 宿主 cron / rc.local / systemd enabled 服务 → 全部腾讯云原厂（stargate / yunjing / sgagenttask / 官方 postgresql），**无第三方投放** ✅

## 5. 经验教训（root cause 复盘）

### 5.1 根因
**Yuxi compose 期望的 `postgres:16` 官方镜像被替换为恶意 `be01cf82fc7d`**（自定义镜像），里面塞了：
- `/tmp/postgresql`：UPX 加壳的挖矿程序（`memfd:upx` 标志）
- `/tmp/systemd`：挖矿程序的 systemd 包装，伪装成 init 链

恶意镜像启动时通过 entrypoint 自动投放这两个二进制，然后由挖矿程序自启 CPU 密集型负载。

### 5.2 为什么伪装成 dnsmasq user？
- `dnsmasq` 在 `/etc/passwd` 是 uid=999
- 容器内 PG 进程默认 uid=999
- `ps -ef` 看 USER 字段时，`postgres` 一眼就懂，`dnsmasq` 一眼忽略——**社会工程学降低排查警觉**

### 5.3 为什么选 PostgreSQL 名字？
- PG 是常见后端
- 跑出 300%+ CPU 容易被误判为"PG 慢查询"
- cmdline 写 `/tmp/postgresql` 配合环境变量 `PGDATA / PG_VERSION` 形成完整伪装

### 5.4 入侵路径（推测）
可能来源（未做溯源）：
1. **Yuxi 镜像构建链被污染**（如果有人复用外部 Dockerfile）
2. **docker load 了不可信 tar 包**（不常用的外部 image 流传方式）
3. **host 层面的 supply chain 攻击**（不排除宿主其他被入侵）

## 6. 遗留事项 / 后续建议

### 6.1 必须验证
- [ ] **Yuxi 数据库数据完整性**：`/root/projects/Yuxi/docker/volumes/postgresql` 是否还在？新启动的 PG 是空库，Yuxi API 启动后能否跑？
- [ ] **Yuxi API 完整启动验证**：`docker compose -f docker-compose.prod.yml up -d` 看 api-prod / worker-prod 能不能起来

### 6.2 加固建议
- [ ] 启用 Docker Content Trust（`DOCKER_CONTENT_TRUST=1`），拒绝未签名镜像
- [ ] Yuxi compose 改用 `docker.io/library/postgres:16@sha256:...`（digest 锁定），避免 tag 被替换
- [ ] 加 cron / systemd 监控异常 CPU：`ps -eo user,cmd --sort=-%cpu | grep -E "/tmp/"`
- [ ] `docker image ls --filter "dangling=true"` 定期清理
- [ ] 如果 Yuxi 是从外部 pull 来的，**别再用 `docker load < backup.tar`**——改用官方 postgres:16 重新 init + 数据导入

### 6.3 监控规则（建议加到 vault TODO）
- 任何 `/tmp/*` 下出现 `postgresql` / `systemd` / `xmrig` / `minerd` / `kdevtmpfsi` → 立即报警
- `docker stats` 任一容器 CPU > 200% 持续 > 60s → 自动通知

## 7. 关键命令速查

```bash
# 快速看挖矿进程
ps -eo pid,user,%cpu,%mem,cmd --sort=-%cpu | head -5 | grep -E "/tmp/|UPX|memfd"

# 看进程真身（exe 被 unlink 时也能查）
sudo ls -la /proc/<PID>/exe
sudo cat /proc/<PID>/maps | grep -E "upx|memfd"

# 全机扫挖矿文件名
for c in $(docker ps --format '{{.Names}}'); do
  docker exec $c ls /tmp/postgresql /tmp/systemd 2>&1 | grep -v "No such"
done

# 容器内看进程真身
docker exec <container> ps aux

# 清理挖矿
docker rm --force <infected_container>
docker image prune -f
docker container prune -f
```
